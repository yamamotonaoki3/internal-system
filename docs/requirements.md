## 1. 目的

社内の連絡と情報共有で起きている、次の4つの困りごとを解決する。Slack風のワークスペース（チャンネル・ダイレクトメッセージ）を土台にする。

| # | 困りごと | 解決の方向 |
| --- | --- | --- |
| 1 | 案件への問い合わせをメールで行っているため、毎回メールを検索する手間がかかる | 案件ごとにやり取りをまとめ、検索できるようにする |
| 2 | 部署の垣根を超えたコミュニティの場がない | 会社のワークスペースとチャンネル（公開・非公開）を設ける。公開チャンネルは参加しなくても読める |
| 3 | 内線で本人にかけても、欠席・外出でつながらず、かけ直しの二度手間になる | ステータス（在席状況）を共有し、ダイレクトメッセージで用件を残せるようにする |
| 4 | 部署内の連絡手段と、誰がいるかを知る一覧がない | 部署のチャンネル・お知らせと、社員の一覧を設ける |

- このシステムは個人開発・学習用である。実際の会社の社員・案件のデータは使わず、すべて架空のデータで動かす。運用先の会社・社員数は決まっていない
- 規模が大きいため、機能ごとに子Issueに分けて、順に作る（Skill「実装の進め方」）

## 2. 想定する利用者

| 利用者 | すること |
| --- | --- |
| 一般メンバー（一般社員。以降、単に「メンバー」とも書く） | 会社から支給されたユーザーID・メールアドレス・初期パスワードでログインする。パスワードを変更する。チャンネル・ダイレクトメッセージでやり取りする。プロフィール（表示名・アバター画像・ステータス）を設定する（表示名は本人が変更できる（決定）。部署・役職・メールアドレス・内線番号は変更できない）。他の人の表示名を押して、その人の本名を確認する（本名はログイン後の全員が見られる（決定。「未決定事項」#21））。案件の作成を申請する。参加する案件のやり取り、案件のTODOの追加・完了（[5-4](requirements/05-case.md)）、社員一覧の閲覧をする。自分専用の整理スペース（[2-8](requirements/02-workspace-channel.md)）に、見つけたチャンネル・ファイル・メッセージ・案件・DMを登録して整理する（C-67）。権限は初期設定で固定で、画面から編集できない |
| オーナー（別名：部署管理者） | 部署ごとに1人だけ置く管理者。自分の部署について、メンバーとチャンネルの管理、退職処理の申請、チャンネル作成の承認、案件の作成の承認、チャンネルの共通フォルダの作成・編集（[2-7](requirements/02-workspace-channel.md)）、ステータスの代理設定、部署のお知らせの投稿・編集・削除をする（できる操作の初期値は [permissions.md](requirements/permissions.md)）。退職申請は全体管理者が処理し、オーナー自身は所属解除・アカウント無効化を実行できない。アカウントの登録・無効化・パスワードの再発行と、社員の所属部署・役職・メールアドレス・内線番号の変更はできない。オーナーになるのは、部署の作成時に全体管理者が指名した社員（指名しなければ、作った全体管理者が自動でオーナーになる）。指名された社員（全体管理者以外）は、指名と同時に、所属がその部署に移る。交代は、全体管理者が別の人を任命して行い、任命と同時に交代する（前のオーナーは一般メンバーに戻る。前のオーナーが全体管理者の場合は、その部署のオーナーの兼任が外れるだけで、全体管理者のままである。これは権限表の D-1・I-3 から導いた内容）。オーナーを無効化するには、先に全体管理者がオーナーを交代させる必要がある。オーナー自身は、自分の権限を変えられない。オーナーは部署ごとに1人で、会社のワークスペースにはオーナーを置かない（C-93・C-99） |
| 全体管理者 | 会社の代表取締役社長に限る全体管理者。アカウント管理（ユーザーID・メールアドレス・初期パスワードの登録と、メールアドレスの確認、CSVでの一括登録、無効化、無効化したアカウントの再有効化、パスワードの再発行）と、社員の部署・役職・メールアドレス・内線番号の変更（[0-4](requirements/00-foundation.md)）を行えるのは、全体管理者だけ（決定）。部署を作れるのも、全体管理者だけ（決定）。社員の所属部署を決めるのも、全体管理者（決定）。会社名の登録も全体管理者が行う（C-93）。全権限を持ち、ロールは編集できない。オーナーの任命・交代、オーナーの権限の編集（[0-7](requirements/00-foundation.md)・[0-8](requirements/00-foundation.md)）も、全体管理者だけが行う。会社のワークスペース（この表の下の箇条書きを参照）の管理（会社直属のチャンネルの承認など）を本務とする（決定。C-99。全体管理者は常に1人。複数の場合は考えない。O-7）。初代管理者は代表取締役社長本人が初回セットアップで登録し、引き継ぎ先もその時点の代表取締役社長に限る（C-42）。全体管理者は、後任を選び、再認証して引き継げる（[0-10](requirements/00-foundation.md)）。本務の部署を1つ持ち（C-102）、所属の数の制限の対象外として、オーナーに任命された複数の部署でだけ、オーナーを兼ねる（C-107。メンバー・チャンネルの管理、チャンネル作成の承認など。任命されていない部署では、オーナーの権限を持たない。例外：オーナー自身が申請した部署のチャンネル作成の承認（C-107）と、案件の作成の承認（[2-2](requirements/02-workspace-channel.md)・[5-3](requirements/05-case.md)））。ステータスの代理設定と部署のお知らせは、全部署について行える。専用のページで監査ログを閲覧する（[0-6](requirements/00-foundation.md)） |

- ロールは3つ（一般メンバー・オーナー・全体管理者）。「部署管理者」は、オーナーの別名で、別のロールではない
- ワークスペースは会社に1つ置く（決定。C-93。[2-1](requirements/02-workspace-channel.md) AC-5〜AC-9）。初期データとして存在し（作成の操作・作成者はない。投入方法は設計の段階で決める）、全体管理者が会社名を登録する。「全体コミュニティ」「全社ワークスペース」の名称と概念は廃止した。全社員が自動で所属する（新入社員はアカウント登録時に自分の部署と会社のワークスペースの両方に所属する。無効化した社員はどちらにも属さない）。会社のワークスペースの管理は全体管理者の本務で（任命・交代は要らない。全体管理者は1人で確定。O-7）、会社直属のチャンネルの作成は、メンバー全員が申請でき、全体管理者が承認する（全体管理者自身の申請は自分で承認できる。C-105）。初期データとして公開チャンネル「全社連絡」を1つ置く。全員が自動で参加し、アカウント作成と同時に参加者になる（C-50・C-100）。追加チャンネルは通常どおり申請する。部署をまたぐ全社員向けのチャンネル（コミュニティなど）は、会社直属のチャンネルとして置く。招待・メンバーの削除・所属なしのルールは部署の所属だけに当てはまり、会社のワークスペースからは誰も外れず、誰も外せない（無効化（[0-1](requirements/00-foundation.md) AC-9）による場合を除く）。同じ人が、自分の部署の範囲と会社全体の範囲の両方でロールを持てる
- 部署は、「所属・チャンネルの整理・管轄（部署オーナー）」の単位で、ワークスペースとは別である（C-93。旧「ワークスペース＝部署」は廃止）。社員は有効な間、必ず1つの部署にだけ所属する（全体管理者も部署を持つ。複数部署の兼務は範囲外。C-102。新入社員は登録時に指定する）。所属は全体管理者が決める。部署異動は全体管理者が旧部署から新部署へ直接切り替え、所属なしの期間を作らない。所属なしは退職者扱いであり、部署管理者は全体管理者へ退職処理を申請できるが、所属解除・無効化を直接実行できない。全体管理者が退職処理としてアカウントを無効化すると、所属がなくなり、会社のワークスペースからも外れる（C-37・C-104、[0-1](requirements/00-foundation.md) AC-8・AC-9・AC-15・AC-20）。無効化済みの社員は社員向け一覧・招待対象に含めない。所属の変更（別の部署への移動）は全体管理者だけが行う。全体管理者が部署のオーナーを兼ねられるのは、任命された部署だけである
- オーナー・全体管理者も社員であり、メンバーとしての操作（投稿・閲覧など）は、メンバーと同じ条件でできる。公開チャンネルは参加しなくても読めるが（C-94）、参加していない非公開チャンネル・ダイレクトメッセージ・案件の内容は、全体管理者・オーナーも見られない。案件の概要は全員に見える（決定。権限表 Q-38）
- ロールごとの権限は「初期値（シード）」で、後から広げることも狭めることもできる（[0-7](requirements/00-foundation.md)）。ただし実装は2段階（[0-9](requirements/00-foundation.md)）：**第1段階**は、権限の初期値を固定のシードとして入れ、ロール名も固定（初期ロールは3つ）。**第2段階**で、ロールの編集・名前の変更・ロールの新規作成を足す
- 利用者は社員のみ。社外の人は、アカウントが発行されないため、登録も利用もできない
- 社員の招待は、同じ会社の有効社員をチャンネルに招待することとして扱う。通常チャンネルでは招待確定と同時に参加者へ追加し、本人の申込・別の人の許可は不要（C-51）。確定後の辞退・却下・期限切れは設けず、確定前は取り消せる。参加済みの社員には重複招待せず「参加済み」と表示する（C-52）。招待操作はチャンネル参加者が再認証して行う。部署への招待はC-37で廃止。招待記録の保存方法は実装設計で整理する。
- パソコンのブラウザに加えて、スマートフォンのブラウザ（Android・iOS）でも使えるようにする。専用のスマートフォンアプリは作らない（「4. 範囲」、[非機能要件の5](requirements/nonfunctional.md)）

案件の概要は全社員が閲覧できる（件名・状態・担当部署・進捗・納期に、案件番号と取引先名を加えたもの。納期はC-86、案件番号・取引先名はC-89で加えた）。通常の内容は参加者限定だが、2026-10-21の合意により、終了アーカイブの承認済み全社員公開と、公開／再開申請の審査用一時閲覧を限定して認める（5-1・5-5・5-6）。参加者限定案件の非参加者は、件名と、全社員に見える案件番号・取引先名だけを検索できる（C-89）。全社員公開が承認されたアーカイブでは、非参加者も件名・メッセージ・TODO・公開可能な添付ファイル名を検索できる（C-64・C-65）。通常の参加依頼機能は作らず、参加者0人の終了案件の再開申請は別に認める。進捗の0件は「項目なし」とする。

## 4. 範囲（作らないもの）

- **ボイスチャンネル**（音声通話・ビデオ通話を含む）。通知の対象にもしない
- **利用者自身による新規登録**（アカウントは全体管理者が発行する）
- **Googleなど外部のログイン**（独自のログインのみ）
- **伝言の専用機能**（ダイレクトメッセージで代替する）
- 内線電話そのものの連携（着信・発信の機能）。ステータスとダイレクトメッセージで、かけ直しの手間を減らす
- カレンダーとの自動連携（ステータスは手で設定する）
- 専用のスマートフォンアプリ。スマートフォンのブラウザ（Android・iOS）で使えるようにする
- 社外の人の利用
- 冗長な構成・カオステスト（学習用のため）
- 実在の社員・案件のデータの利用（すべて架空のデータで動かす）

同じアプリを複数の会社が利用する機能は作らない（2026-10-21決定C-01）。ワークスペースは会社に1つで、公開チャンネルは参加しなくても読める（C-93・C-94）。参加者限定の内容（非公開チャンネル・DM・案件の内容）の不可視と、案件の参加による部署横断の閲覧は区別する。テストの範囲は、参加者限定リソースの認可と部署オーナーの権限の境界とし、実装設計I-08で見直す（C-101）。
