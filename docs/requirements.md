# internal-system の要件定義書

**状態：ドラフト（利用者の確認中）。** 利用者の合意は得ていない。確認で出た修正は、別のPRで反映する。`nonfunctional.md`・`data-model.md` は、さらに「案」の段階である。

この文書は、要件定義書全体の入口である。目的・利用者・範囲・画面・判定結果・全体の未決定事項と、機能一覧を書く。機能ごとの詳細（機能要件・受け入れ条件・関連するデータ・関連するAPI）は `docs/requirements/` にある（「3. 機能一覧」から辿る）。

要件定義（C-76）で、利用者と対話しながら埋める。決まっていないことは推測で埋めず、「未決定」と書く。この文書に書いて利用者の合意を得るまで、実装に進まない。

## 1. 目的

社内の連絡と情報共有で起きている、次の4つの困りごとを解決する。Slack風のワークスペース（チャンネル・ダイレクトメッセージ）を土台にする。

| # | 困りごと | 解決の方向 |
| --- | --- | --- |
| 1 | 案件への問い合わせをメールで行っているため、毎回メールを検索する手間がかかる | 案件ごとにやり取りをまとめ、検索できるようにする |
| 2 | 部署の垣根を超えたコミュニティの場がない | ワークスペースとチャンネル（公開・非公開）を設ける |
| 3 | 内線で本人にかけても、欠席・外出でつながらず、かけ直しの二度手間になる | ステータス（在席状況）を共有し、ダイレクトメッセージで用件を残せるようにする |
| 4 | 部署内の連絡手段と、誰がいるかを知る一覧がない | 部署のチャンネル・お知らせと、社員の一覧を設ける |

- このシステムは個人開発・学習用である。実際の会社の社員・案件のデータは使わず、すべて架空のデータで動かす。運用先の会社・社員数は決まっていない
- 規模が大きいため、機能ごとに子Issueに分けて、順に作る（Skill「実装の進め方」）

## 2. 想定する利用者

| 利用者 | すること |
| --- | --- |
| 一般メンバー（一般社員。以降、単に「メンバー」とも書く） | 会社から支給されたユーザーID・メールアドレス・初期パスワードでログインする。パスワードを変更する。チャンネル・ダイレクトメッセージでやり取りする。プロフィール（表示名・アバター画像・ステータス）を設定する（表示名は本人が変更できる（決定）。部署・役職・メールアドレス・内線番号は変更できない）。他の人の表示名を押して、その人の本名を確認する（本名はログイン後の全員が見られる（決定。「未決定事項」#21））。案件の作成を申請する。参加する案件のやり取り、案件のTODOの追加・完了（[5-4](requirements/05-case.md)）、社員一覧の閲覧をする。自分専用の整理スペース（[2-8](requirements/02-workspace-channel.md)）に、見つけたチャンネル・ファイル・メッセージを登録して整理する。権限は初期設定で固定で、画面から編集できない |
| オーナー（別名：部署管理者） | ワークスペース（＝部署。この表の下の箇条書きを参照）ごとに1人だけ置く管理者。自分のワークスペースについて、メンバーとチャンネルの管理（メンバーの削除は、そのワークスペースからの所属の解除で、削除された社員は所属なしになる）、チャンネル作成の承認、案件の作成の承認、チャンネルの共通フォルダの作成・編集（[2-7](requirements/02-workspace-channel.md)）、ステータスの代理設定、部署のお知らせの投稿・編集・削除をする（できる操作の初期値は [permissions.md](requirements/permissions.md)）。アカウントの登録・無効化・パスワードの再発行と、社員の部署（所属ワークスペース）・役職・メールアドレス・内線番号の変更はできない。オーナーになるのは、ワークスペースの作成時に全体管理者が指名した社員（指名しなければ、作った全体管理者が自動でオーナーになる）。指名された社員（全体管理者以外）は、指名と同時に、所属がそのワークスペースに移る。交代は、全体管理者が別の人を任命して行い、任命と同時に交代する（前のオーナーは一般メンバーに戻る。前のオーナーが全体管理者の場合は、そのワークスペースのオーナーの兼任が外れるだけで、全体管理者のままである。これは権限表の D-1・I-3 から導いた内容）。オーナーを無効化するには、先に全体管理者がオーナーを交代させる必要がある。オーナー自身は、自分の権限を変えられない。ただし、全社ワークスペースは例外で、オーナーは全体管理者であり、任命・交代は行わない（[2-1](requirements/02-workspace-channel.md) AC-9 ③） |
| 全体管理者 | 一番トップの管理者。アカウント管理（ユーザーID・メールアドレス・初期パスワードの登録と、メールアドレスの確認、CSVでの一括登録、無効化、無効化したアカウントの再有効化、パスワードの再発行）と、社員の部署・役職・メールアドレス・内線番号の変更（[0-4](requirements/00-foundation.md)）を行えるのは、全体管理者だけ（決定）。ワークスペース（＝部署）を作れるのも、全体管理者だけ（決定）。社員の所属ワークスペースを決めるのも、全体管理者（決定）。全権限を持ち、ロールは編集できない。オーナーの任命・交代、オーナーの権限の編集（[0-7](requirements/00-foundation.md)・[0-8](requirements/00-foundation.md)）も、全体管理者だけが行う。全社ワークスペース（この表の下の箇条書きを参照）のオーナーでもある（決定。全体管理者がオーナーの権限を持つ。全体管理者は会社創設者の1人で確定。複数の場合は考えない。O-7）。全体管理者は、後任を選び、再認証して引き継げる（[0-10](requirements/00-foundation.md)）。オーナーに任命されたワークスペースでだけ、オーナーを兼ねる（メンバー・チャンネルの管理、チャンネル作成の承認など。任命されていないワークスペースでは、オーナーの権限を持たない。例外：オーナー自身が申請したチャンネル作成の承認と、案件の作成の承認（[2-2](requirements/02-workspace-channel.md)・[5-3](requirements/05-case.md)））。ステータスの代理設定と部署のお知らせは、全部署について行える。専用のページで監査ログを閲覧する（[0-6](requirements/00-foundation.md)） |

- ロールは3つ（一般メンバー・オーナー・全体管理者）。「部署管理者」は、オーナーの別名で、別のロールではない
- 全社ワークスペースを1つ置く（決定。[permissions.md](requirements/permissions.md) の O-1〜O-6。[2-1](requirements/02-workspace-channel.md) AC-5〜AC-9）。初期データとして存在し（作成の操作・作成者はない。投入方法は設計の段階で決める）、名前は「全体コミュニティ」。全社員が自動で参加し（新入社員はアカウント登録の時点で、自分の部署のワークスペースと両方に参加している。無効化した社員はどのワークスペースにも属さない）、社員の「1つのワークスペースにだけ所属する」の所属の数には数えない。全社ワークスペースのオーナーは全体管理者（任命・交代は要らない。全体管理者は1人で確定。O-7）で、チャンネルの作成は、メンバー全員が申請でき、全体管理者（オーナー）が承認する（オーナー自身の申請は自分で承認できる）。他の部署のワークスペースは見えず、全体コミュニティは全員に見える。部署をまたぐ全社員向けのチャンネル（コミュニティなど）は、ここに置く。招待・メンバーの削除・所属なしのルールは部署のワークスペースだけに当てはまり、全社ワークスペースからは誰も外れず、誰も外せない（無効化（[0-1](requirements/00-foundation.md) AC-9）による場合を除く）。同じ人が、自分の部署のワークスペースと全社ワークスペースの両方でロールを持てる。全体コミュニティは、チャンネルではなくワークスペースである（記録。[2-1](requirements/02-workspace-channel.md) AC-11）。初期チャンネルを置くかは未決定（「未決定事項」#30）
- ワークスペースと部署は同じもの（ワークスペース＝部署）で、1つに統合する。ワークスペースの作成と部署の作成は同じ操作。社員は、1つのワークスペース（＝部署）にだけ所属する（登録時に必ず指定する）。所属は全体管理者が決める。オーナーが「メンバーを削除」すると、その社員の所属が外れて「所属なし」になり、所属なしの間は、どの部署のワークスペースにも入れない（全社ワークスペースには参加したまま。[0-1](requirements/00-foundation.md) AC-15）（所属なしの社員は、他のワークスペースのオーナーが招待できる）。所属の変更（別のワークスペースへの移動）は全体管理者だけが行う。全体管理者は、この所属の制限の対象外（複数のワークスペースで、任命されたワークスペースだけオーナーを兼ねられる）
- オーナー・全体管理者も社員であり、メンバーとしての操作（投稿・閲覧など）は、メンバーと同じ条件でできる。参加していないチャンネル・非公開チャンネル・ダイレクトメッセージ・案件・他のワークスペース（＝部署）の専用チャンネルは、全体管理者・オーナーも見られない
- ロールごとの権限は「初期値（シード）」で、後から広げることも狭めることもできる（[0-7](requirements/00-foundation.md)）。ただし実装は2段階（[0-9](requirements/00-foundation.md)）：**第1段階**は、権限の初期値を固定のシードとして入れ、ロール名も固定（初期ロールは3つ）。**第2段階**で、ロールの編集・名前の変更・ロールの新規作成を足す
- 利用者は社員のみ。社外の人は、アカウントが発行されないため、登録も利用もできない
- 友人の招待は、同じ会社の社員を、ワークスペース・チャンネルに招待することとして扱う（「未決定事項」#6）
- パソコンのブラウザに加えて、スマートフォンのブラウザ（Android・iOS）でも使えるようにする。専用のスマートフォンアプリは作らない（「4. 範囲」、[非機能要件の5](requirements/nonfunctional.md)）

## 4. 範囲（作らないもの）

- **ボイスチャンネル**（音声通話・ビデオ通話を含む）。通知の対象にもしない
- **利用者自身による新規登録**（アカウントは全体管理者が発行する）
- **Googleなど外部のログイン**（独自のログインのみ）
- **伝言の専用機能**（ダイレクトメッセージで代替する）
- 内線電話そのものの連携（着信・発信の機能）。ステータスとダイレクトメッセージで、かけ直しの手間を減らす
- カレンダーとの自動連携（ステータスは手で設定する）
- 専用のスマートフォンアプリ。スマートフォンのブラウザ（Android・iOS）で使えるようにする
- 社外の人の利用
- 冗長な構成・カオステスト（学習用のため）
- 実在の社員・案件のデータの利用（すべて架空のデータで動かす）

「複数の会社・組織を同じアプリで扱うこと」は、ワークスペース（＝部署）を複数作れることとの関係を、「未決定事項」#3（組織ごとのデータ分離）で確定する。

## 5. 画面

画面の一覧・画面の移り変わり・画面ごとの構成は、[screens.md](requirements/screens.md)（案。利用者の確認前）にまとめた。確認した結果の修正は、ここに反映する。HTMLのプロトタイプ（`prototype/`）は、画面構成の確認の後に作る。プロトタイプの対象には、パソコンの画面幅に加えて、スマートフォンの画面幅を含める。

利用者との対話で、次のように決まった。`.harness/config.yaml` への反映は、別のIssueで行う（`harness update`）。

| # | 質問 | 回答 |
| --- | --- | --- |
| A | 個人情報の扱い | 扱う（ユーザーID・表示名・本名・アバター画像・部署・内線番号・メールアドレス）。本名は、表示名を押したときに確認できる（登録・変更する人、見られる人、監査の扱いは「未決定事項」#21・#22）。特に配慮が必要な情報は扱わない |
| B | 管理者機能 | ある（オーナー（別名：部署管理者）・全体管理者。アカウント管理・ワークスペース（＝部署）の作成・オーナーの任命・オーナーの権限の編集・監査ログの閲覧ページは全体管理者のみ） |
| C | 重要な操作（決済・公開範囲を広げる・削除・権限の変更など） | ある（アカウントの発行、ワークスペース（＝部署）の作成（オーナーの指名の有無によらず）、権限の変更（ロールの編集・オーナーの任命・交代）、社員の無効化・再有効化（再有効化を再認証の対象にするかは「未決定事項」#23。案は対象）、チャンネルへの招待・ワークスペースへの招待、投稿・ファイルの削除、チャンネル作成の承認。案件の参加者の追加・削除は再認証を求めない（決定）） |
| D | 複数人での共同作業（同時編集・共有） | ある（案件・案件のTODO・チャンネル・メッセージの共有） |
| E | 組織ごとのデータ分離 | **ある（暫定）**。ワークスペース（＝部署）を複数作れるため、ワークスペースをまたいで見えないことを確かめる。全社ワークスペース「全体コミュニティ」（全社員が自動で参加）は全員に見え、他の部署のワークスペースは見えない（決定。2-1 AC-9）。分離のテストの範囲は、「未決定事項」#3で確定する |
| F | リアルタイムの更新 | ある（メッセージ、リアクション、通知）。方式はADRで決める |
| G | 止まったときの影響 | 小さい（学習用） |

- ASVSのレベル：2（個人情報・管理者の機能・重要な操作がある）。レベル3の検討は、特に配慮が必要な情報を扱わないため行わない
- ペネトレーションテスト：初回のリリースの前に必須（個人情報・管理者の機能・重要な操作・組織ごとのデータ分離がある）
- 有効にした共通仕様：C-09、C-14、C-19、C-20、C-30、C-41、C-64、C-66、C-77、C-79。判定の更新で増えるものは、`harness update` で反映する

## 要件定義で決める機能の項目

| 項目 | 回答 | 決めるときに従う共通仕様 |

| ファイルのアップロード（使う・使わない） | 使う（アバター画像、メッセージ・案件への添付）。保存先はR2 | C-63（ファイルのアップロード） |

- 認証・アップロードの実装は、ひな形を生成し直さず、アプリの中で、Skill「セキュリティ」などの共通仕様（C-12〜C-20、ASVSのレベルの判定 F-26、C-63）に沿って行う
- 認証を使うときは、利用者とセッションを保存するDBが必要になる（C-16）。DBはD1を使う
- 管理者のMFAは求めない（管理者の機能がある（B）ため、理由をADRに記録する。[0-5](requirements/00-foundation.md)）
