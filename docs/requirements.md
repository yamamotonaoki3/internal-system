# internal-system の要件定義書

**状態：ドラフト（利用者の確認中）。** 利用者の合意は得ていない。確認で出た修正は、別のPRで反映する。`nonfunctional.md`・`data-model.md` は、さらに「案」の段階である。

この文書は、要件定義書全体の入口である。目的・利用者・範囲・画面・判定結果・全体の未決定事項と、機能一覧を書く。機能ごとの詳細（機能要件・受け入れ条件・関連するデータ・関連するAPI）は `docs/requirements/` にある（「3. 機能一覧」から辿る）。

要件定義（C-76）で、利用者と対話しながら埋める。決まっていないことは推測で埋めず、「未決定」と書く。この文書に書いて利用者の合意を得るまで、実装に進まない。

## 1. 目的

社内の連絡と情報共有で起きている、次の4つの困りごとを解決する。Slack風のワークスペース（チャンネル・ダイレクトメッセージ）を土台にする。

| # | 困りごと | 解決の方向 |
| --- | --- | --- |
| 1 | 案件への問い合わせをメールで行っているため、毎回メールを検索する手間がかかる | 案件ごとにやり取りをまとめ、検索できるようにする |
| 2 | 部署の垣根を超えたコミュニティの場がない | ワークスペースとチャンネル（公開・非公開）を設ける |
| 3 | 内線で本人にかけても、欠席・外出でつながらず、かけ直しの二度手間になる | ステータス（在席状況）を共有し、ダイレクトメッセージで用件を残せるようにする |
| 4 | 部署内の連絡手段と、誰がいるかを知る一覧がない | 部署のチャンネル・お知らせと、社員の一覧を設ける |

- このシステムは個人開発・学習用である。実際の会社の社員・案件のデータは使わず、すべて架空のデータで動かす。運用先の会社・社員数は決まっていない
- 規模が大きいため、機能ごとに子Issueに分けて、順に作る（Skill「実装の進め方」）

## 2. 想定する利用者

| 利用者 | すること |
| --- | --- |
| メンバー（一般社員） | 会社から支給されたユーザーID・メールアドレス・初期パスワードでログインする。パスワードを変更する。チャンネル・ダイレクトメッセージでやり取りする。プロフィール（表示名・アバター画像・ステータス）を設定する（表示名は本人が変更できる（決定）。部署・役職・メールアドレス・内線番号は変更できない）。他の人の表示名を押して、その人の本名を確認する（本名を誰が見られるかは「未決定事項」#21）。参加する案件のやり取り、社員一覧の閲覧をする |
| ワークスペースのオーナー | ワークスペースのオーナー。管理者の権限を持ち、メンバーとチャンネルを管理する（できる操作と、誰がオーナーになるかは「未決定事項」#2）。ワークスペースを作れるのは全体管理者のみ（決定） |
| 部署管理者 | 自分の部署について、ステータスの代理設定、部署のお知らせの投稿、チャンネル作成の承認をする。アカウントの登録・無効化・パスワードの再発行と、社員の部署・役職・メールアドレス・内線番号の変更はできない。ワークスペースのオーナーとの関係と範囲は「未決定事項」#2 |
| 全体管理者 | 一番トップの管理者。アカウント管理（ユーザーID・メールアドレス・初期パスワードの登録と、メールアドレスの確認、CSVでの一括登録、無効化、無効化したアカウントの再有効化、パスワードの再発行）と、社員の部署・役職・メールアドレス・内線番号の変更（[0-4](requirements/00-foundation.md)）を行えるのは、全体管理者だけ（決定）。ワークスペースと部署を作れるのも、全体管理者だけ（決定）。部署管理者の操作（ステータスの代理設定、チャンネル作成の承認など）も、全部署について行える。専用のページで監査ログを閲覧する（[0-6](requirements/00-foundation.md)）。ワークスペースのオーナーとの関係は「未決定事項」#2 |

- 利用者は社員のみ。社外の人は、アカウントが発行されないため、登録も利用もできない
- 友人の招待は、同じ会社の社員を、ワークスペース・チャンネルに招待することとして扱う（「未決定事項」#6で確認する）
- パソコンのブラウザに加えて、スマートフォンのブラウザ（Android・iOS）でも使えるようにする。専用のスマートフォンアプリは作らない（「4. 範囲」、[非機能要件の5](requirements/nonfunctional.md)）

## 4. 範囲（作らないもの）

- **ボイスチャンネル**（音声通話・ビデオ通話を含む）。通知の対象にもしない
- **利用者自身による新規登録**（アカウントは全体管理者が発行する）
- **Googleなど外部のログイン**（独自のログインのみ）
- **伝言の専用機能**（ダイレクトメッセージで代替する）
- 内線電話そのものの連携（着信・発信の機能）。ステータスとダイレクトメッセージで、かけ直しの手間を減らす
- カレンダーとの自動連携（ステータスは手で設定する）
- 専用のスマートフォンアプリ。スマートフォンのブラウザ（Android・iOS）で使えるようにする
- 社外の人の利用
- 冗長な構成・カオステスト（学習用のため）
- 実在の社員・案件のデータの利用（すべて架空のデータで動かす）

「複数の会社・組織を同じアプリで扱うこと」は、ワークスペースを複数作れることとの関係を、「未決定事項」#3で確定する。

## 5. 画面

画面の一覧・画面の移り変わり・画面ごとの構成は、[screens.md](requirements/screens.md)（案。利用者の確認前）にまとめた。確認した結果の修正は、ここに反映する。HTMLのプロトタイプ（`prototype/`）は、画面構成の確認の後に作る。プロトタイプの対象には、パソコンの画面幅に加えて、スマートフォンの画面幅を含める。

## 6. このプロジェクトの判定結果（F-26）

利用者との対話で、次のように決まった。`.harness/config.yaml` への反映は、別のIssueで行う（`harness update`）。

| # | 質問 | 回答 |
| --- | --- | --- |
| A | 個人情報の扱い | 扱う（ユーザーID・表示名・本名・アバター画像・部署・内線番号・メールアドレス）。本名は、表示名を押したときに確認できる（登録・変更する人、見られる人、監査の扱いは「未決定事項」#21・#22）。特に配慮が必要な情報は扱わない |
| B | 管理者機能 | ある（ワークスペースのオーナー、部署管理者・全体管理者。アカウント管理・ワークスペースと部署の作成・監査ログの閲覧ページは全体管理者のみ） |
| C | 重要な操作（決済・公開範囲を広げる・削除・権限の変更など） | ある（アカウントの発行、権限の変更、社員の無効化・再有効化（再有効化を再認証の対象にするかは「未決定事項」#23。案は対象）、参加者の追加・招待、投稿・ファイルの削除、チャンネル作成の承認） |
| D | 複数人での共同作業（同時編集・共有） | ある（案件・チャンネル・メッセージの共有） |
| E | 組織ごとのデータ分離 | **ある（暫定）**。ワークスペースを複数作れるため、ワークスペースをまたいで見えないことを確かめる。「未決定事項」#3で確定する |
| F | リアルタイムの更新 | ある（メッセージ、リアクション、通知）。方式はADRで決める |
| G | 止まったときの影響 | 小さい（学習用） |

- ASVSのレベル：2（個人情報・管理者の機能・重要な操作がある）。レベル3の検討は、特に配慮が必要な情報を扱わないため行わない
- ペネトレーションテスト：初回のリリースの前に必須（個人情報・管理者の機能・重要な操作・組織ごとのデータ分離がある）
- 有効にした共通仕様：C-09、C-14、C-19、C-20、C-30、C-41、C-64、C-66、C-77、C-79。判定の更新で増えるものは、`harness update` で反映する

## 要件定義で決める機能の項目

| 項目 | 回答 | 決めるときに従う共通仕様 |
