# internal-system の要件定義書

この文書は、要件定義書全体の入口である。目的・利用者・範囲・画面・判定結果・全体の未決定事項と、機能一覧を書く。機能ごとの詳細（機能要件・受け入れ条件・関連するデータ・関連するAPI）は `docs/requirements/` にある（「3. 機能一覧」から辿る）。

要件定義（C-76）で、利用者と対話しながら埋める。決まっていないことは推測で埋めず、「未決定」と書く。この文書に書いて利用者の合意を得るまで、実装に進まない。

## 1. 目的

社内の連絡と情報共有で起きている、次の4つの困りごとを解決する。Slack風のワークスペース（チャンネル・ダイレクトメッセージ）を土台にする。

| # | 困りごと | 解決の方向 |
| --- | --- | --- |
| 1 | 案件への問い合わせをメールで行っているため、毎回メールを検索する手間がかかる | 案件ごとにやり取りをまとめ、検索できるようにする |
| 2 | 部署の垣根を超えたコミュニティの場がない | ワークスペースとチャンネル（公開・非公開）を設ける |
| 3 | 内線で本人にかけても、欠席・外出でつながらず、かけ直しの二度手間になる | ステータス（在席状況）を共有し、ダイレクトメッセージで用件を残せるようにする |
| 4 | 部署内の連絡手段と、誰がいるかを知る一覧がない | 部署のチャンネル・お知らせと、社員の一覧を設ける |

- このシステムは個人開発・学習用である。実際の会社の社員・案件のデータは使わず、すべて架空のデータで動かす。運用先の会社・社員数は決まっていない
- 規模が大きいため、機能ごとに子Issueに分けて、順に作る（Skill「実装の進め方」）

## 2. 想定する利用者

| 利用者 | すること |
| --- | --- |
| メンバー（一般社員） | 会社から支給されたユーザーID・メールアドレス・初期パスワードでログインする。パスワードを変更する。チャンネル・ダイレクトメッセージでやり取りする。プロフィール（アバター画像・表示名・ステータス）を設定する。参加する案件のやり取り、社員一覧の閲覧をする |
| ワークスペースのオーナー | ワークスペースを作った人。管理者の権限を持ち、メンバーとチャンネルを管理する（できる操作は「未決定事項」#2） |
| 部署管理者・全体管理者 | アカウントの発行（ユーザーID・メールアドレス・初期パスワードの登録と、メールアドレスの確認）、部署の社員の管理、ステータスの代理設定、チャンネル作成の承認をする。ワークスペースのオーナーとの関係は「未決定事項」#2。全体管理者だけは、専用のページで監査ログを閲覧する（[0-6](requirements/00-foundation.md)） |

- 利用者は社員のみ。社外の人は、アカウントが発行されないため、登録も利用もできない
- 友人の招待は、同じ会社の社員を、ワークスペース・チャンネルに招待することとして扱う（「未決定事項」#6で確認する）
- パソコンのブラウザに加えて、スマートフォンのブラウザ（Android・iOS）でも使えるようにする。専用のスマートフォンアプリは作らない（「4. 範囲」、[非機能要件の5](requirements/nonfunctional.md)）

## 4. 範囲（作らないもの）

- **ボイスチャンネル**（音声通話・ビデオ通話を含む）。通知の対象にもしない
- **利用者自身による新規登録**（アカウントは管理者が発行する）
- **Googleなど外部のログイン**（独自のログインのみ）
- **伝言の専用機能**（ダイレクトメッセージで代替する）
- 内線電話そのものの連携（着信・発信の機能）。ステータスとダイレクトメッセージで、かけ直しの手間を減らす
- カレンダーとの自動連携（ステータスは手で設定する）
- 専用のスマートフォンアプリ。スマートフォンのブラウザ（Android・iOS）で使えるようにする
- 社外の人の利用
- 冗長な構成・カオステスト（学習用のため）
- 実在の社員・案件のデータの利用（すべて架空のデータで動かす）

「複数の会社・組織を同じアプリで扱うこと」は、ワークスペースを複数作れることとの関係を、「未決定事項」#3で確定する。

## 5. 画面

画面の一覧・画面の移り変わりは、要件定義の合意の後に統括が洗い出し、プロトタイプ（`prototype/`）で確かめる。確かめた結果をここに反映する。プロトタイプの対象には、パソコンの画面幅に加えて、スマートフォンの画面幅を含める。

## 6. このプロジェクトの判定結果（F-26）

利用者との対話で、次のように決まった。`.harness/config.yaml` への反映は、別のIssueで行う（`harness update`）。

| # | 質問 | 回答 |
| --- | --- | --- |
| A | 個人情報の扱い | 扱う（ユーザーID・表示名・アバター画像・部署・内線番号・メールアドレス）。特に配慮が必要な情報は扱わない |
| B | 管理者機能 | ある（ワークスペースのオーナー、部署管理者・全体管理者。監査ログの閲覧ページは全体管理者のみ） |
| C | 重要な操作（決済・公開範囲を広げる・削除・権限の変更など） | ある（アカウントの発行、権限の変更、社員の無効化、参加者の追加・招待、投稿・ファイルの削除、チャンネル作成の承認） |
| D | 複数人での共同作業（同時編集・共有） | ある（案件・チャンネル・メッセージの共有） |
| E | 組織ごとのデータ分離 | **ある（暫定）**。ワークスペースを複数作れるため、ワークスペースをまたいで見えないことを確かめる。「未決定事項」#3で確定する |
| F | リアルタイムの更新 | ある（メッセージ、リアクション、通知）。方式はADRで決める |
| G | 止まったときの影響 | 小さい（学習用） |

- ASVSのレベル：2（個人情報・管理者の機能・重要な操作がある）。レベル3の検討は、特に配慮が必要な情報を扱わないため行わない
- ペネトレーションテスト：初回のリリースの前に必須（個人情報・管理者の機能・重要な操作・組織ごとのデータ分離がある）
- 有効にした共通仕様：C-09、C-14、C-19、C-20、C-30、C-41、C-64、C-66、C-77、C-79。判定の更新で増えるものは、`harness update` で反映する

## 要件定義で決める機能の項目

| 項目 | 回答 | 決めるときに従う共通仕様 |
| --- | --- | --- |
| 認証方式（なし・アプリ独自・OIDC・併用） | アプリ独自（管理者がユーザーID・メールアドレス・初期パスワードを発行し、本人がパスワードを変更する）。Googleなど外部のログインは使わない | C-12〜C-20（認証方式・セッション・MFA など）、F-26（ASVSのレベルの判定） |
| 外部IdP（OIDC・併用のとき） | なし | — |
| ファイルのアップロード（使う・使わない） | 使う（アバター画像、メッセージ・案件への添付）。保存先はR2 | C-63（ファイルのアップロード） |
| 扱うファイルの種類（アップロードを使うとき） | 画像・動画・文書（PDF等） | C-63 |

- 決まった内容は、`.harness/config.yaml` の `answers`（`auth`・`idp`・`file_upload`・`file_kinds`）に反映する。別のIssueで行う
- 認証・アップロードの実装は、ひな形を生成し直さず、アプリの中で、Skill「セキュリティ」などの共通仕様（C-12〜C-20、ASVSのレベルの判定 F-26、C-63）に沿って行う
- 認証を使うときは、利用者とセッションを保存するDBが必要になる（C-16）。DBはD1を使う
- 管理者のMFAは求めない（管理者の機能がある（B）ため、理由をADRに記録する。[0-5](requirements/00-foundation.md)）

## 7. 未決定事項

全体の未決定事項の正は、この表とする。各機能ファイルの「この機能に関わる未決定事項」は、この表の番号を引いたものである。

「決める時期」が「Issueへの分割の前」のものは、利用者と決める。決まらない場合は、安全側（権限を狭く、削除は非表示）として扱う。

| # | 内容 | 決める時期 |
| --- | --- | --- |
| 1 | 案件を作れる人（メンバーも作れるか、部署管理者のみか）と、案件の参加者を追加できる人 | Issueへの分割の前 |
| 2 | 権限の考え方。ワークスペースのオーナーの管理者権限でできる操作の一覧（元の指示が「以下の操作が可能」で途切れている）と、全体管理者・部署管理者との関係（併存するか、オーナーに一本化するか）。チャンネル作成の承認の「管理者」が、全体管理者かオーナーか | Issueへの分割の前 |
| 3 | ワークスペースと部署の関係（部署はワークスペースの中の所属か。1人が複数のワークスペースに入れるか）と、組織ごとのデータ分離（判定E）の確定 | Issueへの分割の前 |
| 4 | （決定済み：初回ログイン時の変更は必須、忘れたときは管理者が再発行する。[0-3](requirements/00-foundation.md)に反映） | — |
