# 0022：全社連絡を補うmigrationを例外的に手作成する

- 状態：採用
- 日付：2026-11-09
- 関係：Issue #200、[ADR-0018](0018-client-initial-seed-migration-exception.md)、[ADR-0021](0021-department-channel-backfill-migration-exception.md)、2-1 AC-16・AC-17、0-1 AC-15、[project-rules.md](../project-rules.md)

## 背景

「全社連絡」は、申請・承認を経ない初期データとして、全員が参加するチャンネルである（2-1 AC-17）。#200でこれを用意し、既存の有効な社員を全員参加させる。既存の行にデータを補う処理は、migrationの生成ツールでは作れない。

## 選択肢

1. 全社連絡を作って社員を参加させる専用の手作成migration（0011）を1本置く
   - 良い点：新規DBでも既存DBでも同じ手順で、全社連絡のある状態になる。適用の記録がmigrationの履歴に残る
   - 悪い点：生成手順と異なる作成手順の例外が増える。名前が衝突すると作れない
2. セットアップのときだけ全社連絡を作る
   - 良い点：migrationの例外が増えない
   - 悪い点：すでにあるDBには全社連絡がない
3. 作らず、全社連絡がない事実を記録するだけにする
   - 良い点：データ移行のリスクがない
   - 悪い点：#200の受け入れ条件（全員が参加する全社連絡）を満たせない

## 決定

選択肢1を採る。

- 手作成を認めるのは「全社連絡の補完」の1本（`0011_seed_company_general_channel.sql`）だけ。ほかの手作成は認めない。0018・0021は変更しない
- 一意性は、生成した0010（`channels_company_general_unique`。`purpose`が`company_general`の行だけの部分一意インデックス）が守る。0011は、文だけで完結し、何度流しても同じ結果になる（べき等）
- 全社連絡がなく、名前「全社連絡」が既存のチャンネル（アーカイブ済みを含む）と衝突する場合は作らず、`audit_logs`に`channel.company_general_backfill`・`failure`を1件だけ記録する。migration自体は失敗させない
- 全社連絡はIDではなく`purpose`で取る。有効な社員（`is_active = 1`）のうち未参加の人を、全員参加させる
- ルームIDはULID形式の固定値で、`backend/src/lib/channel-rules.ts`の`COMPANY_GENERAL_ROOM_ID`と一致させる（テストで突き合わせる）
- 新規のDBでは、セットアップより前に流れるため、参加者0名の全社連絡ができる。最初の管理者は、セットアップのときに参加する
- 本番への適用は、この決定に含まれない。本番適用の前に、ローカルで「0009まで適用→部署・有効な社員・無効な社員を投入→0010・0011を適用→もう一度適用」のリハーサルを行い、利用者の承認を得る

## 理由

アカウント発行・セットアップ・閲覧の認可が、「全社連絡が必ず1つある」ことを前提にできるため。名前の衝突を黙って別名にすると利用者の意図しない名前が付き、migrationを失敗させると適用が止まるため、衝突したときは作らずに記録する。

## 影響

- ADR-0018・0021に続く、手作成migrationの例外の3本目。例外をこれ以上広げない（ほかのデータ移行は、新しいADRで判断する）。
- **名前が衝突して全社連絡を作れなかった場合の復旧**：衝突したチャンネルを改名して衝突を解消し、0011と同じ補完をもう一度行う。それまでは、全社連絡がないため、アカウント発行とセットアップは失敗する（アカウント発行は503）。`audit_logs`の`channel.company_general_backfill`の`failure`の有無は、デモの前に確かめる。
- ルームIDが既存と偶然ぶつかると、主キー違反でmigrationが失敗して適用が止まる（データは壊れない）。
- **ローカルのリハーサルは実施済み**：使い捨てのローカルD1で、0009まで適用 → 部署・有効な社員2名・無効な社員1名を投入 → 0010・0011を適用 → もう一度適用、名前の衝突、新規DBを確かめた。**本番への適用は未実施**で、利用者の承認が別途必要。
- 通常のDBテストは空のDBにmigrationを流すため、補完のmigrationは別に検証が要る（`company-general-backfill.db.test.ts`）。
