# 0014：開発・テスト用の使い捨ての秘密の値は、AIが環境ファイルに書いてよい

- 状態：採用
- 日付：2026-11-04
- 関係：Issue #172（親Issue #108）、`AGENTS.md`「絶対にしないこと（秘密情報）」、`docs/project-rules.md`、`docs/secrets.md`、ADR-0013

## 背景

実装が進むにつれ、開発用・テスト用の環境ファイル（`.env.development`・`.env.test`）に、乱数で作る使い捨ての値（例：`SETUP_TOKEN`・`PII_ENCRYPTION_KEY`・`LOGIN_THROTTLE_KEY`）を入れる作業が、Issueごとに利用者の手作業として発生し、作業が中断されている。

`AGENTS.md`は「秘密情報の値は利用者が入力する。AIは手順とコマンドを案内するだけ」としている。利用者の指示（2026-11-04）に基づき、条件つきで、AIが行ってよい範囲を決めて記録する。

## 選択肢

1. 従来どおり、すべての秘密情報の値を利用者が入力する
   - 良い点：ルールが単純で、AIが値に触れる機会がない
   - 悪い点：Issueごとに手作業が発生し、作業が中断される。使い捨ての値でも同じ負担がかかる
2. 開発・テスト用の、乱数で作る使い捨ての値に限り、AIが`.env.development`・`.env.test`に書いてよい。本番と実在の認証情報は利用者が扱う
   - 良い点：作業が中断されない。漏れても本番に影響しない値に限るため、リスクが小さい
   - 悪い点：AIが値を生成して書くため、値の扱いに条件を守らせる必要がある
3. 本番を含め、すべてAIが入力する
   - 良い点：手作業がなくなる
   - 悪い点：本番の認証情報をAIに扱わせることになり、漏えい時の影響が大きい。採らない

## 決定

選択肢2を採る。**開発・テスト用の、乱数で作る使い捨ての値に限り、AIが`.env.development`・`.env.test`に書いてよい**。

次の条件をすべて守る。

- 対象は`.env.development`と`.env.test`だけ。本番の値（`wrangler secret put`・GitHubのSecretsなど）は、これまでどおり利用者が入れる
- 値は、乱数で作った使い捨てのものに限る。外部サービスの実際のキーなど、実在の認証情報は対象外
- 値を画面・会話・ログに出さず、ファイルを読んで確認しない。項目の有無は、項目名だけを表示する`npm run env:check`で確認する
- 動作確認で値を使うときは、使い捨ての値を使い、確認後に作り直す
- 安全装置（権限の確認などで操作が止められた場合）は、回避せず、利用者に依頼する

## 理由

- 対象が、乱数で作った使い捨ての値に限られるため、漏れても本番のデータや認証情報には影響しない。作り直せば無効にできる
- 本番と実在の認証情報を対象外にすることで、`AGENTS.md`の秘密情報のルールが守ろうとしている、実害の大きい漏えいは防げる
- 利用者の手作業を減らし、Issueごとの中断をなくせる

## 影響

- `AGENTS.md`（ハーネスが管理するファイル）は自分で直さない。ハーネスのルールより緩めるため、`docs/project-rules.md`に記録し、ハーネスへの改善の提案をIssueとして起票する（#172）
- リスクと緩和：値がファイルに残るが、`.gitignore`で除外されたファイルだけに書く。値は乱数で使い捨てのため、疑わしいときは作り直す。作り直すと、その鍵で暗号化した開発・テスト用の架空のデータは読めなくなるが、テスト用DBは `npm run db:reset:test` で作り直せる。本番の鍵（`PII_ENCRYPTION_KEY`）を入れ替えない規則（ADR-0013、`docs/secrets.md`）は、本番と実データの鍵に対するもので、この決定とは競合しない
- 見直す条件：対象に含める値の種類を増やすとき、ハーネス側で同じ運用が取り込まれたとき（取り込まれたら`docs/project-rules.md`の記述を消す）
