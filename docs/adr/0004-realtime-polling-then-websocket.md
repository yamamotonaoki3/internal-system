# 0004：リアルタイム更新は、最初は短い間隔のポーリングで作り、あとでWebSocketに置き換える

- 状態：採用
- 日付：2026-11-02（利用者の承認は2026-11-02〜03）
- 関係：Issue #105、決定記録 T-01・C-145、`docs/requirements/01-messaging.md`の1-9、`docs/requirements/nonfunctional.md`、調査メモ[T-01 リアルタイム更新の方式](../research/T-01-realtime.md)

## 背景

メッセージ・通知・未読の更新を、画面を開いたままの利用者へ3秒以内に反映する必要がある（C-88、1-9 AC-1・AC-2）。画面とAPIは1つのCloudflare Workers（Hono）にまとめ、DBはD1、認証はクッキー方式のセッション（ADR-0003）である。

Workerの1回のリクエストは、別のリクエストや別のisolateへ直接メッセージを送れない。サーバーから「今すぐ押し出す」方式（WebSocket・SSE）には、接続を束ねる場所（実質Durable Objects）が要る。押し出しが不要なポーリングだけが、Durable Objectsなしで成り立つ。

## 選択肢

1. Durable Objects＋WebSocket（Hibernation API）
   - 良い点：反映が即時に近い。待機中はハイバネーションで時間課金が発生しない。接続時にWorkerでクッキーのセッション・`Origin`・権限を確認できる
   - 悪い点：仕組みが増える（Durable Objectsのクラス、バインディング、マイグレーション設定）。テストが難しい。取りこぼしの復旧を自前で設計する。デプロイで接続が切れうる
2. 短い間隔のポーリング（2秒）
   - 良い点：実装とテストが最も単純。Durable Objectsが要らない。3秒以内の要件は、間隔2秒なら平均1秒・最大2秒＋処理時間で満たせる見込み
   - 悪い点：空振りのリクエストが多い。Workers Freeの1日10万リクエストは、同時50人でも約半日で超える見込みで、Workers Paidが前提になる。D1の読み取りが増える
3. ロングポーリング
   - 単独で選ぶ理由が見つからなかった（Workers単体では、待機中にD1を何度も見るか、Durable Objectsに待たせることになり、どちらの良さも中途半端になる）
4. SSE（Server-Sent Events）
   - 送信は別にHTTPのPOSTが要る。押し出しにはDurable Objectsが要る点はWebSocketと同じで、待機中に課金しない仕組みの記載を確認できなかった

## 決定

- **最初は、2秒間隔のポーリングで作る**。Workers Paidを前提にする。
- そのあと、**WebSocket（Durable Objects＋Hibernation）に置き換える**。置き換えは別のIssueで行う。
- 「**最後のID以降を取るAPI**」を、ポーリングとWebSocketの共通の土台にする。WebSocketの再接続時の取りこぼしの補完にも、同じAPIを使う。WebSocketは「更新があった」という合図を押し出す用途に絞り、メッセージ・未読・通知の中身はHTTP API（D1が正本）で取得する。
- 「最後のID以降」が成り立つのは、IDが時刻順に並ぶためである（ADR-0006）。

### WebSocket導入時の確認事項（実装時に確かめること）

- **`Origin`の確認**：WebSocketのアップグレード要求はGETで、`originCheck`（状態を変える操作が対象）の対象外になる。Workerの中で、アップグレード要求にも`Origin`の確認を必ずかける。Cloudflare側が自動で検証するかは公式の記載を確認できなかった
- **クッキー認証**：ブラウザのWebSocketは`Authorization`ヘッダーを付けられない。クッキーが届くのは、アップグレード要求を最初に受けるWorkerである。Workerでセッション（D1）と、その部屋・案件を見る権限を確認してから、Durable Objectへ転送する。`SameSite=Lax`のクッキーがアップグレード要求に付くことは、アプリ内ブラウザ（LINEなど）を含めて実機で確認する
- **権限変更時の切断**：部屋から外された、または無効化された利用者の接続が残らないよう、切断の方法（Durable Objectへの切断指示、または定期的な再確認）を設計する。ADR-0003の「無効化ですべてのセッションを失効させる」と合わせる
- **テスト方法の確認**：`@cloudflare/vitest-pool-workers`で、アップグレード要求を送りDurable Objectを介してメッセージを受け取るテストが書けるか、ハイバネーション後の再開が確かめられるかを、最小の試作で確認する
- そのほか、調査メモの10章（1つのDurable Objectが持てる同時接続数、デプロイ時の切断、iOS Safariのバックグラウンド、参加していない公開チャンネルの購読の単位など）を確認する

## 理由

- ポーリングは実装・テストが最も単純で、Durable Objectsのバインディングやマイグレーション設定が要らない。要件の3秒以内を満たせる見込みがあり、まず動くものを作って機能を先に進められる
- 「最後のID以降を取るAPI」を共通の土台にしておけば、WebSocketへの置き換えは、画面側の更新の取り方の差し替えが中心になる。WebSocketにしても、切断・取りこぼしの補完にこのAPIが要るため、作った分は無駄にならない
- WebSocketは、反映の余裕・切断状態の表示・費用（Hibernationで待機中は課金なし）の面で長期的に有利だが、テスト方法などの未確認事項が多い。ポーリングで先に作ることで、未確認事項を実装の前に抱え込まずに済む

## 影響

- Workers Paidを前提にする（ポーリングの空振りでFreeの上限を超える見込みのため）。同時50人・間隔2秒でのD1の読み取り行数と応答時間（p95で500ミリ秒以下）は、実装時に実測する（未実測）
- 要件1-9には「最初はポーリング」の注記を足す（決定記録C-145）。反映時間の要件（3秒以内）は変えない
- ポーリング間隔を2秒より長くする場合は、3秒以内の要件との整合を決め直す
- WebSocketへの置き換えは別のIssueで行う。そのIssueの計画で、上の確認事項を計画に入れる
- 見直す条件：ポーリングのD1負荷が実測で許容できない、またはWorkers Paidを前提にできない場合は、置き換えの時期を早める
