# 0013：初回セットアップの認証は環境のシークレット（SETUP_TOKEN）で行い、本名はAES-256-GCMで暗号化して保存する

- 状態：採用
- 日付：2026-11-03（利用者の決定 D-5・D-6・D-7）
- 関係：Issue #119、決定記録 C-157・C-158（I-05の一部を決める）、ADR-0007・ADR-0008・ADR-0012、`docs/requirements/00-foundation.md`の0-1 AC-10、`docs/requirements/screens.md`のS-34、[設計書 roles-and-setup.md](../design/roles-and-setup.md)

## 背景

初代の全体管理者は、アプリ内の初回セットアップ（S-34）で登録する。このとき、ログインできる利用者はまだ1人もいないため、通常の認証は使えない。一方で、セットアップのAPI（`POST /api/setup`）は未認証で呼べる入口になるため、第三者に先に初代管理者を作られると、会社の全権限を奪われる。要件（0-1 AC-10）は「初回専用の認証を必要とし、成功後は再利用できない」とし、認証の発行・受け渡しの方式は実装設計に任せていた（I-05）。

また、本名（`users.legal_name`）は個人情報であり、DBの内容が流出しても読めないようにしたい。ADR-0012（ゼロトラスト）は、保存するデータの機密性も守る対象にしている。

## 選択肢

### 初回専用の認証

1. **環境のシークレット（`SETUP_TOKEN`）**：運用者が乱数を作って環境（Workersのシークレット）に入れ、セットアップ画面で入力する。DBに値を持たない。完了後に運用者がシークレットを削除する
2. DBにトークンを保存する：マイグレーションやシードで値を入れる必要があり、DBのバックアップやダンプに秘密が残る。値の受け渡しの経路も別に要る
3. 起動時に生成してログに出す：Workersには「起動」の概念が弱く、ログに秘密を出すことになる（ログの閲覧権限者に漏れる。ログに秘密を書かない原則に反する）
4. 認証なし（未登録の間は誰でも登録できる）：公開直後に第三者に先を越されうる。要件（初回専用の認証が必要）を満たさない

### 本名の保存

1. 平文：DBの流出がそのまま個人情報の流出になる
2. **アプリ側でAES-256-GCMにより暗号化**：鍵は環境のシークレットで、DBと別に置く
3. ハッシュ化：本名は表示・変更の承認で読み出す必要があるため使えない

## 決定

### 初回専用の認証（SETUP_TOKEN）

- 認証は**選択肢1（環境のシークレット）**とする。値は、32バイトの暗号学的乱数をbase64url（パディングなし）にした**ちょうど43文字**とする。作り方と本番での入れ方は`docs/secrets.md`に書く。値を入力するのは利用者で、AIは実行しない
- サーバーは、入力値と設定値を**どちらもSHA-256にして、定数時間で比較**する（長さや内容の違いが処理時間に表れないようにする。`backend/src/lib/setup-token.ts`の`verifySetupToken`）
- 設定が未設定または形式不正のとき、**セットアップだけ**を503にする（アプリ全体は止めない。形式不正は値を出さずにエラーとして記録する。`backend/src/config.ts`）
- 「一度だけ」は、トークンではなく**DBの状態**（全体管理者の割り当てがあるか）で保証する。完了後は、正しいトークンでも**常に409**を返す
- **完了後は、運用者がシークレットを削除する**（`wrangler secret delete SETUP_TOKEN`。利用者が実施する。`docs/secrets.md`）。削除すると、以後は503になる
- 処理の順序は、503（設定の不備）→403（トークンの誤り・欠落）→422（入力の検証）→409（完了済み・同時実行に負けた）とする。トークンを持たない人に、入力の検証の結果や完了の状態を知らせないため
- 失敗（トークンの誤り）は、`logger.audit`にだけ記録する（値は記録しない）。成功は、`audit_logs`に、利用者の作成と同じ`db.batch`で記録する

### 試行制限

- `/api/setup`の**試行制限は、#120でADR-0008の仕組み（接続元単位の制限）ができてから適用する**。本Issue（#119）では適用しない
- それまでの代わりの対策は、(1) トークンが256ビットの乱数で、総当たりが現実的でないこと、(2) 失敗を`logger.audit`に記録して検知できるようにすること、(3) セットアップが終わればシークレットを削除して入口を閉じること、の3点とする。公開APIのレート制限が未整備である間は、セットアップを終えるまで入口を開けておく期間を短くすることが望ましい（具体的な運用の取り決めは未決定）

### 本名の暗号化

- 本名は**AES-256-GCM（WebCrypto）**で暗号化して`users.legal_name`に保存する。保存の形式は`v1:<iv>:<暗号文>`（base64url。先頭は版）とし、将来の鍵や方式の変更に備える
- **AAD（追加の認証データ）には`users.id`**を使う。暗号文を別の利用者の行に写しても復号できない
- 鍵は**環境のシークレット`PII_ENCRYPTION_KEY`**（32バイトの乱数のbase64url）とする。設定の読み込み時と復号時の両方で、デコード後がちょうど32バイトであることを確認する。違えばセットアップを503にする
- 実装は`backend/src/lib/pii-crypto.ts`（`encryptLegalName`・`decryptLegalName`）。改ざん・鍵や行の違い・知らない版・壊れた形式は例外にし、空の値や元の値を返さない
- ログの伏せ字の対象に`legalName`・`legal_name`を足す（`backend/src/lib/logger/logger.ts`）。監査ログの`detail`には本名・メールを入れない

### 本名・表示名の長さ（D-7）

- セットアップでは、本名・表示名とも**1〜30文字**に限る。本名の一般の規則（1〜50文字）は変えない。初期の表示名は本名と同じ値にする

### 未決定のこと（推測で決めない）

- **`PII_ENCRYPTION_KEY`の紛失時の扱い**：紛失すると保存済みの本名を復号できない。控えの置き場所（`docs/secrets.md`の「本番の値を控えておく場所」）は利用者が選ぶ。紛失後の復旧手順は**未決定**
- **鍵のローテーション（鍵の入れ替え）の手順**：版つきの形式（`v1`）で将来の対応はできる形にしたが、複数の鍵を持つ方式・再暗号化の手順・実施の時期は**未決定**。必要になった時点で、新しいADRで決める

## 理由

- 環境のシークレットなら、秘密がDB・ソース・ログに残らず、運用者だけが値を持つ。完了後に削除でき、入口を物理的に閉じられる
- トークンは高いエントロピーなので、パスワード用の遅いハッシュは不要で、SHA-256で足りる（ADR-0008のセッショントークンと同じ考え方）。ハッシュにそろえるのは、比較の時間を長さや内容から切り離すため
- 「一度だけ」をDBの状態で保証すれば、シークレットの削除を忘れても、完了後は乱用できない
- 本名は表示のために復号が要る。AES-GCMは改ざんも検知でき、WebCryptoでWorkersの標準機能だけで実装できる（新しいライブラリが要らない）。AADに行の識別子を入れることで、DBを書き換えられても暗号文の使い回しを防げる

## 影響

- 運用者は、デプロイ時に`SETUP_TOKEN`と`PII_ENCRYPTION_KEY`の2つのシークレットを用意し（`.env.development`・`.env.test`にも利用者が値を入れる）、完了後に`SETUP_TOKEN`を削除する手順が増える
- `/api/setup`の試行制限が入るまでは、トークンの総当たりを受け止める制限がない。上の「それまでの代わりの対策」で補い、#120で適用する（適用したら、このADRに追記するか、新しいADRで置き換える）
- `PII_ENCRYPTION_KEY`を紛失すると、本名を復号できない。本名の更新（変更届の承認）で上書きするまでは、本名を表示できない
- 全体管理者へのTOTP（ADR-0009）は#122で足す。それまでの間、初代管理者はパスワードだけでログインできる状態になる（#119の「決めないこと」に記載）
- 見直す条件：鍵のローテーションが必要になったとき、`/api/setup`の試行制限を入れたとき、セットアップを運用者以外が行う形に変えるとき

## 追記（Issue #120。2026-11-03）：`/api/setup`の試行制限を入れた

上の記述は元のまま残す。「試行制限」の節と「影響」の節にある「`/api/setup`の試行制限は#120で適用する」を、Issue #120で実施した。

- `POST /api/setup`に、**接続元単位の試行制限**（ADR-0008の仕組み。`login_attempts`の`bucket_type='setup_source'`）を入れた。窓15分・受付30回まで・超えたら15分ロックで、ログイン（`source`）とは別の枠で数える。**トークンの確認より前**に受付枠を確保する（総当たりを数えるため）。使い切ると`429`と`Retry-After`
- 処理の順序は、本文の形→接続元の特定・`LOGIN_THROTTLE_KEY`の確認（503）→受付枠（429）→設定の不備503・トークン403→入力の検証422→完了済み409。`GET /api/setup/status`には制限をかけない
- トークンの誤りは、従来どおり`logger.audit`にだけ記録する（値は記録しない）。ロックに入った1回だけを、`audit_logs`に`setup.rate_limited`として記録する
- `LOGIN_THROTTLE_KEY`が未設定・不正なときは、`POST /api/setup`も503になる（制限なしで動かさない）。運用者は、セットアップの前に`LOGIN_THROTTLE_KEY`も入れておく（`docs/secrets.md`）
- 「それまでの代わりの対策」の(1)〜(3)のうち、(2)は`logger.audit`の記録のまま残る。試行制限が入ったため、セットアップを終えるまで入口を開けておく期間を短くする望ましさは、弱まった（具体的な運用の取り決めは未決定のまま）
