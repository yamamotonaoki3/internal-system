# 0009：全体管理者にだけTOTP（認証アプリ）を必須にする

- 状態：採用
- 日付：2026-11-02（利用者の承認は2026-11-02〜03）
- 関係：Issue #105、決定記録 C-151（0-5 AC-5と、要件定義書6章・7章#8の「管理者のMFAは求めない」を置き換える）、`docs/requirements/00-foundation.md`の0-1・0-2・0-5、`docs/requirements.md`の6章、Skill「セキュリティ」、調査メモ[全体設計の方針の下調べ](../research/design-foundation.md)の7章

## 背景

要件定義書6章は「管理者のMFAは求めない（管理者の機能がある（B）ため、理由をADRに記録する）」と決めていた（0-5 AC-5、7章#8）。Skill「セキュリティ」は、MFAの要否を簡易なアプリでも明示的に判断することを求める。

前提は次のとおり。

- 個人情報を扱い（A。本名はログイン後の全員が見られる）、管理者の機能があり（B）、重要な操作がある（C）。止まったときの影響は小さい学習用（G）。ASVSのレベルは2
- メール送信サービスは使わない（C-39）。アカウントは全体管理者が発行し、自己登録はない
- 全体管理者ができること：アカウントの登録・無効化・再有効化、他人のパスワードの再発行（初期パスワードを一度だけ見る。0-3 AC-7）、権限・ロールの変更、オーナーの任命、監査ログの閲覧、チャンネル・案件の物理削除、すべての案件への自動参加（C-134）。再発行したパスワードでその人としてログインできるため、管理者のアカウントが奪われたときの影響は全社員分に及ぶ
- 再認証（0-5）もパスワードだけなので、パスワードが漏れた攻撃者は再認証も通る

## 選択肢

1. MFAなし（再認証・監査ログ・試行制限で補う）：実装・復旧の手間が小さい。パスワード漏えい後の不正ログインを防ぐ層がない
2. 全体管理者だけTOTP（認証アプリ。RFC 6238）：外部サービスの契約が不要で無料。WebCryptoで実装できる。管理者の端末紛失時の復旧手順が要る
3. 全員にTOTP：一般メンバーの負担と復旧の問い合わせが増える。リスクに対して過剰
4. パスキー（WebAuthn）：強いが、実装・テスト・復旧の費用が大きい
5. 重要な操作のたびの追加確認（ステップアップ）：操作ごとの確認は増やせるが、ログイン自体の保護にはならない

## 決定

**全体管理者だけ、TOTP（認証アプリ。RFC 6238）を必須にする**。一般メンバー・部署オーナーには求めない。

- 実装はWebCryptoで自作し、ライブラリを追加しない。外部サービスの契約は不要で、無料
- これは**要件の変更**である。要件定義書6章の「管理者にMFAを求めない」、7章の#8、0-5 AC-5、0-2などの記述を、決定C-151で置き換える（元の記述は残し、置き換えの注記を足す）

### 未決定として残す細部（推測で決めない）

- TOTPの登録の流れ（初代全体管理者の初回セットアップS-34、既存の全体管理者への適用の時期、引き継ぎ時の後任の登録）
- リカバリコードを発行するか、発行する場合の件数・表示・再表示
- TOTPの再発行・解除の方法と、その操作の再認証・監査ログ
- 端末を紛失したときの復旧の手順
- 唯一の全体管理者がTOTPを使えなくなったときの復旧手順（0-3 AC-9・C-32の運用復旧手順との関係）
- TOTPの秘密鍵の保存方法（暗号化の有無と、鍵の保管）
- TOTPの試行制限（ADR-0008の制限との関係）、時刻のずれの許容幅、同じコードの再使用の防止
- ログイン時に聞く画面の流れ（S-02との関係）、プロフィール系の画面の置き場
- 再認証（0-5）にTOTPを含めるか
- ASVSのバージョンと該当項目の番号の確認（この調査では確認していない）

## 理由

- 全体管理者の力が大きく、アカウントが奪われた影響が全社員に及ぶ。再認証・監査ログ・試行制限は、パスワードが漏れた後の不正ログインを防げない。TOTPはそれを防ぐ層になる
- ASVSレベル2は多要素認証に関する要求を含む。管理者にMFAを課すことで、「レベル2を採用する」という判断と矛盾しにくくなる。項目の番号とバージョンは未確認で、実装前に確認する（確認して不適合なら、逸脱として受け入れる場合は理由を記録する）
- 一般メンバー・オーナーに求めないのは、利用者の決定である（管理者の力の大きさに対して、全員に求める負担とのつり合いをとった線引き）。拡大の検討は、下の「見直す条件」に従う
- WebCryptoでTOTPを実装すれば、ライブラリも外部の契約も不要で、メールを使わない方針（C-39）と矛盾しない

## 影響

- 要件の変更：0-1（初代全体管理者の登録）、0-2（ログイン）、0-5、画面（S-02・S-34・プロフィール系）、API、状態遷移、用語集、権限表に反映する。細部が未決定のため、これらの文書には「未決定」と書く
- 唯一の全体管理者がTOTPを失うと、復旧が難しくなる。復旧の手順は未決定で、実装の前に決める必要がある
- 見直す条件：全体管理者が複数になる・外部から管理画面に入る運用になる・個人情報の範囲が広がる・インシデントが起きた場合に、一般メンバーやオーナーへの拡大を検討する
- 運用の注意：管理者のパスワードの強度・保管（パスワードマネージャーの利用など）、監査ログの定期的な確認を運用に書く
