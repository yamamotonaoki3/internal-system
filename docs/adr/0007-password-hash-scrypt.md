# 0007：パスワードのハッシュはnode:cryptoのscryptを採用する（本番で確認して最終決定）

- 状態：採用（本番での確認を経て最終決定する。「影響」の節を参照）
- 日付：2026-11-02（利用者の承認は2026-11-02〜03）
- 関係：Issue #105、決定記録 T-04・C-148、`docs/requirements/00-foundation.md`の0-1・0-3、決定C-34・C-35・C-40・C-41、調査メモ[T-04 パスワードのハッシュ方式とWorkersの処理時間](../research/T-04-password-hash.md)・[T-04 Argon2idの実用性](../research/T-04-argon2id.md)・[D1のみ構成でのスパイク](../research/spike-d1-hash.md)

## 背景

パスワードのハッシュ方式を決める必要があった。OWASPのパスワード保存のチートシートは、Argon2id（最優先）、scrypt、bcrypt、PBKDF2（FIPS-140が必要なときのみ）の順に推奨している。利用者の方針は「OWASPを最優先にする」である。

制約は次のとおり。

- Workersの1リクエストあたりのCPU時間は、Freeが10ミリ秒、Paidが既定30秒（`limits.cpu_ms`で最大5分）。強い方式は、Freeでは収まらない
- WebCrypto（`crypto.subtle`）で使える鍵導出はPBKDF2だけ。`node:crypto`（`nodejs_compat`。互換性日付が2026-08-04以降なら指定なしで使える）では、`argon2`・`argon2Sync`だけが未対応と明記されており、`scrypt`・`pbkdf2`は対応外の明記がない
- 新しいライブラリは、利用者の承認なしに追加できない
- CSV一括登録（最大100人）は、全件成功か全件取消で、初期パスワードを一度だけ表示する（C-34・C-35）

## 選択肢

1. Argon2id（WASMのライブラリ）
   - 良い点：OWASPの最優先
   - 悪い点：候補の`argon2id`（openpgpjs）1.0.1は更新が止まっている。`hash-wasm`はWranglerと組み合わせると`WebAssembly.compile()`が禁止されて動かない報告がある。WASMのArgon2idをWorkersで動かす実績・保守に不安がある。新しいライブラリの追加になる
2. `node:crypto`のscrypt
   - 良い点：ライブラリの追加が不要。OWASPが認める構成がある（N=2^17,r=8,p=1、代替としてN=2^16,r=8,p=2など）。ローカルの実測で、N=2^17も動いた（約230ミリ秒）
   - 悪い点：本番で動くかは未確認。N=2^17はメモリが約128MiB必要で、isolateのメモリ上限（128MB）と同じ大きさ
3. WebCryptoのPBKDF2-HMAC-SHA256（60万回以上）
   - 良い点：ライブラリ・`nodejs_compat`とも不要。ネイティブ実装
   - 悪い点：OWASPでは優先順位が低い。本番にはPBKDF2の反復回数が100,000回までという上限がある、という第三者の報告がある（公式には記載がなく未確認）。ローカルでは1,000,000回まで動いた

## 決定

**`node:crypto`のscryptを採用する**。パラメータは**N=2^16, r=8, p=2**（OWASPの代替構成。メモリは約64MiB）。

- **更新が止まっているライブラリ（`argon2id` 1.0.1）は使わない**。Argon2idのWASMライブラリは、Workersで動かす実績・保守に不安があるため、不採用とする
- **本番（Workers Paid）でメモリ・CPU時間・動作を確認して最終決定する**。確認の手順は、調査メモ[spike-d1-hash.md](../research/spike-d1-hash.md)の6章に基づき、**利用者が実行する**（AIは本番へデプロイしない）。確認で、パラメータ（N・p）を実測に基づいて調整することがある
- **scryptが本番で動かない場合は、PBKDF2-HMAC-SHA256の60万回以上にする**。ただし、本番に反復回数の上限があるかは未確認である。上限が60万回を下回る場合の扱い（OWASPの推奨を下回る回数で運用し、理由を記録するか、別の方式を探すか）は**未決定**
- **保存形式**は、方式・パラメータ・ソルトを含む**自己記述の文字列（PHC形式）**にする。D1の列は1つのパスワードハッシュ列で足りる（C-34：現在のハッシュのみ保持）
- **再ハッシュ**：ログイン成功時に、保存されたハッシュが現行の設定より弱い場合は、新しいハッシュに置き換える。置き換えに失敗しても、ログインの成否は変えず、失敗をログに残す（主の処理に付随する後始末の失敗の扱い）
- **前提**：Workers Paidと、`limits.cpu_ms`の引き上げ（【案】。本番確認で確定する。Freeの10ミリ秒では、どの強い方式も収まらない）
- **CSV一括登録（100人）**：1リクエストで順番に計算する。全件成功か全件取消、初期パスワードは一度だけ表示し、C-34・C-35は変えない。パラメータは**実測で決める**（ローカルの目安：scrypt N=2^14,r=8,p=1で100件が約2.6秒、N=2^17では約23秒の見込み。N=2^16,p=2の100件は未実測）。初期パスワードに軽い方式を使う案（初期パスワードは高エントロピーなため）は、ハッシュの種類が2つになり複雑になるため、今は採用しない。100件がCPU時間に収まらないと実測で分かったときに、改めて検討する
- ログイン試行の制限の判定は、ハッシュの計算より先に行う（ADR-0008）。存在しないIDでも、同じ時間になるようダミーの計算を行う（0-2 AC-7）

## 理由

- OWASPを最優先にする方針に対し、Argon2idは動かす実績・保守の面で、現時点で採用できない。次点のscryptは、ライブラリの追加なしに使える見込みがあり、OWASPが認める構成がある
- N=2^17（OWASPの推奨）はメモリがisolateの上限と同じ大きさで、本番で失敗する可能性が高い。代替のN=2^16,p=2は、メモリを約64MiBに抑えつつOWASPの構成に収まる
- 自己記述の形式にすれば、方式やパラメータを後から引き上げても、ログイン時に古いハッシュを検証して置き換えられる

## 影響

- 本番での確認が済むまで、この決定は暫定である。確認する項目：scryptの動作・メモリ・CPU時間、PBKDF2の反復回数の上限、100件の一括登録がCPU時間に収まるか
- scryptの実装に`nodejs_compat`の有効化または互換性日付2026-08-04以降が要る。ひな形の`wrangler.jsonc`の設定を、実装時に確認する
- 新しいライブラリは追加しない
- 見直す条件：本番でscryptが動かない、Argon2idのWorkers向けの保守されたライブラリが現れた、OWASPの推奨が変わった
