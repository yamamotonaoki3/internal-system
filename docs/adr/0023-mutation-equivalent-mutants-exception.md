# 0023：ファイル別ミューテーションスコア80%の基準に、同値変異体による例外を設ける

- 状態：採用
- 日付：2026-11-10
- 関係：Issue #207、[ADR-0020](0020-test-scope-mutation-e2e.md)、Skill「quality-tools」「testing」、AGENTS.md「テストと品質」、[mutation.md](../testing/mutation.md)

## 背景

2026-11-10のデモ統合の全体ミューテーション（main 30ae59b、全体スコア89.00%）で、4ファイルがファイル別80%未満だった（Issue #207）。#207で振る舞いのテストを足した結果、`client.service.ts`は68.13%から82.42%、`ClientForm.tsx`は76.54%から86.42%に達した。次の2ファイルは、振る舞いのテストでは殺せない「同値変異体」のために、80%に届かない。

- `backend/src/services/authorizer.ts`：17/29（58.62%）
- `frontend/src/features/messages/merge-messages.ts`：10/15（66.67%）

同値変異体とは、元のコードと観察できる振る舞いが同じになる変異である。どんなテストを書いても殺せない。

## 選択肢

1. 本番コードをスコアのために変える（例：使われない引数や比較を書き換えて変異体を消す）
   - 良い点：スコアが80%に届く
   - 悪い点：テストを通すための変更になり、AGENTS.md「テストと品質」に反する。本番コードの意図が不自然になる
2. 内部の配線を`vi.mock`のspyで確かめるテストを足す
   - 良い点：生存した変異体を殺せる
   - 悪い点：実装の写しになり、振る舞いを守るテストではなくなる。実装の整理のたびに壊れる
3. Strykerの除外コメント・設定を足す
   - 良い点：スコアの対象から外せる
   - 悪い点：本番コードの変更であり、Skill「quality-tools」の禁止にあたる。除外の根拠がコードに残らない
4. 同値変異体を、コードの根拠つきで証明し、ADRに例外として記録する
   - 良い点：本番コードもテストも不自然にならない。例外の範囲と根拠が追える
   - 悪い点：基準に例外ができる。証明の誤りが見逃されるおそれがある

## 決定

選択肢4を採る。利用者が2026-11-10に決めた。「テストを通すための変更は行わない」方針に従い、選択肢1・2・3は採らない。

- 次の2ファイルの生存変異体を、同値変異体として例外にする
- 全体スコア（89.00%）と、ほかのファイル別80%の基準は変えない
- 例外は「同値であることをコードの根拠つきで証明し、ADRに記録して利用者の承認を得たもの」に限る
- Strykerの除外コメント・設定は足さない
- 本番コードをスコアのために変えない

### authorizer.ts（生存12件）

各`canManage*`（3関数）につき4件が生存する。行番号は`backend/src/services/authorizer.ts`のもの。

- optionsの`{ logger }`を`{}`にする変異（33・45・57行目）
- `createLogger({ traceId })`を`createLogger({})`にする変異（34・46・58行目）
- 範囲`{ type: "company" }`を`{}`にする変異（35・47・59行目）
- 範囲の`"company"`を`""`にする変異（同じ行）

同値の根拠は次のとおり。

- (a) `backend/src/lib/authorization.ts`の`createAuthorizer`が返す`can`は、`options.logger`を使わない。loggerを使うのは`authorize`の拒否時の記録だけで、`canManage*`は`can`しか呼ばない。よって、loggerに関する変異は結果に影響しない
- (b) 対象の3権限（`perm.client.manage`・`perm.workspace.create`・`perm.account.create`）は、`backend/src/lib/permissions.ts`の`DEPARTMENT_OWNER_ONLY`（`workspace.manage`・`role.workspace.edit`・`role.workspace.assign`）に含まれない。permission-resolverの全体管理者の枝`scope.type === "company" || !departmentOwnerOnly.has(permission)`は、範囲の`type`がcompanyでも空でも付与される。部署オーナーの枝は`type`がdepartmentのときだけで、一般社員・無効・存在しない利用者は空集合になる。よって、範囲を変えても判定結果が変わる入力はない

計画レビュー（opus）がコードを読んで確認した。test-writerが絞った実行で、12件すべてSurvivedであることを確かめた。

### merge-messages.ts（生存5件）

12行目の比較`a.id < b.id ? -1 : a.id > b.id ? 1 : 0`のうち、次の変異が生存する。

- 第1比較の`<`を`<=`にする変異
- 第2比較の`>`を`>=`・`<=`・`true`・`false`にする変異（4件）

同値の根拠は次のとおり。直前でMapによりIDで重複を除くため、並べ替えの比較に等しいIDの組が現れない。等しいIDのときだけ結果が変わる変異は、観察できる振る舞いに現れない。4件の全順列（24通り）と30件の固定した順不同のテストを足しても、結果は変わらなかった。このテストは、並べ替えの退行防止として残す。

## 理由

スコアのためにコードを変えたり、実装の写しになるテストを足したりすると、品質を測る指標が品質を損なう。同値変異体は、定義上、どのテストでも殺せない。そのため、基準を満たせない原因がテストの不足ではないことをコードの根拠で示し、記録して承認を得るほうが、基準の意味を保てる。

計測（取得元はStrykerの`Done in`）：

- 4ファイルの絞った実行：4分10秒（216変異体）
- 3ファイルの絞った実行：3分27秒（187変異体）
- `authorizer.ts`単独：1分50秒（29変異体）

## 影響

- ファイル別の基準に、初めて例外ができる。例外の濫用を防ぐため、ADRへの記録と利用者の承認を必須にする。このADRの2ファイル以外は、例外にならない。
- **見直しの条件**：該当ファイルの本番コードを変えたとき、またはStrykerの変異の種類が変わったときは、例外を見直す。絞った実行で、生存した変異体が上の一覧と同じかを再確認する。
- 同値の証明が誤っていた場合は、殺せる変異体を見逃すことになる。見直しのときに、根拠のコード（`createAuthorizer`の`can`・`DEPARTMENT_OWNER_ONLY`・permission-resolverの枝）が変わっていないかを確かめる。
