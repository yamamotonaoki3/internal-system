# 0038：ブラウザの「戻る」で文書が丸ごと戻る場合（bfcache）は、離れるときに中身を同期して隠し、戻ったときに、自分で取り直したセッションと概要の答えだけで、外す・再試行・読み込み直しを決める

- 状態：採用（Issue #342 の 342-A。決定記録 C-212）
- 日付：2026-11-28
- 関係：Issue #342（この ADR。#323 の5つ目）・#323（親）・#338・#339・#340・#341・#298・#376・#382・#383・#388・#390・#391・#392・#398、決定記録 C-206・C-207・C-208・C-209・C-210・C-211・C-212、[ADR-0033](0033-reload-page-after-access-loss.md)・[ADR-0034](0034-cross-tab-access-loss-hint.md)・[ADR-0035](0035-session-user-mismatch-header.md)・[ADR-0036](0036-case-access-loss-outside-view.md)・[ADR-0020](0020-test-scope-mutation-e2e.md)、[docs/design/access-loss.md](../design/access-loss.md)・[cases.md](../design/cases.md)・[auth-session.md](../design/auth-session.md)・[drafts.md](../design/drafts.md)・[docs/testing/bfcache.md](../testing/bfcache.md)、Skill「frontend」「frontend-state」「security」「testing」

## 背景

- ブラウザは、別の文書へ移るとき、前の文書を、メモリごと凍らせて保存することがある（bfcache）。「戻る」で戻ると、`main.tsx` は実行し直されず、凍る前の画面・入力・キャッシュが、そのまま現れる
- 外された人に、サーバーは新しい中身を返さない。残るのは、ブラウザのメモリの中の、すでに取得した中身である。離れている間に外されていても、戻った直後の文書には、確かめる前の案件の中身が、そのまま出る
- #338〜#341・#339（ADR-0033・0034・0036）の見張りは、取得・通信の結果で動く。戻った文書では、通信と判定が終わるまで、先に画面を隠す仕組みがない。凍っていた間の要求の答えや、凍る前のキャッシュは、資格の根拠にならない
- 文書の利用者（#298）は、戻っても、凍る前と同じ値のまま固定される。API の要求は守られるが、通信の前に出る中身の表示は守れない
- 実際に bfcache に入るかは、ブラウザ・文書の状態による。Playwright は、bfcache による復元を既定で扱えず、合成のイベントでは実際の復元を証明できない。Safari・iOS は、確かめる環境がない（利用者の決定 2026-11-25）
- 計画レビュー1回目で、最初の計画（本番のコードが新規4・変更16以上）は、単独でレビュー・マージできる大きさを超えていると指摘された。利用者の決定（2026-11-28）で、範囲を 342-A に縮めた

## 選択肢

### 戻ったときの動き

| 案 | 内容 | 良い点 | 悪い点 |
| --- | --- | --- | --- |
| A（採用） | 離れるとき、その処理の中で中身を隠す。戻ったとき、自分でセッションと案件の概要を取り直し、資格が残っていれば外し、確かめられなければ隠したまま再試行を出し、外されていれば隠したまま読み込み直す | 資格があれば、入力・画面の状態を保てる（読み込み直さない） | 確かめの間、短く覆う。守りの状態と、覆いの部品が増える |
| B | 戻ったときは、必ず（資格があっても）、隠して読み込み直す | 単純。メモリの古い状態が、すべて消える | 資格がある人も、保存していない入力を失う。利用者の決定（2026-11-25）の「資格があれば、入力と画面の状態を保ち、読み込み直さない」に合わない |
| C | bfcache に入れないようにする（`Cache-Control: no-store` の追加、`unload` の登録など） | 戻っても、文書が新しく作られる | 文書の配信と API の配信は別で、API のヘッダーを根拠にできない。Chrome は条件つきで、`no-store` の文書も bfcache の対象にする。ブラウザごとの成立条件は、確かめきれない。入ることを防ぐ保証にならない |

### 守りが決める材料

| 案 | 内容 | 良い点 | 悪い点 |
| --- | --- | --- | --- |
| A（採用） | 守りが、戻ったときに自分で始めた要求（セッションの直接の取得、対象ごとの概要の直接の取得）の答えだけで決める | 凍っていた間の答え・キャッシュ・通常の取得の答えを、資格の根拠にしない。守りの中に、試行の番号1つ（と登録ごとの識別）だけで完結する | 凍る前に送った通常の要求の、遅い答えによる副作用は、既存の照合（C-210）の範囲でしか防げない（残る範囲） |
| B | 通常の取得の保留・中断、S-17・中継・409 の処理・一覧の比較元に、復元の世代を足す | 凍る前の要求の遅い答えも、強く捨てられる | 本番のコードが新規4・変更16以上になる。Query の取得に中断の信号を渡すと、離れた後の確定が取り消され、合図・下書きの消去が行われなくなる（C-206・C-207 の退行）。#391（条件つき）に分けた |

### 隠し方

| 案 | 内容 | 良い点 | 悪い点 |
| --- | --- | --- | --- |
| A（採用） | 包み（ルーター全体）に、`hidden`・`inert` を、離れる処理の中で直接付ける。毎回の描画の後に、その時点の状態から付け直し、解除のときも DOM から直接外す。隠す前のスクロール・フォーカス・選択範囲を控え、外した後に戻す | 既存の隠し方（#338）と同じで、子のモーダル・popover も隠れる。子を外さないので、入力・開閉の状態が残る | 隠すとスクロールとフォーカスが外れるので、控えて戻す処理が要る。描画の値と DOM の食い違いに、付け直しの契約が要る |
| B | 配置を保つクラス・`inert` で隠す | スクロールを保ちやすい | 子の上書き・最上位の層まで隠れることを、別に保証する必要がある。今回は採らない |

| 案 | 内容 | 良い点 | 悪い点 |

| B | いつも`showModal()`のダイアログにする | 単純 | 開くと、開いている popover が閉じる。戻ったときに、画面の状態が変わる |
| C | いつも通常の要素にする | popover を閉じない | 子のモーダルが開いていると、その外は祖先を隠しても操作できないので（HTML の仕様）、再試行に届かず、確かめの失敗から戻れない（コードレビュー1回目の重大） |

### 戻ったときの確かめの結果ごとの扱い

| 結果 | 採用した扱い | 理由 |
| --- | --- | --- |
| 全件が参加者 | 外して表示の状態を戻す。参加の期間は進めない。読み込み直さない | 通常の確かめの結果を捨てる窓を広げない |
| 外された（`lost`・`notFound`） | 既存の確定の入口へ。片付け → 入口 → 合図 → 下書きの消去 | 既存の順序と印を使い、二重にしない |
| 別の利用者 | 切り替えの入口へ。喪失側の副作用なし | C-209 の優先を保つ |
| 401（HTTP の状態で判定） | 覆ったまま、ページごと読み込み直す（利用者の決定） | ログイン画面のコミットを待つ仕組みを作らない。メモリのキャッシュを失う |
| 概要の 403（利用者の決定） | 中身を片付けて、ページごと読み込み直す。下書きは消さない・合図は送らない | 資格を失っているかもしれないので、入力を保つより、中身を出さないほうを取る。保存していない入力は失う |
| 通信の失敗・5xx・時間切れ・照合で採用できなかった | 隠したまま、再試行を出す。入力は保つ | 確かめられないことを、許可にも喪失にもしない |
| 対象が 0 件（読み込み直しが`idle`） | 覆わず、確かめない（利用者の決定） | 案件の中身を持たない画面の「戻る」の体験を悪くしない |

## 決定

- **案 A（離れるとき同期して隠す → 戻ったとき直接確かめる）を採る**。`frontend/src/features/access-loss/page-restore-guard.ts` の`installPageRestoreGuard`が、`pagehide`・`pageshow`を受ける。登録は`main.tsx`が、見張りの登録の後・描画の前に1回だけ行う（解除しない）。`access-loss`は、`cases`・`auth`の確かめに依存せず、`main.tsx`が関数として渡す（`features/auth`の`verifyDocumentSession`・`features/cases`の`caseAccessTargets`・`verifyBySummaryFetch`・`settleVerifiedCaseAccess`）
- **状態は文書ごとに1つ**：`idle`・`prepared`・`verifying`・`failed`・`handedOff`。既存の読み込み直しの状態（`idle`・`waiting`・`reloading`）とは別に持つ。離れるとき、対象を持つ、または読み込み直しが`idle`でなければ、包みを隠して`prepared`にする。戻ったとき（`pageshow`。`persisted`の値によらない）、`prepared`なら確かめを始める
- **確かめの順**：セッションを新しく直接取って文書の利用者と比べる（`verifyDocumentSession`）→ 同じ利用者のときだけ、対象の全件の概要を、キャッシュの外で直接取る（`verifyBySummaryFetch`の詳しい結果。同時に2件）→ 全件が参加者として採用されたときだけ解除する。キャッシュ・戻る前の要求・通常の取得には合流せず、答えをキャッシュに書き戻さない
- **古い答えは、試行の番号と登録ごとの識別の両方で捨てる**。要求は中断せず、完了したときと、確定の入口を呼ぶ直前に照らす。確定の入口の照合（`stillCurrent`）が成り立たなければ、副作用なしで`unverified`を返し、守りは`failed`にする
- **確定の入口を、見張りから1つ公開する**：`settleVerifiedCaseAccess`。戻り値は`confirmed`・`handedOff`・`unverified`。通常の経路の確定（`settleOutside`）は変えない
- **読み込み直しが`idle`でないときは、案件を確かめない**。セッションだけ確かめ、別の利用者なら先に切り替えの入口を呼ぶ。`reloading`なら、その復元について1回だけ、いまの場所の読み込み直しをやり直す
- **範囲は 342-A**：Query の取得に中断の信号を渡さず、S-17・中継・409 の処理・一覧の比較元に世代を足さない。強い守りは #391、待ちの期限と遷移の行き先の厳密化は #392

## 理由

- 案 A：資格があるときは、入力と画面の状態を保てる（利用者の決定の1）。凍っていた間の答え・キャッシュを根拠にしないので、確かめられたものだけを外す。確かめられないものを、許可にも喪失にもしない（Skill「frontend-state」「security」）
- 案 C（bfcache に入れない）を採らない理由：入ることを防げる保証が、配信・ブラウザの両方に無い。防げなかったときの守りが、いずれにせよ要る
- 離れる処理の中で同期して隠す：描画や非同期の処理を待つと、戻った直後の最初の描画に中身が見える。捕捉・通知・描画への同期が例外で終わっても、隠すことを先にする
- 毎回の描画の後に付け直し、解除のときも直接外す：直接付けた属性を、古い描画の値で取り消さず・残さないため。描画への通知が失敗しても、再試行が成功すれば外れる
- 試行の番号だけでなく、登録ごとの識別も照らす：解除して登録し直すと、番号は初期に戻り、古い完了と番号が一致しうるため
- 401 と 403 を、読み込み直しにする：ログイン画面の描画を待つ仕組み（`App.tsx` の変更）は、単独でレビューできる大きさを超える。403 は、資格を失っているかもしれず、中身を出さないほうを、入力を保つより優先する（利用者の決定）
- 失敗の覆いを、子のモーダルがあるときだけ`showModal()`にする：文書の仕様で、モーダルのダイアログが開いていると、その外は、祖先を`hidden`にしても、操作できない。覆いをいつもモーダルにすると、開いている popover が閉じる。両方を満たすには、子のモーダルがあるときだけ、モーダルにするしかない
- 参加の期間を進めない：通常の確かめの結果を、復元の答えで捨てる窓を広げないため。通常の経路の動きは変えない
- 範囲を縮めた：1つの Issue で、単独でレビュー・マージできる大きさに収める（計画レビュー1回目の重大。利用者の決定）。大きくする代わりの案は #391・#392 に分けた

## 影響

- フロントエンドに、新しいファイルが2つ増える（`access-loss/page-restore-guard.ts`・`auth/verify-document-session.ts`）。変更するのは、`AccessLossBoundary.tsx`・`reload-after-access-loss.ts`（入口を1つ足す）・`cases`の3ファイル（`case-access-evidence.ts`・`case-access-verification.ts`・`case-access-loss-monitor.ts`）・各機能の`index.ts`・`main.tsx`・`stryker.config.json`（ミューテーションの対象の登録）。API・DB は変えない。`verifyBySummaryFetch`は、1つの引数の呼び出しの戻り値・投げ方を変えず、詳しい結果を返す呼び方を足した
- `main.tsx`に、全画面に作用する守りを登録し、覆いの境界を変えるので、ADR-0020 (c) により、E2E は全件（開発用・本番形）。ミューテーションは、認可に関わるファイルの絞った診断（ADR-0028 の B）
- ADR-0033・0034・0036 の「残る範囲」の bfcache（#342）は、342-A で扱った（各 ADR に、元の記述を残して、追記した）
- **残る範囲（「戻ったときの全部を解消した」とは言わない）**：
  - 凍る前に送った要求の遅い答えによる副作用は、C-210 の照合の範囲でだけ防ぐ（強い守りは #391。条件つき）
  - 読み込み直しの待ちの上限（5秒）は、凍っていた時間の分だけ延びうる。遷移の元の種類・行き先の再現も、現在の場所の読み込み直しにとどまる（#392）
  - 検索だけの経路は扱わない（#388）。通常の例外後の印・Refetch 側の例外の契約など（#390）、テストの準備の完了待ち（#398）も、この決定の範囲外
  - ログインが切れていたとき（401）は、ページごと読み込み直すので、メモリのキャッシュを失う
  - 概要の 403 の読み込み直しでは、保存していない入力を失う
  - セッションのキャッシュが無い文書は、戻ったときに確かめない（画面は認証の枠が止める。メモリの案件のキャッシュは残る）
  - 概要の 409 の後のセッションの取り直しが 401 のときは、`failed`を経てから、再試行で読み込み直す（#382 と同じ経路）
  - 子のモーダルを開いたまま失敗すると、開いている auto の popover が閉じる。その覆いを開けなかったときは、保存していない入力を失う（例外はテストが差し替えて起こしただけ）。子のモーダルが無いときの覆いをクリックすると、開いている popover が閉じうる（未検証）
  - 合成のイベントの E2E は、実際の復元の証拠ではない。**実際の復元は、通常のブラウザでの確かめ（M0〜M3。[bfcache.md](../testing/bfcache.md)）で行う。まだ行っていない**。Safari・iOS は未確認
- 見直す条件：通常のブラウザの確かめや使用中に、凍る前の要求の遅い答えによる、具体的な失敗が再現したとき（#391 を行う）。Safari・iOS の確認環境が整ったとき。復元の覆いの動きを変える、HTML の仕様・ブラウザの実装の変更があったとき
