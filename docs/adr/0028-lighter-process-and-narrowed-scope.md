# 0028：進め方を軽くし、範囲を絞る（文書・テストだけの差分のレビュー省略、ミューテーションの後回し、計画レビューの回数、並列の進め方）

- 状態：採用（2026-11-16 利用者決定。[Issue #267](https://github.com/yamamotonaoki3/internal-system/issues/267)）
- 日付：2026-11-16
- 関係：Issue #267、Issue #138、[ADR-0016](0016-supervised-automation.md)、[ADR-0020](0020-test-scope-mutation-e2e.md)、リリース前の検証 #160、Skill「実装の進め方」、Skill「レビュー」、Skill「品質チェックの道具」、[project-rules.md](../project-rules.md)

## 背景

2026-11-16 時点で、機能の実装が約35件残っている。直近の実績は1日あたり1〜1.5件で、このままでは完了まで5〜7週間かかる。

#138 では、軽微な指摘が1件出るたびに、CI と最新の状態（head の SHA が一致するレビュー）の確認を1周し、それが1日に3回あった。また、ミューテーションの絞った診断でマージを約3時間待った。その間に見つかった本番の不具合は0件だった。

利用者は、進め方を軽くすることと、範囲を絞ることを決めた。

## 決定

次の4つで、ハーネスのルールより緩める。

| 区分 | 決定 | 緩めるハーネスのルール |
| --- | --- | --- |
| A（一部） | 文書・テストだけの差分は、CI の成功だけでマージしてよい（別の AI のコードレビューを省く） | AGENTS.md「実装の進め方」（コードレビューは実装とは別の AI で行う）、Skill「実装の進め方」の役割の流れ |
| B | ミューテーションは、認可・個人情報に関わるファイルだけ、絞った診断をマージの前に行う。そのほかはマージを止めず、リリース前の検証（#160）でまとめて実行する | Skill「品質チェックの道具」（対象の処理で80%以上）の確認の時期。ADR-0020 の(a)の「開発中のミューテーション」 |
| C | 計画レビューは最大2回とする。重大な指摘が残る場合だけ3回目を行う。データ破損・認証の回避・情報漏えいにつながる指摘は、これまでどおり解消するまで続ける | Skill「実装の進め方」「レビュー」の「計画レビュー・コードレビューとも最大3回」（計画レビューの部分） |
| E | 依存しない Issue を、別の worktree で2件まで並列に進める。Stryker・E2E・Codex などの重い処理は同時に動かさない | Skill「実装の進め方」の「複数のIssueを続けて進める条件」（直前の Issue の PR がマージ済み） |

緩めないもの（記録のために書く）：

- 数値の基準（ミューテーション80%以上）、対象の定義、E2E、通常テスト・型・Lint・セキュリティ検査の全体実行
- 本番のコードが変わる差分のコードレビュー（別の AI）。コードレビューの回数の上限（最大3回）
- 秘密情報・テストデータ・破壊的な操作・本番への操作の決まり

緩めるものに当たらないと判断したもの：

- A の「軽微な指摘は後追いの Issue に回してマージしてよい」「最新の状態の確認は、本番のコードが変わったときだけ行う」：Skill「レビュー」は、重大を「直さないと進めない・マージできない」、軽微をそれ以外と分けている。軽微な指摘でマージを止めないことと、head の SHA の確認は、このプロジェクトのマージの運用（2026-11-15 決定）であり、ハーネスのルールではない
- D（デモ動画は親 Issue の区切りでまとめて録る）：デモ動画はこのプロジェクトの運用であり、ハーネスのルールにはない

## 理由

- 軽微な指摘と、ミューテーションの待ちで、マージが何時間も止まっていた。待った間に見つかった本番の不具合は0件だった
- 残りの機能の実装が約35件あり、いまの進め方のままでは5〜7週間かかる
- ミューテーションは、リリース前の検証（#160）でまとめて全体を実行する（ADR-0020 の(d)）。認可・個人情報に関わるファイルだけはマージの前に確かめ、重大な事故につながる範囲の検出力は保つ
- 計画レビューの2回目までに重大な指摘が解消されれば、3回目は要らない。安全に関わる指摘は、回数に関係なく解消するまで続ける

## 影響とリスク

- 文書・テストだけの差分は、別の AI のレビューを受けない。テストだけの差分で、テストの意味が崩れても見つからないおそれがある。対策：本番のコードを含む差分は、これまでどおりレビューする
- 認可・個人情報に関わるファイル以外のミューテーションの劣化は、リリース前の検証（#160）まで見つからない。対策：#160 で重要処理全体のミューテーションを必ず行う
- 並列で進めると、変更が衝突するおそれがある。対策：依存しない Issue だけを対象にし、別の worktree で進め、重い処理は同時に動かさない
- 範囲を絞る（後回しにする Issue）ことは、要件の取り下げではない。後回しにした Issue は閉じない

## 範囲を絞る

後回しにする Issue：#117・#129・#152・#153・#157・#158・#159・#222・#223。優先する Issue：案件の中心（#146〜#150）・添付（#140）・検索（#155）・アカウントの無効化（#128）ほか。詳しくは [project-rules.md](../project-rules.md) の「2026-11-16決定の進め方の軽量化と範囲の絞り込み（Issue #267）」に書く。

## 運用の境界

「認可・個人情報に関わるファイル」「本番のコードが変わったとき」「文書・テストだけの差分」の例外、「親 Issue の区切り」、並列の細部の解釈は、[project-rules.md](../project-rules.md) の「運用の境界」に書く（統括の解釈。安全な側に倒す。利用者が変えたら従う）。特に、既存のテストの期待を変える・テストを消す／スキップする差分は、「文書・テストだけの差分」として CI の成功だけでマージせず、別の AI のレビューを行う。

## 2026-11-16 の追加：手元の検証を段階にする（Issue #271）

- 関係：[Issue #271](https://github.com/yamamotonaoki3/internal-system/issues/271)、AGENTS.md「完了の定義」2、Skill「品質チェックの道具」、Skill「テスト」

### 決定

手元では、全体の `npm run check` を実行しない。変えたファイルの lint・format、型チェック、関係するテストのファイル、関係する E2E（範囲は ADR-0020）にする。全体のテスト・型・Lint・セキュリティ検査は、CI（`.github/workflows/check.yml`。コードを変えた PR で `npm run check` の全体を実行する）に任せ、CI が失敗したら原因を直す。

### 緩めるハーネスのルール

- Skill「品質チェックの道具」・Skill「テスト」の「品質チェックとテストは、手元とCIで共通の`npm run check`で、プロジェクト全体に対して実行する」の、手元での全体実行
- AGENTS.md「完了の定義」2「該当するテストと品質チェックが、プロジェクト全体に対して通っている」は、CI が全体を実行するため、CI の成功で満たすと整理する。完了の定義そのものは変えない（全体に対して通っていることを求める点は同じで、実行する場所が手元から CI になる）

### 理由

CI が同じ全体を実行しているのに、手元でも全体を実行すると、同じ検証が重なる。#138 では、重い検証の待ちが時間の多くを占めた。手元は、変えた範囲の早い確認に絞る。

### 影響とリスク

- 全体で初めて見つかる失敗が、CI まで分からない。対策：CI が失敗したらマージせず原因を直す。数値の基準・対象・E2E の範囲は変えない
- CI は E2E を実行しない。対策：関係する E2E は手元で実行する（範囲は ADR-0020）。E2E の全件はリリース前の検証（#160）と #189 の最終確認の前に行う

### 緩めるものに当たらないと判断したもの

2〜6（テストの層の役割・期待値の独立・失敗の分類・時間の記録・レビュー依頼の終了の基準）は、ハーネスのルールを強める、または補うもので、緩めない。
