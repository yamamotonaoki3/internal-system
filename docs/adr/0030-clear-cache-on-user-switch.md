# 0030：利用者の切り替えのときは、枠で一括してキャッシュを捨てる（キーごとに利用者の ID を足さない）

- 状態：採用（2026-11-18 利用者決定）
- 日付：2026-11-18
- 関係：Issue #284（表示の側）、Issue #300（進行中の操作）、Issue #298（別のタブ）、決定記録 C-187、要件 0-2 AC-8・決定記録 C-160、[docs/design/auth-session.md](../design/auth-session.md)、[project-rules.md](../project-rules.md)、Skill「frontend-state」「security」

## 背景

同じ画面を開いたまま、セッションの利用者が替わると（A のセッションが切れ、同じタブで B がログインする）、B の応答が届くまでの間、A のデータ（メッセージ・スレッド・未読・通知・チャンネル・下書き・初回のパスワード変更の入力など）が、TanStack Query のキャッシュや画面の状態から表示されえた。本人・参加者限定のデータの漏えいに当たる。

多くのクエリのキーは利用者の ID を含まない。一方、期限切れのあとの同じ利用者の再ログインでは、前の一覧や端末の下書きを残す（0-2 AC-8 の #120 の読み方）。この両方を満たす必要がある。

## 比べた案

| 案 | 内容 | 見送った理由 |
| --- | --- | --- |
| A | すべてのキーに利用者の ID を足す | 約15のキーの族と、その書き換えの箇所を直す必要があり、新しいキーで付け忘れても検出できない |
| B' | 利用者ごとに`QueryClient`を分ける | 同じ利用者のキャッシュも失い、再ログインで前の一覧を残す動き（0-2 AC-8）に反する |
| **B（採用）** | 利用者の ID が替わった瞬間に、枠でセッション以外のクエリのキャッシュを一括して捨てる | — |

## 決定

- 利用者の ID が、前に分かっていた ID と違う値に替わった瞬間に、セッション以外のクエリのキャッシュを捨てる（`frontend/src/features/auth/user-switch-guard.ts`の`installUserSwitchGuard`。`frontend/src/main.tsx`で1回だけ登録する）
- 同じ利用者の再ログインでは捨てない。セッションが無い間も覚えた ID は消さない
- mutation のキャッシュは捨てない
- セッションを書くときは、古いセッションの取得を取り消してから書く（`publishSession`。`useLogin`が使う）
- 認証の枠（`RequireAuth`）は、同期で読んだ利用者の ID でログイン後の領域（初回のパスワード変更の画面を含む）を作り直し、その ID がセッションの内容と一致しない間は中身を出さない
- 既にキーに利用者の ID を入れている機能（退職処理の申請・監査ログ・案件・チャンネルの管理）は、そのまま残す（二重の守り）
- 別のタブで別の利用者がログインした場合は範囲外（Issue #298）。進行中の操作の扱いは Issue #300 に分ける（利用者の決定）

## 理由

- 新しいキーに利用者の ID を足さなくても守られる。付け忘れによる漏えいが起きない
- 同じ利用者の再ログインでは何も捨てないので、0-2 AC-8 の動きと両立する
- 捨てたクエリの進行中の取得は取り消され、古い応答がキャッシュに書き戻されない
- mutation のキャッシュを捨てても、進行中の mutation の後処理は止まらない。捨てると、再ログインでの操作の継続や、ログアウトの後処理に退行が出るおそれがあるため、触らない
- 進行中の操作まで含めると範囲が広がり、退行のおそれも出るため、表示の側と分けた（計画レビューを4回行った経過による）

## 影響

- 新しいクエリのキーに利用者の ID を足す必要はない。ただし、利用者の切り替えのテストに、その画面を足すかを確かめる（[project-rules.md](../project-rules.md)）
- この決定だけでは、操作の途中で別の人に替わった場合の、前の利用者の操作の応答の書き戻し（返信の件数・編集・削除・ログアウトの後処理）と、残りの通信（添付・本文）は防げない。Issue #300 で守る
- mutation の状態を読む表示（`LogoutFailureNotice`・`useIsReactionPending`）が替わった後に何を出しうるかは、Issue #300 の洗い出しに含める
- 認証の枠が、セッションと同期の ID が一致するまで一瞬「確認中です」を出すことがある（前の利用者のデータは含まない）
- 見直す条件：Issue #298・#300 の方針が、この決定と合わないとき。キャッシュの設計（キーの構成）を変えるとき
