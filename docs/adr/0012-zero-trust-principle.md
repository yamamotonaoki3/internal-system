# 0012：ゼロトラストを設計の原則とする

- 状態：採用
- 日付：2026-11-02
- 関係：Issue #163（親Issue #108）、ADR-0003・0007・0008・0009・0011、決定記録 C-76・C-81・C-133・C-134・C-135・C-137・C-139・C-150・C-151・C-153、Skill「セキュリティ」（`.claude/skills/security/SKILL.md`）、追加の層の調査は別Issue #164、ウイルススキャンは別Issue #116

## 背景

このプロジェクトの設計は、ゼロトラストの考え方と多くの点で重なる。ここでいうゼロトラストは、「社内のネットワークや端末からのアクセスだから安全」とは見なさず、アクセスのたびに、誰が・何に・どの権限でアクセスするかを確認する考え方である。

ただし、これまでは方針として明記されておらず、`docs`・Skill・`AGENTS.md`のどこにも書かれていなかった。個々の決定はADRと決定記録にあるが、共通の原則として束ねていないため、今後の判断（新しい機能の認可、認証の追加など）で拠り所にできない。

この ADR は、すでに決めた項目を原則に沿って整理し、足りない点を明記する。新しい仕組みを導入する決定ではない。

## 選択肢

1. 原則を明記せず、個々の決定だけで運用する
   - 良い点：文書が増えない
   - 悪い点：新しい判断のたびに、既存の決定との整合を個別に確かめる必要がある。足りない点が見えにくい
2. ゼロトラストを設計の原則としてADRに明記し、既存の決定との対応表と、足りない点を載せる
   - 良い点：判断の基準が1つになる。既存の決定をたどれる。足りない点を推測で埋めずに残せる
   - 悪い点：対応表を、決定が変わるたびに保つ必要がある
3. 原則の明記に加えて、ネットワーク側の追加の層（Cloudflare Accessなど）も、この ADR で決める
   - 良い点：原則と対策を一度に決められる
   - 悪い点：費用・運用・個人情報の判断が要り、調査が済んでいない。推測で決めることになる

## 決定

選択肢2を採る。**ゼロトラストを、このプロジェクトの設計の原則とする**。

原則の内容は次のとおり。

- 「社内だから」「ログイン済みだから」を理由に、確認を省かない
- サーバー側で、リクエストごとに、利用者の本人確認（セッション）と、対象への権限を確認する。画面側の表示の制御だけに頼らない
- 重要な操作では、追加で本人確認（再認証）を求める
- 権限は最小にし、ロールと、参加者に限った対象（チャンネル・案件など）で絞る
- 乗っ取り・不正の兆候に気づき、被害を止める手段（監査ログ・試行制限・セッションの即時失効）を持つ
- 外から入ってくるデータ（添付のファイルなど）は、中身を確認し、見かけを信用しない

### 原則と既存の決定の対応表

| 原則 | 既存の決定 | 根拠 |
| --- | --- | --- |
| 毎回、サーバー側でセッションを確認する | セッションをD1に保存し、無操作30分・1日の判定を読み取り時に行う。セッションIDは`HttpOnly`のクッキーで運び、サーバー側で照合する | [ADR-0003](0003-auth-cookie-session.md)、[ADR-0008](0008-session-and-login-throttle.md)、決定C-149 |
| 毎回、対象ごとに権限を確認する | リソースIDを指定する操作は、そのリソースごとに毎回権限を確認し、一覧は見てよい範囲に絞る | Skill「セキュリティ」の認可の規則 |
| 重要な操作の再認証 | 一度再認証すると5分間は再入力を求めない。公開の承認は、すべて再認証付き | 決定C-139（0-5 AC-2、5-5 AC-3）、C-81 |
| 全体管理者の多要素認証 | 全体管理者だけTOTPを必須にする。細部は未決定（下の節） | [ADR-0009](0009-admin-mfa-totp.md)、決定C-151 |
| パスワードの安全な保存 | scryptによるハッシュ。本番で確認して最終決定 | [ADR-0007](0007-password-hash-scrypt.md)、決定C-148 |
| 最小権限（ロール） | 全体管理者のみが監査ログを閲覧できる | 決定C-76、C-81 |
| 最小権限（参加者に限った対象） | 案件の担当部署のオーナー・全体管理者の自動参加は、決定で範囲を明示している。アーカイブした案件の中身を見られるのは、全体管理者だけ | 決定C-133、C-134、C-135 |
| 監査ログ | 案件の終了・再開・引き継ぎなどを、誰が・いつ・何をしたかを監査ログに記録する | 決定C-81 |
| 試行制限 | ログインの試行は接続元単位でD1に記録して制限する。社員ID単位はロックせず待ち時間を増やす | [ADR-0008](0008-session-and-login-throttle.md)、決定C-150 |
| セッションの即時失効 | パスワードの変更・再発行・無効化に伴う失効を、同じ`db.batch`で行う | [ADR-0008](0008-session-and-login-throttle.md)、決定C-149 |
| 入力データ（ファイル）の中身の検査 | docx・xlsx・pptxは拡張子と中身（zipの構造）が一致する場合だけ許可し、マクロつき・旧形式は不可。形式は中身で判定する | [ADR-0011](0011-attachment-inspection-and-virus-scan.md)、決定C-137、C-153 |

## 理由

- 社内のネットワークや端末を信頼する前提にしないことで、個々の判断を、場所ではなく「誰が・何に・どの権限で」に統一できる
- 個人情報を扱い、全体管理者の力が大きい（ADR-0009）。1つの層が破られても被害が広がらないよう、層を重ねる方針と合う
- すでに決めた項目の多くが、この原則を満たしている。明記することで、今後の判断の基準になり、足りない点も見える
- 追加の層の採否は、費用・運用・個人情報の観点で調査が要るため、この ADR では決めない

## 影響

- 新しい機能の認可・認証の設計では、この原則と対応表に照らして確認する。コードレビューでも、サーバー側での毎回の確認が抜けていないかを見る
- 対応表の元になる決定が変わったときは、この ADR の表を更新する（決定を変える場合は、元のADRを消さず、新しいADRを足す）
- 見直す条件：対応表に載せた決定が置き換わったとき、未決定の点が決まったとき、ネットワーク側の制御などの追加の層を採るとき

### 足りない点・未決定の点（推測で決めない）

| 項目 | 状況 |
| --- | --- |
| ネットワーク側の制御 | **未決定**。接続元のIPアドレスや経路による制限は、現時点で決めていない。Cloudflare Accessなどの追加の層の採否は、別Issue #164で調査する。この ADR では採否を決めない |
| 端末の状態の確認 | **未決定**。端末の管理状態・OSやブラウザの状態を、アクセスの条件にするかは決めていない |
| ウイルススキャン | **未決定**。別Issue #116で調査してから決める（[ADR-0011](0011-attachment-inspection-and-virus-scan.md)、決定C-153）。現在の検査は「種類の一致」の確認であり、安全性の保証ではない |
