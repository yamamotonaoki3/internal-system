# 0015：スタイルの方針は、Tailwind CSS 4とCSS変数のデザイントークンと、自前の小さな共通部品にする

- 状態：採用
- 日付：2026-11-04
- 関係：Issue #171（親Issue #108）、`docs/research/T-07-style-foundation.md`、`docs/tech-stack.md`、ADR-0012（ゼロトラスト）、ADR-0013（初回セットアップ。適用の対象の画面）

## 背景

- 本番のフロントエンドには、スタイルの仕組み（CSSの方針・基準値・共通の部品）がまだ無い。これまでに作った画面（初回セットアップ・ログイン・ホーム）は、装飾のない最小の見た目になっている。画面が増える前に、共通の方針を決めて手戻りを防ぐ必要がある
- 本番のCSPは `style-src 'self'`（`backend/src/lib/security.ts`）で、インラインの `<style>` の注入を許可していない。実行時にCSSを注入する方法は、そのままでは動かない
- プロトタイプ（`prototype/`）の色の一部は、WCAG 2.1 AAを満たさない（主ボタンの白文字、補足の文字、フォーカスの輪郭など。数値は調査メモの3章・5章）。プロトタイプは本番のコードに流用しない決まりのため、値の参考にとどめる
- 初回のJavaScriptはすでに目標（圧縮後200KB以下）を超えているため、JavaScriptを増やさない方法が望ましい

## 選択肢

調査の詳細は `docs/research/T-07-style-foundation.md` の6章・7章。

1. 素のCSS（グローバル＋CSS変数）
   - 良い点：新しいライブラリが要らない。CSPに影響しない
   - 悪い点：部品が増えると名前の管理が難しくなり、規律が要る
2. CSS Modules＋CSS変数
   - 良い点：Viteの標準機能で、新しいライブラリが要らない。ファイル単位で閉じ、CSPにも影響しない
   - 悪い点：トークンの運用を自分たちで守る負担がある
3. Tailwind CSS 4＋CSS変数＋自前の小さな部品
   - 良い点：JavaScriptを増やさず、CSSは外部ファイルとしてビルドされるためCSPを変えずに済む。公式のVite手順があり、Vite 8に対応する。トークンを一か所に集めやすい
   - 悪い点：新しいライブラリが2つ増える（承認が要る）。ユーティリティクラスの学習が要り、`className` が長くなるため、共通の部品に閉じ込める運用が前提。任意の値も書けるため、逸脱を防ぐには運用とレビューが要る
4. UI部品のライブラリ（Base UI・Radix UIなどの無装飾の部品、Mantineなどの装飾つきの部品）
   - 良い点：ダイアログ・メニューなど複雑な部品のキーボード操作・フォーカス管理が得られる
   - 悪い点：一部の部品がインラインの `<style>` を注入する可能性があり、CSP有効下での動作確認が要る（Radixは未確認、Base UIは注入を止める設定がある）。ライブラリが増える。装飾つきのものは、プロトタイプの見た目への上書きの手間が大きい
5. CSS-in-JS系（Emotion・styled-components、それに依存するMUI・Chakra）
   - 悪い点：実行時にインラインの `<style>` を注入するため、現状のCSPと衝突する（nonceまたはCSPの変更が要る）。現時点では推奨しない

## 決定

選択肢3を採る。利用者が決定した（2026-11-04）。

- **スタイルの方法**：Tailwind CSS 4＋CSS変数のデザイントークン＋自前の小さな共通部品。共通の部品は `frontend/src/components/` に、素の `button`・`label`・`input` などで作る
- **新しく入れるライブラリ**：`tailwindcss` と `@tailwindcss/vite` の2つだけ。バージョンは固定し、公開から十分に日数が経った版を選ぶ（最新版は避ける。調査時点の候補は4.3.3。入れる直前に、版と公開日を再確認して決める）
- **色**：WCAG AAを満たすよう、色相を保ったまま調整する（コントラスト比は組み合わせごとに計算して決める）
- **ダークモード**：作らない。基準値をCSS変数で持つので、後から足せる
- **フォント**：端末のフォントのみ。Webフォントは入れない（CSPの変更なし）
- **アイコン**：アイコンのライブラリは入れない
- **UI部品のライブラリ**：今は入れない。ダイアログ・メニューなどが必要になった機能のIssueで個別に追加する。その場合、CSPを有効にしたままの動作検証を先に行う
- **CSP**：変えない

### ライブラリ導入の条件

利用者の指示（公式のものだけを入れる）に基づき、ライブラリを入れるときは次をすべて行う。

1. 公式の導入手順に書かれたパッケージ名と完全に一致することを確認する
2. npmの登録情報の公式リポジトリ・公開者が、公式と一致することを確認する
3. 公開から十分に日数が経った版を、バージョン固定で入れる
4. 導入時のスクリプトを実行しない（`--ignore-scripts`）
5. 導入後に、ロックファイルの差分・整合性ハッシュ・脆弱性（`npm audit`・OSV）を確認する
6. 確認した結果を、Issueに記録する

## 理由

- JavaScriptを増やさず、初回のJavaScriptがすでに目標を超えている現状を悪化させない
- CSSは外部ファイルとしてビルドされるため、CSP（`style-src 'self'`）を変えずに済む。CSPの変更は、ゼロトラストの原則（ADR-0012）に照らしても、理由なく緩めない
- 公式のVite手順があり、`@tailwindcss/vite` はVite 8に対応する
- 色・文字・余白などの基準値を一か所に集められ、後続のIssue（共通レイアウト #121など）が同じ値で画面を作れる
- 入れるライブラリは2つに限られ、調査（公開情報のみ。調査メモの9章）では、導入時に自動実行されるスクリプトも、既知の脆弱性の登録も見つからなかった
- 複雑な部品のライブラリは、CSP有効下での動作が未確認のものがあるため、必要になった時点で検証してから入れる方が安全
- 調査は公開情報の確認で、第三者の再照合は未了のため、上の導入の条件で、入れる直前に再確認する

## 影響

- `docs/tech-stack.md` に `tailwindcss` と `@tailwindcss/vite` を追記する。ライブラリを実際に追加する実装の段階で、バージョンとあわせて更新する
- 後続のIssueの画面は、この方針（トークン・`frontend/src/components/` の共通部品）に沿って作る。場所と書き方は設計書（`docs/design/`）に書く
- 色の調整（コントラストのため）により、プロトタイプと見た目が少し変わる
- 初回のJavaScript・CSSの大きさの増加は、ビルド出力で測って記録する（Issue #171のAC-5）
- ダイアログ・メニューなどの部品を追加するときは、CSPを有効にしたままの動作検証が先に要る。注入を止める手段のない部品は使わない
- 見直す条件：CSPを変える必要が出たとき、Tailwindでの運用（クラスの逸脱）が保守の負担になったとき、ダークモードが要件になったとき
