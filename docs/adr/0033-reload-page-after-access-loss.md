# 0033：案件の資格を失ったと確定したら、キャッシュを数え上げて消すだけでなく、ページごと読み込み直す

- 状態：採用（Issue #338。決定記録 C-206）
- 日付：2026-11-22
- 関係：Issue #338（この ADR。#323 の1つ目）・#323（親）・#308・#363・#339・#340・#341・#342、決定記録 C-190・C-206、[ADR-0030](0030-clear-cache-on-user-switch.md)、[docs/design/access-loss.md](../design/access-loss.md)・[cases.md](../design/cases.md)、Skill「frontend-state」「security」

## 背景

- S-17 を開いたまま資格（案件の参加者であること）を失った人の画面から、参加者だけの中身を取り除く必要がある。#308（C-190）は、クエリのキャッシュと完了した操作の記録を、**数え上げて**取り除く方式で始めた（`forgetCaseContent` など）
- #323 は、この数え上げの漏れを、3回の計画レビューと PR #328 で繰り返し指摘された。部品の状態・進行中の処理の続き・画面の外のメモリなど、数え上げの対象に入れ忘れる場所が、レビューのたびに見つかった。対象を広げるたびに、また別の場所が見つかり、収束の見通しが立たなかった
- 「資格を失った」と確定した時点で、メモリの中に参加者だけの中身が残っていないことを、数え上げの網羅に頼らず保証したい

## 選択肢

| 案 | 内容 | 良い点 | 悪い点 |
| --- | --- | --- | --- |
| A | 数え上げの対象を広げ続ける | 画面が途切れない。変更が小さい | 漏れを、レビューと実装が追いかけ続ける。残りがないことを示せない。#323 が3回の計画レビューで収束しなかった |
| B | 資格を失ったと確定したら、ページの文書ごと読み込み直す | 実行環境ごと消えるので、部品の状態・進行中の処理・メモリの中のすべてが残らない。残りがないことを、文書が替わったことで示せる | 入力中の内容が消える。待ち方・隠し方・知らせ・利用者の切り替えとの重なりの設計が要る |
| C（採用） | A の片付けを残したまま、その後に B を行う | 読み込み直しを取りやめる場合（別の利用者に替わったとき）でも、いまの片付けの保証を保てる。既存のテストの期待を変えずに済む | 片付けと読み込み直しの両方を持つ。数え上げの方式を、この Issue では削除しない |

## 決定

案 C を採る。資格を失ったと確定したら、いまの片付け（C-190(2)(4)）を行ったうえで、ページの文書ごと読み込み直す（入口は`frontend/src/features/access-loss/reload-after-access-loss.ts`の`requestAccessLossReload`）。

- 読み込み直す場合は、(a) 中身の拒否の後の確かめで確定したとき（画面を離れた後も、作り直された画面が表示中でも、必ず呼ぶ。重なった要求は入口で合流する）、(b) この画面で参加者として見た後に外されたと確かめられたとき、(c) 本人の退出が成功したとき。**参加者だったことを見ていない片付け**（最初から非参加・404、古い非参加の概要、作り直しの経路）、5xx・通信の失敗、参加者のままの 403 では、読み込み直さない。参加していない案件を開くたびにページが読み込み直されないようにするため。時間による歯止めは持たない
- 読み込み直す前に、進行中の操作（`MutationCache`の操作と、`services/api-client.ts`が数える、`MutationCache`に載らない直接の書き込みの要求）を、最初の要求から最大5秒待つ。実行の直前にも確かめ直し、予約の後に始まった操作があれば待機に戻る。持ち主が押したログアウトだけは、その後処理が終わるまで上限なしで待つ。待つ間と、呼んでから文書が替わるまでの間は、ルーターの下の画面全体（ダイアログ・popover・離脱の確認を含む）を描画から外し、全画面の覆いだけを出す（`AccessLossBoundary`）。離脱の確認は出さない（`suppressBeforeUnload`）
- 待機は持ち主（確定を始めた利用者）を持ち、別の利用者に替わったら取りやめる。取りやめても、片付けは済んでいる（ADR-0030 の枠と両立する）
- 読み込み直した後の知らせは、保存先に**種類だけ**を書く（利用者の ID・案件の中身は書かない）。保存先を使えない端末でも、アプリは起動し、読み込み直しは続ける

## 理由

- 数え上げは、漏れを検出する側（レビュー）に依存する。実行環境ごと消す方式は、資格の喪失という安全側の要求に対して、漏れの有無を、対象の網羅に頼らず保証できる
- 片付けを残すことで、読み込み直しを取りやめる枝（別の利用者に替わったとき）でも、メモリの中身が残らない保証が、いまより後退しない（`installUserSwitchGuard`は完了した操作の記録を消さないため）
- 読み込み直しの契機を「参加者だったことを見た後」に限るのは、読み込み直しがユーザーの入力を消す動作であり、参加していない案件を開くだけで起こしてはならないため
- 利用者の決定（2026-11-21）：確かめの応答が届く前に別の画面へ移っていた場合も、片付けて、さらに読み込み直す
