# 0006：IDは時刻順のテキスト、一覧はカーソル方式、未読は既読位置から数え直す

- 状態：採用
- 日付：2026-11-02（利用者の承認は2026-11-02〜03）
- 関係：Issue #105、決定記録 I-01・C-147、`docs/requirements/api-draft.md`の2.4、`docs/requirements/data-model.md`の設計-9、調査メモ[全体設計の方針の下調べ](../research/design-foundation.md)の5章

## 背景

メッセージの並び順、既読位置の比較、一覧のページ送り、未読件数の持ち方を決める必要があった（I-01）。DBはD1のみで、`db.batch()`の中では前の文の結果を使えない（ADR-0005）。ひな形の例のテーブル（`sample_users`）は連番の整数IDを使っている。

## 選択肢

### IDの形式

1. 連番の整数：小さく速い。推測しやすく、`batch`の中で先にIDを知れない
2. UUID v4（`crypto.randomUUID()`）：パッケージ不要。時刻順にならず、索引の局所性が悪い
3. 時刻順に並ぶULID相当のテキスト：文字列の辞書順が時刻順になる。推測しにくい。同じミリ秒内の順序は工夫が要る
4. ULIDのライブラリを追加する：実装は楽だが、新しいライブラリの追加には利用者の承認が要る

### ページ送り

1. カーソル方式（並び替えの値＋IDを印にする）：件数が増えても速い。追加で行がずれても重複・欠落しない。ページ番号での移動はできない
2. オフセット方式：ページ番号で移動できる。大きいオフセットは遅く、D1の読み取り行数の課金にも効く

### 未読件数

1. 件数のカウンターを保存する：読むのは速いが、投稿のたびに参加者の数だけ書き込み、削除・非表示・参加の出入りで食い違う
2. 既読位置（`read_positions`）だけを正とし、未読数は数え直す（上限つき）
3. 2に「ルームの最新メッセージID」（`rooms.last_message_id`）を足す：サイドバーの「未読があるか」が1行の比較で済むが、投稿ごとに1行の更新が増える

## 決定

- **ID**：時刻順に並ぶULID相当のテキスト（時刻部分＋乱数部分）を、**自前で生成する**（Web Cryptoを使う。ライブラリを追加しない）。同じ要求の中で連続して生成するときは、直前のIDより必ず大きくする（単調に増やす）。内部IDは変更しない・再利用しない。ログイン用のユーザーID文字列（`login_id`）、案件番号、`direct_key`は内部IDとは別の列にする
- **ページ送り**：**すべての一覧をカーソル方式にそろえる**。ページ番号は使わない
  - 印（`cursor`）は、最後の行の「並び替えの値＋ID」を符号化した文字列とし、入力として必ず検証する。壊れた印は`422：VALIDATION_ERROR`
  - 次があるかは`limit + 1`件取って判定する。`nextCursor`は続きがなければ`null`
  - 並び替えの値が重複しうる一覧は、IDを第2キーにして順序を一意にする
  - 1回の件数はC-90のとおり（メッセージ50件・その他20件・最大100件）
- **未読**：既読位置（`read_positions.last_read_message_id`）を保存し、未読数は**上限つきで数え直す**（例：99件以上）。件数のカウンターは持たない。サイドバーの「未読があるか」の判定が重いと実測で分かったときだけ`rooms.last_message_id`を足す案は、**将来の選択肢**として残す（今は採用しない）
- **索引**：一覧ごとの候補を設計書（`docs/design/overview.md`の「索引の候補」）に書く。確定は、実装時に`EXPLAIN QUERY PLAN`で確認して行う

## 理由

- ID：メッセージの「新しい順」、既読位置の「より新しい」、カーソルが、IDの順序だけで書ける。ADR-0004の「最後のID以降を取るAPI」も、この順序に依存する。IDをアプリ側で先に作れるので、`batch`の中で参照するIDを前の文の結果に頼らずに使える。UUID v4は時刻順にならない。ライブラリの追加を避け、十数行の自前の実装で足りる
- Workersでは、処理中は時刻がほぼ進まない（I/Oのときだけ進む）ため、同じ要求の中で連続して作ると同じ時刻になる。単調に増やす実装が必要になる理由はこれである
- カーソル方式は、メッセージの遡り表示（S-05）に合い、読み取り行数が少ない。ページ番号での移動を必要とする画面の要件は、現時点でない
- 未読は、持つ事実を1つ（既読位置）にすれば、削除・非表示が自然に反映される。IDが時刻順なので、索引（ルーム, ID）の範囲を読むだけで数えられ、上限をつけることで読み取り行数も抑えられる

## 影響

- IDは認可の代わりにならない。推測しにくくても、対象のリソースごとに権限を確認する
- ひな形の`sample_users`は連番のIDだが、これは例であり、要件のテーブルには適用しない
- 総件数の表示が要る一覧は、別の数え直し、または上限つきの表示にする
- 「ページ番号で移動」が画面の要件になった一覧が出た場合は、その一覧に限って方式を見直す（新しいADRを追加する）
- スレッドごとの未読の既読位置のテーブルを足すかは、実装の計画で決める（未決定）
- 画面に未読の件数を出すかは、画面の洗い出しの後に#15で見直す（設計-9。未決定のまま）
- 単調増加の実装は、Workersの時刻の仕様の最新を、実装前に公式で再確認する
