# 0008：セッションはD1に保存し、ログインの試行制限は接続元単位でD1に記録する

- 状態：採用
- 日付：2026-11-02（利用者の承認は2026-11-02〜03）
- 関係：Issue #105、決定記録 I-05・I-09・C-149・C-150（C-41を置き換える）、ADR-0003、`docs/requirements/00-foundation.md`の0-2・0-3・0-5、`docs/requirements/nonfunctional.md`の3章、調査メモ[全体設計の方針の下調べ](../research/design-foundation.md)の6章

## 背景

ADR-0003は、クッキー方式のセッションを採用したが、保存の構造・失効の処理は決めていなかった（I-05）。ログイン・現在のパスワード確認・再認証の試行制限は、決定C-41が「社員ID単位は15分以内に5回連続失敗で15分制限」「接続元単位の上限・窓・解除時間は実装設計」としていた（I-09）。

セッションの要件は、無操作30分・ログインから1日で失効（0-2 AC-5）、端末ごとのログアウト（0-2 AC-6）、パスワード変更・再発行・無効化での失効（0-3 AC-4・AC-8、0-1 AC-9）、再認証から5分は再入力不要（0-5 AC-2）である。

C-41の社員ID単位のロックには問題がある。第三者が他人のユーザーIDで5回失敗させれば、その人を15分ログイン不能にできる。Skill「セキュリティ」は「第三者が他人をロックできないようにする」を求めている。

## 選択肢

### セッションの保存先

1. D1（`sessions`テーブル）：強い一貫性。失効が即時。ユーザーと結合して無効化・パスワード変更を確認できる。認証のたびに読み取りが1回、最終操作時刻の更新が書き込みになる（間引く）
2. KV：読み取りが速くTTLで自動削除できるが、結果整合で他の拠点への反映に60秒以上かかりうる。「ログアウト・パスワード変更後の即時の失効」に合わない
3. Durable Objects：強い一貫性。構成が増え、学習用の規模では過剰になりうる

### 試行制限の実現方式

1. D1の`login_attempts`：強い一貫性。15分などの任意の窓にできる。失敗のたびに書き込みになる
2. Workersのレート制限（`ratelimits`バインディング）：窓が10秒または60秒だけで、15分の窓を表せない。拠点ごとの近似値で厳密でない
3. Durable Objectsで自作：厳密だが構成が増える
4. CloudflareのWAFのレート制限ルール：独自ドメインとゾーンの設定が前提で、アプリ内の共通案内・アカウント単位の制限とは別になる

### 社員ID単位の制限

1. C-41のまま（5回失敗で15分ロック）：第三者が他人を締め出せる
2. ロックせず、失敗が続くほど応答の待ち時間を段階的に増やす：第三者が他人を締め出せない。総当たりは遅くなる

## 決定

### セッション（ADR-0003の補足）

- **セッションはD1の`sessions`に保存する**（KVは反映に60秒以上かかるため採用しない）
- **トークン**は暗号学的な乱数32バイト（Web Crypto）を、URLに安全な文字列にしてクッキーで運ぶ。DBには**SHA-256のハッシュ**を保存する。ログイン成功のたびに新しく発行する（固定化攻撃の防止）
- **無操作30分・1日の判定は、読み取り時に行う**。最終操作時刻の更新は**1分に間引く**（前回の更新から1分以上たったときだけ書く）。30分の判定が最大1分ずれる
- パスワード変更・パスワードの再発行・無効化に伴うセッションの失効は、**パスワードのハッシュ更新などと同じ`db.batch`で行う**。失効の書き込みが失敗したら、成功扱いにせずエラーとして返す
- **期限切れのセッションとログイン試行の記録の掃除は、Cron Triggers（`scheduled`）で行う**。保持期間は実装の計画で提案する
- ADR-0003の状態を「提案」から「採用」にする（本文は最小限の更新で、変更の履歴を末尾に書く）

### ログインの試行制限（決定C-41を置き換える）

- **接続元単位**：接続元は`CF-Connecting-IP`で取る（`X-Forwarded-For`は使わない）。IPv6は`/64`に丸める。生のIPは保存せず、**秘密の鍵つきHMAC**を保存する（鍵はWorkersの秘密情報で、値は利用者が`docs/secrets.md`の手順で入れる）。**窓15分・上限30回・解除15分**（【案】。根拠となる実データはなく、運用で見直す）を、D1の`login_attempts`で行う。接続元のカウントは、ログインの成功で戻さない（他人のIDを試し続ける攻撃を、1回の成功で帳消しにされないため）
- **社員ID単位**：**ロックしない**。失敗が続くほど、応答の待ち時間を段階的に増やす（第三者が他人を締め出せないようにするため）。待ち時間の段階の具体値は**未決定**
- 制限中は、アカウントの有無・制限の種類・残り回数を明かさず、共通の案内と`429`・`Retry-After`を返す（C-41から引き継ぐ）。手動解除の機能は設けない
- 制限の判定は、パスワードのハッシュ計算より先に行う（計算の負荷を攻撃に使わせない）。存在しないIDでも、同じ表示・同じ時間になるようにする
- 一般のAPIのレート制限（X-8の後半。上限値は未決定）は、Workersのレート制限バインディングで足りるかを別に判断する

## 理由

- D1は強い一貫性があり、要件の即時の失効を満たす。Time Travelでバックアップされ、テストも容易である
- トークンは高いエントロピーなので、パスワード用の遅いハッシュは不要で、SHA-256で足りる
- 接続元単位の制限は、15分の窓が要るため、Workersのレート制限バインディングでは表せない。社員ID単位と同じ仕組みで、再認証・パスワード確認にも使える
- 社員ID単位のロックは、第三者による締め出し（サービス妨害）を許す。待ち時間を増やす方式なら、総当たりを遅くしつつ、本人は正しいパスワードでいずれ入れる

## 影響

- 決定C-41の「社員ID単位で15分以内に5回連続失敗で15分ロック」は置き換わる。決定記録に新しいC番号で記録し、C-41に注記する。0-2 AC-4・0-5 AC-4などの受け入れ条件を直す
- 社内の全員が同じ出口IP（NAT）から使う場合、接続元の上限が全員に効く。30回は数百人規模の社内を想定した初期値で、実測と運用で見直す
- 存在しないユーザーIDの試行も数えるため、`login_attempts`の行が増える。キーの長さ制限と掃除（Cron）と接続元の上限で抑える
- ローカル・テストでは`CF-Connecting-IP`が付かない。ヘッダーが無い場合の扱い（共通のキーに集約するか、エラーにするか）は**未決定**。エラーのもみ消しをしない原則を守る
- Pseudo IPv4の設定など、独自ドメインを使う場合のゾーン設定を確認する
- 見直す条件：スマートフォンの専用アプリ、外部システムのAPI利用、複数ドメインにまたがる構成（ADR-0003のとおり）
