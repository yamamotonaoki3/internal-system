# 0032：本番への最初のまとまった適用（migration 0013 以降）を、利用を止めて、1回の作業で行う例外

- 状態：採用
- 日付：2026-11-21
- 関係：Issue #351（この ADR）・#346（親。本番へのデプロイの準備）・#347・#348・#349・#350・#353・#160、Skill「env-deploy」の「本番 DB の変更」「切り戻し」「バックアップと復元」、[ADR-0025](0025-rebuild-referenced-table-defer-foreign-keys.md)・[ADR-0031](0031-search-fts-handwritten-migration.md)、手順書 [production-first-rollout.md](../operations/production-first-rollout.md)

## 背景

- 本番の D1 には、migration 0012 までしか当たっていない（#160 の記録。AI は本番を確かめていない）。0013 から、出す版に含まれる最後の migration（見込みは 0035）までの、20 本を超える migration と、埋め戻しの SQL・検索の索引の作成を、まとめて当てる必要がある
- 本番は、いま、社員が使っていない（利用者の確認。2026-11-21。#346）
- Skill「env-deploy」は、本番 DB の変更で「前の版に切り戻しても動くようにする」と定める。前の手順書（migration を先に当て、日を空けてデプロイしてよい形）は、これを守るために、いま本番で動いている版が、新しい DB の構造の上で動くことを確かめる必要があった（前の手順書の U-5）
- しかし、次の理由で、その確かめは、手間に比べて得るものが小さい
  - 古い版のコードを、新しい migration を当てた DB の上で動かして確かめる仕組みが、このプロジェクトにない（手元のテストは、取り出したコミットの migration で DB を作る）
  - いま本番で動いている版と、コミットの対応の記録がない（#160 に見つからない。記録の方法は #348 で決める）
  - 検索（0032 以降）を当てた後に、古い版がメッセージを書くと、索引と元の表がずれる（古い版は索引を更新しない）

## 選択肢

1. 案 X：前の手順書のまま（migration を先に当て、古い版との両立を確かめ、日を改めてデプロイしてよい）
   - 良い点：Skill「env-deploy」の決まりどおり。デプロイの後に問題が出ても、アプリだけを前の版に戻せる
   - 悪い点：古い版との両立を確かめる仕組みを、新しく作る必要がある（大きい）。古い版が新しい構造の上で、数日動きうる。検索の索引が、その間にずれる。戻す先の時点の期限を、過ぎる恐れがある
2. 案 Y：利用を止めて、migration → 埋め戻し → 検索の索引の作成 → デプロイを、1回の作業で続けて行う
   - 良い点：古い版が新しい構造の上で動く時間が、数分（migration の終わりからデプロイまで）だけになる。両立の確かめが要らない。索引がずれない
   - 悪い点：戻す手段が、Time Travel で DB を戻すこと（アプリと組で戻す）だけになる。Time Travel で、FTS5 を含む DB を戻せるかは、確かめていない
3. 案 Z：案 Y の前に、検証用の D1（#350）で、架空のデータで、同じ順の通しのリハーサルを1回行う
   - 良い点：案 Y の良い点に加えて、本当に戻せるか・所要の時間・`PRAGMA foreign_key_check` が使えるかを、本番の前に確かめられる
   - 悪い点：検証用の D1 の作成と後片付けの手間（#350 で元々要る手間に、少し足す程度）

## 決定

案 Z を採る（利用者の決定。2026-11-21。#346）。

- 本番への最初のまとまった適用（migration 0013 から、出す版に含まれる最後の migration まで・埋め戻しの SQL・検索の索引の作成・アプリのデプロイ）を、利用を止めて、1回の作業で、続けて行う。手順は [production-first-rollout.md](../operations/production-first-rollout.md)
- 戻すときは、**アプリと DB を、組で戻す**（アプリを前の版に戻し、DB を、作業の前に控えた時点に、Time Travel で戻す）。**アプリだけを前の版に戻し、DB を新しい構造のまま残す方法は、使わない**（前の版が新しい構造の上で動くことを、確かめていないため）
- 止めている間のアクセスは、周知と、件数の見比べで扱う。作業の間に件数が増えていたら、止まる。毎日 03:17（日本時間。`wrangler.jsonc` の `triggers.crons` の `17 18 * * *`〔UTC〕）の Cron の時刻は、作業の時間に含めない。アドレスを一時的に無効にする方法は、採らない
- 本番への適用の前に、DB の書き出し（`wrangler d1 export`）は、しない（FTS5 を含む DB は書き出せない。ADR-0031。戻す手段は Time Travel だけ）

### この例外が使える条件（すべてを満たすときだけ）

1. 本番に、利用者（社員）がいない。作業の間、利用を止めることを、前もって周知してある
2. 検証用の D1（#350）で、同じ順の通しのリハーサル（時点を控える → 当てる → 埋め戻し → 索引の作成 → 戻す → 件数で確かめる）を行い、戻せたこと・所要の時間を #160 に記録してある
3. 戻す先の時点（作業の直前に控えるもの）が、Time Travel の保持期間の内にある

### 適用の範囲

- **今回の1回だけ**（本番への最初のまとまった適用）。社員が使い始めた後の本番 DB の変更は、Skill「env-deploy」の元の決まり（前の版に切り戻しても動くようにする・3段階）に戻る
- 作業の途中で日を改めることになり、社員が使い始めた場合は、この例外は使えない。止まって、利用者と、進め方を決め直す

### Skill「env-deploy」の、どの決まりから、どう外れるか

| 決まり | 今回 |
| --- | --- |
| 列の削除・改名を、1回のデプロイで行わない（3段階） | **外れない**。0013〜0033 に、列の削除・改名はない（SQL を読んで確かめた）。表の作り直しは 0016（`rooms`。値は変えない。ADR-0025）。0034・0035（検索用の表の作り直しの予定。PR #352）は、マージの後に、手順書で確かめる |
| 前の版に切り戻しても動くようにする | **外れる**。前の版が、新しい構造の上で動くことを確かめない。代わりに、アプリと DB を組で戻す |
| 切り戻しは、前の版をもう一度デプロイすることを基本にする | 変えない（アプリを戻すときの方法。#348 で決める）。ただし、DB も組で戻す |
| 復元の手順を文書にし、検証の設定で、実際に復元できることを確かめておく | 変えない。案 Z のリハーサル（#350）で満たす |

## 理由

- いま誰も使っていないので、「古い版と新しい DB が長く同居する」状況を作らないのが、一番単純で安全。古い版の確かめの仕組みを新しく作る（案 X）より、手間も危なさも小さい
- 止めているので、DB を戻しても、失われるのは、作業の中で作った確かめ用のデータだけの見込み
- 戻す手段が Time Travel だけになるため、本番の前に、検証用の D1 で「本当に戻せる」「何分かかる」を確かめる（案 Z）

## 影響

- 手順書を、[production-first-rollout.md](../operations/production-first-rollout.md) に書き直した（前の `production-migration-0013-0031.md` は、案内だけを残した）。前の手順書の「古い版との両立の確認（手順 1-6・U-5）」は外した。ただし、いま本番で動いている版は、戻す先として控える
- 引き受ける危ない点
  - 止めている間にも、古い版は要求に応える（利用を止める仕組みはコードにない）。開いたままのタブ・監視・Cron から要求が届くと、(a) migration の最中の読み取りが、一時的にエラーになりうる、(b) 書き込みが通ると、戻したときに消える・埋め戻しと索引の対象から漏れる。ログインしていない要求の、状態を変える操作は、Origin の検査（`backend/src/lib/security.ts` の `originCheck`）と認証で断られる。対策は、周知と、件数の見比べ（増えていたら止まる）
  - 戻す手段が Time Travel だけ。保持期間を過ぎた時点には戻せない。戻している間は、処理中の要求が取り消される
  - デプロイの後に問題が出ると、作業の間に作った確かめ用のデータも、戻すと失われる
- 確かめていないこと（#350 のリハーサルで確かめる）
  - FTS5 を含む DB を、Time Travel で戻せるか（ADR-0031 の Time Travel の項）
  - 戻すのにかかる時間
  - `wrangler d1 execute --remote` から `PRAGMA foreign_key_check` が使えるか
- 見直す条件：リハーサルで戻せないと分かった場合、または社員が使い始めた場合は、この ADR を使わず、進め方を決め直す
