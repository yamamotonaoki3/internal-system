# 0036：案件の画面の外でも資格の喪失に気づけるよう、成功応答に案件の ID を足し、取得の実績はキャッシュから求め、見張りと S-17 の担当を分ける

- 状態：採用（Issue #339。決定記録 C-210）
- 日付：2026-11-27
- 関係：Issue #339（この ADR。#323 の2つ目）・#323（親）・#338・#340・#341・#342・#298・#376、決定記録 C-190・C-206・C-207・C-208・C-209・C-210、[ADR-0033](0033-reload-page-after-access-loss.md)・[ADR-0034](0034-cross-tab-access-loss-hint.md)・[ADR-0035](0035-session-user-mismatch-header.md)・[ADR-0030](0030-clear-cache-on-user-switch.md)・[ADR-0020](0020-test-scope-mutation-e2e.md)、[docs/design/access-loss.md](../design/access-loss.md)・[cases.md](../design/cases.md)・[threads.md](../design/threads.md)・[drafts.md](../design/drafts.md)、Skill「frontend-state」「security」「backend」

## 背景

- #338（ADR-0033）は、案件の画面（S-17）で資格を失ったと確定したら、ページごと読み込み直す。#341（ADR-0034）は、別のタブにも、その案件の参加者の概要を持つタブに限って、確かめのきっかけを伝える。どちらも、**S-17 を開いている間**か、**参加者の概要をキャッシュに持つタブ**の話である
- S-17 の外（スレッド一覧 S-35・スレッドの返信 S-07 など）では、外された後の応答が、検出の仕組みに合わない
  - 返信の取得は 404。部屋の取得は 404 または 403。S-17 の見張り（`useCaseAccessLoss`）は、案件の画面を開いている間しか、その拒否を見ていない
  - スレッド一覧は、見えなくなった行を除いて 200 を返す。エラーにならないので、拒否の購読では気づけない
  - 概要を一度も取得していない文書（S-35 だけを開いている）では、部屋・スレッドがどの案件のものかを、画面が知らない。別のタブの合図も、参加者の概要を持たないタブでは、確かめの通信すら行わない
- 外された人に、サーバーは新しい中身を返さない。残るのは、ブラウザのメモリの中の、すでに取得した部屋・スレッドの中身である

## 選択肢

### 案件との対応をどこから得るか

| 案 | 内容 | 良い点 | 悪い点 |
| --- | --- | --- | --- |
| A | 既存のキャッシュ（案件の概要・一覧・詳細、チャンネルの詳細）の対応だけを使う | サーバーを変えない | S-35 だけを開いた経路では対応が無く、AC-1・AC-2 を全経路で満たせない。保証が、たまたま対応が取れる経路に限られる |
| B（採用） | スレッド一覧と返信の**成功応答**に、案件の ID（`caseId`）を足す | 概要を取得していなくても、取得した時点で、どの案件のものかが分かる。部屋ごとに対応を取りに行く追加の通信がいらない | API の応答に項目が増える。一覧の SQL に結び付きが1つ増える |
| C | 部屋の ID から、案件を引く別の API を足す | 応答の形を変えない | 部屋ごとに追加の通信が増える。404 の部屋では引けない。API が1つ増える |
| D | 403・404 のエラー応答に、案件の ID を載せる | 失敗した時点で分かる | 外された人・存在しない案件への応答に、案件との対応という情報を載せることになる（存在を開示しない扱い、API 草案 2.5.2 に反する） |

### 取得の実績をどこで持つか

| 案 | 内容 | 良い点 | 悪い点 |
| --- | --- | --- | --- |
| A（採用） | その場の Query のキャッシュから求める | 片付け・Query の削除・利用者の切り替えで、キャッシュと一緒に消える。古い実績が残らず、別の状態の複製もない（Skill「frontend-state」） | 実績の判定が、キャッシュの形（キー）に依存する |
| B | 見張りが、取得した部屋・スレッドの台帳を別に持つ | キャッシュが消えても、過去の取得を思い出せる | 片付け・切り替えのたびに、台帳の消し忘れを追う必要がある。#323 が数え上げの漏れで3回の計画レビューを重ねた原因と同じ形になる |

### 見張りと S-17 の分担

| 案 | 内容 | 良い点 | 悪い点 |
| --- | --- | --- | --- |
| A | S-17 の購読を残し、全体の見張りも同じ出来事を受けて、後から打ち消し合う | 既存の S-17 を変えない | 確かめ・合図・下書きの消去が二重になりうる。消去は戻らないので、二重・順序の入れ替わりが、新しい下書きを消す |
| B（採用） | Query の出来事を受ける購読を1つにし、S-17 は担当として登録する。担当がいれば、見張りは、きっかけを渡すだけにする | 同じ出来事を2か所で受けない。担当がいなければ（S-17 を開いていない・離れた後）見張りが画面の外の確定を行う | 登録・解除と、進行中の確かめの持ち主を、見張りが管理する |

## 決定

- **成功応答に`caseId`を足す（案 B）**：`GET /api/me/threads` の各項目と、返信の取得（最新・追加）の成功応答に、必須の`caseId`（案件の部屋は案件の ID、通常のチャンネル・DM は`null`）を足す。`caseRoom`は残す。403・404 の応答には足さない。`caseId`は確かめの対象を特定するだけで、認可には使わない（サーバーは毎回認可する）。スレッド一覧の SQL は、内側で見える範囲・並び・カーソル・`LIMIT`を決めた後、外側で一意の索引（`cases_channel_id_unique`）で`cases`に結び付ける（行を増やさず・除かないので、件数・`nextCursor`は変わらない）。返信の 403・404 では、エラー応答からではなく、**直前に成功したデータ**の`caseId`と親の部屋の ID を使う
- **取得の実績は、Query のキャッシュから求める（台帳を作らない）**：`frontend/src/features/cases/case-access-evidence.ts`の`caseRoomEvidence`（案件の ID つきの返信・スレッド一覧のその案件の行・案件との対応が分かる部屋の正常に取得したメッセージ）と、`caseIdOfRoom`（部屋の ID から案件を引く）。案件一覧の行・案件の詳細だけは、新しい部屋・スレッドの実績にしない。実績の判定と、それに使った部屋の ID は、1つの関数から返す（別々の関数で求めると、食い違うため）
- **見張りと S-17 の担当を分ける（案 B）**：`frontend/src/features/cases/case-access-loss-monitor.ts`が、`QueryClient`ごとに購読を1つ持つ（`installCaseAccessLossMonitor`）。S-17（`useCaseAccessLoss`）は担当として登録する（`registerCaseAccessLossHandler`）。同じ利用者・案件の担当がいれば、見張りは、確かめ・片付け・入口・合図・下書きの消去をせず、きっかけを担当に渡す。いなければ、見張りが、概要を直接1回取って確かめ、画面の外の確定（`settleOutside`）を行う。進行中の確かめは、利用者・案件ごとに1つ（始めた側が、画面を離れた後も、最後まで処理する）
- **スレッド一覧の行の消失は、確かめのきっかけにとどめる**：その取得を始めた時点の一覧と、取得の成功後の一覧を比べ、消えた行の案件を、案件ごとにまとめて概要で確かめる。行の消失だけでは、喪失と確定せず、入口・合図・下書きの消去を行わない
- **実績がある初回の非参加・404 は、取得で届いた新しい概要の答えで確定する**：S-17 のフックが扱う。古い非参加の概要のキャッシュ・手での書き換えだけでは、確定しない（下書きは消すと戻らないため）
- **別のタブの合図の対象を広げる**：参加者の概要、または同じ案件の取得の実績をキャッシュに持つタブ。受けたタブは、入口だけを呼ぶ（ADR-0034 の制限は変えない）
- 検索だけの経路は、扱わない（利用者の決定。別の Issue（#388））。`features/access-loss/`の待機・覆い・読み込み直し・知らせの仕組みと、`lib/refetch-answer.ts`は変えない

## 理由

- 案 B（`caseId`）：概要を取得していない文書で、取得した部屋・スレッドを案件に結び付ける方法が、ほかにない。成功応答に足すので、存在を開示しない扱い（404）を崩さない。認可には使わないので、画面が偽の値を持っても、サーバーの判定は変わらない
- キャッシュから実績を求める：台帳は、片付け・切り替えのたびに消し忘れを追う、数え上げと同じ形になる（ADR-0033 の背景）。キャッシュなら、消えたものを、実績として使わない。キャッシュの不在を「喪失」の証拠にしない規則（C-209）とも合う
- 担当の分け方：同じ出来事を2つの購読で受けて、あとから打ち消す形は、順序の入れ替わりで、取り戻せない下書きの消去を二重にしうる（計画レビューの1回目で指摘された）。購読を1つにして、持ち主を決める
- 行の消失を契機にとどめる：並び替え・ページ境界・参加者でない行の入れ替わりで、行は消えうる。概要で確かめた答えだけを、喪失の根拠にする（利用者の入力を消す動作のため）

## 影響

- API の成功応答に項目が1つ増える（`docs/api/openapi.json`の`ThreadListItem`・`ReplyLatestPage`・`ReplyAfterPage`、API 草案の EP-1-07・EP-3-08）。エラー応答は変わらない。スレッド一覧の SQL に`cases`との LEFT JOIN が1つ増える（一意の索引で引く。SQL の本数・件数は変わらない。[threads.md](../design/threads.md)）
- フロントエンドに、3つのファイル（`case-access-evidence.ts`・`case-access-verification.ts`・`case-access-loss-monitor.ts`）が増える。資格の確かめ（以前の`useCaseAccessLoss.ts`の`verifyParticipant`）は、`case-access-verification.ts`の`verifyBySummaryRefetch`（S-17。取り直しの答えで決める）と`verifyBySummaryFetch`（画面の外。概要を直接取る）に分けて移した。5種類の判定と、C-209 の扱い（409 は、別の利用者が確かでも、切り替えの入口が動いているときだけ`switched`。それ以外は`unverified`）は変えない
- ADR-0033 の「読み込み直すのは、この画面で参加者だったことを見た後に限る」は、部屋・スレッドの取得の実績がある初回の非参加・404 にも広げた（元の記述は残し、注記した）。ADR-0034 の中継の対象と、合図を送る場所も広げた（同じく注記）
- `main.tsx`は、利用者の切り替えの見張り → 中継 → 見張り → 描画の順に登録する。全画面に作用する見張りなので、ADR-0020 (c) により、E2E は全件を行う
- **残る範囲（「画面の外の全部を解消した」とは言わない）**：
  - 検索だけの経路（別の Issue（#388））
  - bfcache（#342）
  - `BroadcastChannel`が使えない環境・別の保存の区画（別のブラウザ・プロファイル・プライベートウィンドウ）の別のタブ
  - 中継は、利用者が A → B → A と替わった場合を見分けない（入口を呼ぶだけの経路で、片付け・下書きの消去はしない）
  - 概要の Query だけが捨てられ、実績は残っている場合は、作り直された答えでは確定しない（下書きを消さない側。作り直した画面は「実績がある初回」として、あらためて扱わない）
  - S-17 の確かめは、利用者が替わった後も、始めた利用者の分を片付ける（C-206・C-207 の前からの決まった動き。画面の外の確かめは、副作用の直前に、利用者の世代・参加の期間を照らす）
  - 別のタブの下書きの書き戻し（#341 の限界。変わらない）
  - 数え上げの方式の削除、案件一覧の行の比較は、扱わない
- 見直す条件：検索だけの経路を扱うとき（検索の応答に案件との対応を足す設計が要る）。部屋・スレッドの応答に`caseId`を足す範囲を広げるとき
