# 0026：マークダウンの描画に react-markdown と remark-gfm を使い、生の HTML を通さず、描画する要素とリンクを許可リストで限る

- 状態：採用
- 日付：2026-11-14
- 関係：Issue #134、共通仕様 C-128・C-144、[要件 1-5](../requirements/01-messaging.md)（AC-1〜AC-8）、[ADR-0015](0015-style-foundation.md)、Skill「security」・「frontend-build」、[tech-stack.md](../tech-stack.md)

## 背景

Issue #134（投稿の編集・削除とマークダウンの表示）で、メッセージの本文をマークダウンとして整形して表示する。要件 1-5 は次を求めている。

- AC-1・AC-2：記法のない本文は文字を失わずに表示し、太字・斜体・取り消し線・箇条書き・引用・コード・リンクを整形する。入力欄にプレビューは付けない
- AC-3・AC-8：本文に HTML やスクリプトを書いても実行されない。生の HTML を使わせる仕組み（`rehype-raw`）と `rehype-sanitize` は入れない設計とし、この「入れない」ことをルールとして残す
- AC-4：リンクは別のタブで開き、`rel` に `noopener`・`noreferrer` を付ける。リンクとして扱う URL の形式は `http`・`https`・`mailto` だけ。本文中の URL は、記法がなくても自動でリンクにする
- AC-5：画像の記法は画像として描画しない（画像は添付 1-6 で扱う）
- AC-6：取り消し線は `~~text~~` の形だけ。表・タスクリスト・脚注は整形しない
- AC-7：メンションの強調は、利用者の決定（Issue #134 の U-6）で #139 に回した。#134 では `@名前` を文字のまま出す

C-128（2026-10-29）は、react-markdown 10.1.0 と remark-gfm 4.0.1 を採用する方針を決め、「ADR に残す（実装を始める前）」と求めた。2026-11-11 に利用者が、この2つの追加を承認した。

C-144 の【案】のうち、次を採用する（Issue #134 の U-4・U-5）。

- (a) 整形しない記法は、原文のまま表示する。見出し（`#`）・区切り線（`---`）にも広げる
- (b) 1回の改行は、改行として表示する
- (c) 入れ子の段数の制限とリンクの文字を装飾しない規則は、実装しない

制約は次のとおり。

- CSP は `style-src 'self'` で、`style` 属性を許さない（[ADR-0015](0015-style-foundation.md)）。react-markdown は表の `align` を `style` 属性に変える
- 初回の JS は目安 200KB（Skill「frontend-build」）。今は約240KB（#160）で、2つのライブラリで約44KB 増える見込み
- 新しいライブラリは、導入前に安全性を検査して Issue に記録する。公開から2週間未満の版は使わない

## 選択肢

1. react-markdown＋remark-gfm を使い、`rehype-raw`・`rehype-sanitize` は入れない（描画する要素を許可リストで限る）
   - 良い点：既定で生の HTML を文字として出す。React の要素を作るので `dangerouslySetInnerHTML` が要らない。許可リストで描画する要素と URL を限れる
   - 悪い点：整形しない記法を原文で出すには、自前の remark プラグインが要る
2. 1.に `rehype-sanitize` を足す
   - 良い点：許可リストの機能がライブラリ側にある
   - 悪い点：要素の許可は `allowedElements` で足りる。依存が増える。要件 AC-8 が「入れない設計」と決めている
3. マークダウンを HTML に変換して `dangerouslySetInnerHTML` で出す
   - 良い点：描画の部品が単純
   - 悪い点：XSS の対策を、変換後の HTML の無害化に全面的に頼る。Skill「security」が禁じている
4. 自前のパーサーを書く
   - 良い点：依存が増えない
   - 悪い点：記法の解釈の漏れ・不具合が XSS や表示の崩れにつながる。保守の負担が大きい
5. 入力欄にプレビューを付ける
   - 良い点：書き手が結果を確かめられる
   - 悪い点：要件 AC-2 が付けないと決めている。画面と部品が増える

## 決定

選択肢1を採る。

### ライブラリ

- `react-markdown` 10.1.0 と `remark-gfm` 4.0.1 を、版を固定して追加する（`--save-exact`。2026-11-11 に利用者が承認）
- 公開から2週間未満の推移的な依存8個（`mdast-util-to-hast`・`vfile-message`・`mdast-util-to-markdown`・`mdast-util-gfm-autolink-literal`・`mdast-util-gfm-task-list-item`・`mdast-util-mdx-jsx`・`mdast-util-gfm-table`・`markdown-table`）は、`package.json` の `overrides` で、2週間以上前の直前の版に一時的に固定する（Issue #134 の U-1。2026-11-14）。`mdast-util-to-hast` は、既知の脆弱性（CVE-2025-66400）が修正済みの 13.2.1 に固定する。固定する版・公開日の一覧は `docs/tech-stack.md` の「一時的な transitive override」に記録し、2週間を過ぎた後の依存の更新で外す
- `rehype-raw`・`rehype-sanitize` は入れない。生の HTML は、HTML として解釈せず文字として出す。テストで `package.json` にないことを確かめる

### 描画する要素

- 許す要素は `p`・`br`・`strong`・`em`・`del`・`ul`・`ol`・`li`・`blockquote`・`code`・`pre`・`a` の12個だけ
- 二重の防御として、`allowedElements` で許可リストを指定し、`unwrapDisallowed` で許可しない要素は中身だけを残す。後者は、前者が漏れたときの備えである
- 全要素で `className` を捨てる（利用者由来のクラスを通さない）
- `dangerouslySetInnerHTML` は使わない

### リンク

- `urlTransform` で、`new URL()` で絶対 URL として解釈でき、スキームが `http:`・`https:`・`mailto:` のものだけを通す。相対 URL・`//` で始まるもの・`javascript:`・`data:`・`vbscript:` は通さない。大文字・空白・文字参照を混ぜた形も、解釈した後のスキームで判定する
- リンクは `target="_blank"`・`rel="noopener noreferrer"` にする
- 本文中の URL は、`remark-gfm` の自動リンクで、記法がなくてもリンクにする

### 許可しない記法

- 画像・表・タスクリスト・脚注・生の HTML・許可しない形式のリンク・見出し（`#`）・区切り線（`---`）は、書いたままの文字（原文）で出す（C-144(a) を採用、見出し・区切り線に広げる）。自前の remark プラグイン1つで、該当する構文木の節を原文の文字に戻す。ライブラリは増やさない
- 1回の改行は改行として表示する（C-144(b)）
- 取り消し線は `~~` だけ（`remark-gfm` の `singleTilde: false`）。`~1つ~` は取り消し線にしない
- メンションの強調は #139 で扱う。#134 では `@名前` を文字のまま出し、ボタン・リンクを付けない

### CSP との両立とスタイル

- 表は描画しない。これにより `align` が `style` 属性に変わる経路をなくす。`style` 属性が出ないことは、本番形の E2E で確かめる
- 整形後のスタイルは、固定のクラス `markdown-body` を持つ外枠で本文を包み、その配下の要素（`ul`・`ol`・`li`・`blockquote`・`code`・`pre`・`a`・`p`）を `frontend/src/styles/` の外部の CSS で付ける。Tailwind の初期化で消える箇条書きの印・番号も、ここで戻す。`style` 属性・任意値のクラス・動的なクラス名は使わない（[ADR-0015](0015-style-foundation.md)）

### 初回の JS の大きさ

- マークダウンの部品は `React.lazy` で動的に読み込む。読み込むまでは、今の表示（文字のまま・`whitespace-pre-wrap`）にする
- 動的に読み込んでも、初回の JS は約240KB のまま（#160 で扱う）。実測は、実装の後に下の「実測の結果」へ追記する

## 理由

- 生の HTML を HTML として解釈する経路を持たず、描画する要素・URL のスキーム・クラスを許可リストで限るので、XSS の入り口が少なく、守りを確かめやすい。許可リストを要素の指定（`allowedElements`）で書けるため、`rehype-sanitize` は要らない
- 画面の部品が React の要素を作るので、文字列の HTML を挿入する経路が要らない
- 整形しない記法を原文で出すのは、書いた内容を黙って消さず、書き手が意図した文字を失わないため（1-5 AC-1 の「文字を失わない」の考え方に合わせる）
- 表を描画しないのは、CSP を緩めて `style` を許すより、機能を1つ減らす方が安全で、業務の連絡に表が必須ではないため
- 公開から2週間未満の依存を避けるのは、悪質なパッケージが混入しても検知されるまでの時間を稼ぐため。固定は一時的で、2週間を過ぎれば外す

## 影響

- 依存が2つ（推移的な依存を含めて約100個）増え、`overrides` の8個を管理する。`docs/tech-stack.md` に記録する。2週間を過ぎたら外し、`npm audit --omit=dev`・`npm run security:osv` で確かめる
- 自前の remark プラグインと許可リストの部品（`frontend/src/features/messages/markdown/`）は、XSS の対策の中心になるため、ミューテーションの対象に足す（[ADR-0020](0020-test-scope-mutation-e2e.md)）
- 許す要素を増やすとき（例：画像・表）は、CSP・URL・スタイルへの影響を確かめ、このADRを見直す
- メンションの強調は #139 で足す。そのとき、強調の部品が許可リストの外の要素・属性を出さないことを確かめる
- 開いたままの画面に編集・削除を即時に反映する仕組みは、このADRの範囲外（#117）
- ライブラリの版を上げるときは、`rehype-raw`・`rehype-sanitize` が入っていないこと、許可リストの外の要素が出ないことを、テスト（XSS の文字列・fast-check）で確かめる

## 実測の結果（2026-11-14、実装の後に追記）

- 初回の JS の大きさ（`npm run size:report`）：950,106 B（gzip 273,411 B）。導入前は 941,339 B（gzip 270,911 B）で、**+2,500 B（gzip）** にとどまった。マークダウンの部品を動的に読み込むため、「約44KB 増える」見込みより大幅に小さい。目安200KBを超えている状態（#160）は変わらない
- 動的に読み込む塊：`MarkdownBody-*.js` 194,224 B（gzip 57,540 B）。メッセージの本文を初めて描画するときに読み込む
- 新しく入ったパッケージは93個。インストール時のスクリプトを持つものは0件、公開から2週間未満のものは0件（overrides の8個を固定したあと。一覧は `docs/tech-stack.md`）
- `npm audit --omit=dev`：0件。`npm run security:osv`：成功

## 読み込みに失敗したときの扱い（実装の後に追記）

動的に読み込む塊が読み込めなかったとき（通信の失敗など）、`React.lazy` の失敗は `Suspense` では受け止められず、React Router の既定のエラー画面（例外の詳細を出す）まで届いて画面全体が壊れる。そこで、`MessageBody` を `MessageBodyBoundary`（エラー境界）で包んだ。

- その本文だけを、書いたままの文字（原文）と案内に替える。画面の残りは動き続ける
- 例外の詳細・ファイル名は画面に出さない
- ログは足さない。共通の記録口ができる #234 で足す（エラーを握りつぶしたのではなく、失敗を明示した代替表示にしている）

【Issue #134 のコードレビュー2回目の指摘で、上の扱いを次のように変えた（元の記述は残す）】

- 動的読み込みの失敗だけを、専用のエラー（`MarkdownLoadError`。`MessageBody.tsx` の `lazy` の `import()` の失敗を包んで投げ直す）で識別する。`MessageBodyBoundary` は、このエラーのとき、書いたままの文字と「書式つきの表示を読み込めませんでした。再読み込みしてください。」を出す
- 読み込みに成功した後の描画中の例外（プラグインの不具合など）は、本文を書いたままの文字で出し、「この本文は書式つきで表示できませんでした。」を出す。例外の詳細は出さず、再読み込みを勧めず、その行だけに留める
- 理由：Skill「frontend」の、予期できるエラーと予期しないエラーを区別する規則に従うため。再読み込みで直るのは読み込みの失敗だけである
- ログは、共通の記録口ができてから #234 で足す
- テスト：`frontend/src/features/channels/channel-detail.markdown-load-error.test.tsx`・`channel-detail.markdown-render-error.test.tsx`

【Issue #134 で、利用者が追加で決めた（2026-11-14。元の記述は残す）】

- 参照形式のリンクの定義の行（`[r]: …`）の扱い：本文の参照が**許可した URL のリンクになったときだけ**、その最初の定義の行を隠す（書式の標準どおり）。どこからも使われていない定義、許可しない URL（`javascript:`・`data:`・相対など）の定義、画像の参照だけに使われた定義、同じ名前の2つ目以降の定義の行は、書いたままの文字の段落で出す（U-4：書いた内容を失わない）。画像の参照の扱いは、利用者の決定を当てはめた統括の判断。実装は `remark-restrict.ts` の `revealUnusedDefinitions`（リンクになった識別子を記録し、木の処理の後に、隠す条件に当たらない定義を原文の段落に替える）。テストは `frontend/src/features/messages/markdown/MarkdownBody.restrict.test.tsx` の describe「参照形式のリンクの定義の行の表示」（23件、XSS の5件を含む）
