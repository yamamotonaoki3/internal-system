- 関係：Issue #197、[ADR0019](0019-efficiency-trial.md)、[ADR0016](0016-supervised-automation.md)、[試行手順](../operations/efficiency-trial.md)、管理Issue #189、リリース前の確認 #160、ハーネスIssue #71（ハーネス側の番号。正式なリポジトリ `ysteam0117/harness` のIssue #71。個人の旧リポジトリ `yamamotonaoki3/harness` の #71 は別の内容）、ハーネスの改善の提案 `ysteam0117/harness` #78

| --- | --- | --- |

| #192のミューテーション | 重要15source・658変異。58.36%→65.81%→78.93%→81.53%と複数回実行。主因はStryker 10.0.0の誤分類と限定計測の設定（明示`testFiles`）であり、「同じ全体の再実行」だけが原因ではない | `docs/tech-stack.md`（Strykerの誤分類診断）、`docs/design/client-management.md`、`reports/harness-efficiency-proposal.md` |
| E2E | #192の最終QAで開発用55件・本番形9件（#123では開発用54件・本番形9件）。件数は変更ごとに `playwright test --list` で確認して書く | `docs/tech-stack.md`、`reports/123-current-delivery-status.md` |
| CI | `.github/workflows/check.yml` は `npm run check` とビルドまで。ミューテーション（`npm run mutation`）とE2E（`npm run test:e2e`・`npm run test:e2e:prod`）は各Issueでローカル実行 | `.github/workflows/check.yml`、`package.json` |
| 所要時間 | **未測定**（リポジトリに記録がない） | — |

- 現在の重要処理の対象一覧は `stryker.config.json` の `mutate`（24パターン、`!**/*.test.ts` を除く）
- ADR0019は「変更確定後は最終状態の必須全体ゲート」を各Issueに求めている

## 選択肢

| 選択肢 | 良い点 | 悪い点 |
| --- | --- | --- |
| 1. 現行維持（ADR0019の最終状態の必須全体ゲートを各Issueで） | 判断が不要で見逃しが最も少ない | 対象一覧とE2Eが増えるほど、関係のない範囲の再実行が増える。時間は未測定 |
| 2. 開発中は影響範囲に絞り、決めた時期に全体を確認する（推奨案） | 変更と無関係な再実行を減らせる。80%基準は維持できる | 影響範囲の判定を誤ると、全体確認の時期まで見逃す。判定の根拠を記録する手間が増える |
| 3. 全体をCIで毎回実行する | 人の判断に頼らず、毎回全体を確認できる | CIの時間・コストが増える。E2EはD1・起動物の準備が必要で、CIへの移行は別の作業になる |

## 決定

選択肢2を採用する。

### (a) 開発中のミューテーション

- 対象：変更した重要処理と、その変更の影響を受ける重要処理（参照元）。参照元は `.dependency-cruiser.cjs` を使ったdependency-cruiserの逆依存などで機械的に求め、求め方と結果をIssueに記録する
- 実行：対象の処理で80%以上とする。Strykerの `--mutate`・`--incremental` は未検証のため、検証が済むまでは使ったことにせず、既存の方法（`stryker.config.json` の対象を変更した範囲に絞る。`docs/testing/mutation.md` の「よくある失敗と対処」）で絞る
- 参照元の求め方：dependency-cruiserの逆依存も未検証のため、検証が済むまでは、変更したファイルの参照元を手で（`import` の検索などで）追い、追った方法を記録する
- 「重要処理」の定義は `stryker.config.json` の対象一覧とする。追加・除外の基準はSkill「品質チェックの道具」「テスト」の認証・認可・個人情報・重要な業務ルール
- 対象一覧の見直しは、重要処理を足す・外すIssue（認証・認可・個人情報・重要な業務ルールに関わる機能のIssue）の中で、そのIssueの担当が行い、理由をIssueに記録する
- 新規・変更部分と、以前の結果の有効性を確認できない部分は必ず実行する

### (b) 開発中のE2E

- 対象：新規・変更したspecと、変更が影響する画面・APIのspec、最小限のスモーク（`e2e/health.spec.ts`・`e2e/login.spec.ts`）
- spec は、変更した画面・APIに対応するものを手で選ぶ。Playwrightの `--only-changed` は未検証のため、検証が済むまでは使ったことにしない
- 影響の対応表（画面・API → spec）は最初は作らない。見逃しが出たら作る

### (c) 範囲を広げる条件

次のいずれかに当たる場合は、絞らずに重要処理全体のミューテーションとE2E全件を実行する。

- 共有定義（`shared/`）の変更
- 認証ゲート・ミドルウェア・CSP・ルーティングの枠・共通レイアウトの変更
- 依存・ビルド・テスト基盤・設定（`stryker.config.json`・`playwright.config.ts`・`playwright.prod.config.ts`・tsconfig等）の変更
- 範囲を確実に絞れない場合

### (d) 全体確認の時期

- リリース前の検証（#160）と、#189の最終確認の前の2回、重要処理全体のミューテーションと、E2E全件（開発用・本番形）を必ず実行する
- 定期的な全体実行（週1回・マージ後など）は入れない。必要になったら、所要時間の測定結果を見て、ADRの改訂で追加する
- 全コードへの一律のミューテーションは求めない

### (e) 結果の再利用条件

- 対象コード・関連する共通コード・テスト・依存・設定が変わらず、現在の対象範囲と合格基準を満たすことを確認できた場合だけ再利用する
- 証拠（コマンド・日時・結果・ハッシュ・環境）はADR0019と[試行手順](../operations/efficiency-trial.md)の記録に合わせる

### (f) 記録

- 対象と除外の理由、範囲の根拠、実行結果、再利用の根拠、生存ミュータントへの対応をIssueに記録する
- 失敗・中断・未実行を成功扱いにしない
- 範囲を絞った結果を、範囲外の合格として流用しない。ADR0019の「限定診断を全体合格へ流用せず」はこの意味で維持し、各Issueの完了条件としての全体ゲートを(d)の時期へ移す

### (g) 緩和しないもの

- 通常テスト（単体・結合）、型・Lint・セキュリティ検査（`npm run check`・`npm run security`）
- 既存の品質・セキュリティ基準（ミューテーション80%以上など。`docs/requirements/nonfunctional.md` §8）

## Skill・AGENTS.mdとの関係

- Skill「品質チェックの道具」は「影響の大きい処理（認証・認可・個人情報・重要な業務ルール）を対象に `npm run mutation`」「対象の処理で80%以上」、Skill「テスト」は「認証・認可・個人情報・重要な業務ルールではミューテーションで検出力を確かめる」と書いており、各Issueでの全体実行は要求していない。各Issueの全体ゲートはこのプロジェクトの運用（ADR0019・`docs/project-rules.md`）である
- 判断：80%基準・対象の定義・テストの種類を変えないため、Skillの規則より緩めるものではなく、プロジェクトの運用（ADR0019）の変更にあたる。ただしAGENTS.mdの「工程ごとの全体検証」の例外を広げる面があるため、AGENTS.mdの「ハーネスのルールより緩めるルールは、理由をADRに記録し、利用者の承認を得てから `docs/project-rules.md` に書く」に従い、本ADRの承認（2026-11-09）を得て `docs/project-rules.md` へ反映した

## 理由

- 80%基準と対象の定義を保ったまま、変更と無関係な再実行を減らせる
- 見逃しの危険は、機械的な範囲の求め方・根拠の記録・範囲を広げる条件・(d)の全体確認で抑える
- 時間の短縮効果は、決定時点では未測定だったため、削減率を主張しなかった。2026-11-10の計測結果は下の「計測の結果（2026-11-10）」に書く

## 影響とリスク

- 影響範囲の判定を誤ると、(d)の時期まで見逃す。対策は、機械的な求め方・根拠の記録・(c)の条件・(d)の全体確認
- dependency-cruiserで逆依存を求める方法（`deps:check` は層の違反の検出用）が使えるかは**未検証**。検証方法：既知の重要処理（例：`shared/client-rules.ts`）を変えた場合の参照元を出し、手で追った結果と比べる
- Stryker 10.1.1の `--mutate`・`--incremental` が、このプロジェクトで正しく使えるかは**未検証**。`docs/tech-stack.md` のとおり、明示 `testFiles` は静的変異の起動を遅らせる制限があり、限定計測では使わない。`--incremental` の保存結果は、テスト・依存・設定の変更や誤分類（10.0.0の事例）を引き継ぐおそれがあるため、検証後に使う場合も、保存結果はGitに入れず、(c)に当たる変更では捨てて全体を実行する。検証方法：同じ対象で通常実行と `--incremental` の結果（変異の数・分類）を比べる
- Playwrightの `--only-changed` が、このプロジェクト（`scripts/run-local.ts` 経由の起動・シード）で使えるかは**未検証**。対応表を作る場合は、画面・API・specの追加のたびに保守の負担が増える
- 所要時間は、決定時点では未測定だった。2026-11-10に測定した（下の「計測の結果（2026-11-10）」）
