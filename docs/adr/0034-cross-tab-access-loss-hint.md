# 0034：別のタブには、資格の喪失を「確かめのきっかけ」として伝え、受けたタブは自分で確かめ直して、隠して読み込み直すだけにする

- 状態：採用（Issue #341。決定記録 C-208）
- 日付：2026-11-23
- 関係：Issue #341（この ADR。#323 の4つ目）・#323（親）・#338・#339・#340・#342・#298・#376・#239・#372、決定記録 C-117・C-206・C-207・C-208、[ADR-0033](0033-reload-page-after-access-loss.md)・[ADR-0030](0030-clear-cache-on-user-switch.md)、[docs/design/access-loss.md](../design/access-loss.md)・[cases.md](../design/cases.md)・[drafts.md](../design/drafts.md)、Skill「frontend-state」「security」

## 背景

- #338（ADR-0033）は、資格を失ったと確定したタブを、ページごと読み込み直す。#340（C-207）は、そのタブで、案件の部屋のメッセージの下書きを消す。どちらも、**確定したタブ**の中の話である
- 同じ保存の区画（同じブラウザ・同じプロファイル）で、同じ案件を開いている**ほかのタブ**は、自分の通信で 403 などを受けるまで、案件の中身を持ち続ける。画面を表示していないタブ（別の画面を開いている・隠れている）は、自動の更新が止まっている間、受けることもない
- 同じ Cookie を共有するタブでは、画面の利用者（セッションのキャッシュ）と、通信の利用者（Cookie）が食い違うことがありうる（#298。方式は未決定）。その状態で、確かめの応答（別の利用者への答え）を、画面の利用者の喪失と取り違える場合が、いまの `main` でもある（#376）。下書きは、消すと戻らない
- #239（C-117）は、下書きの別のタブへの伝え方として、`storage` のイベントも `BroadcastChannel` も、入れないと決めた（ログアウトの後の書き戻しについて）

## 選択肢

| 案 | 内容 | 良い点 | 悪い点 |
| --- | --- | --- | --- |
| A | 何もしない（各タブが、自分の通信で検出する） | 変更がない | 画面を表示していないタブ・自動の更新が止まっているタブに、中身が残り続ける |
| B | `storage` のイベントで伝える | 古いブラウザでも使える | 値が保存先に残り、消す処理と、残った値の読み分けが要る。#239 で、意図して購読していない |
| C | `BroadcastChannel` で伝え、受けたタブは、合図をそのまま信じて、片付け・下書きの消去まで行う | 受けたタブで、書き戻しの隙間まで塞げる | 合図の利用者を、通信の利用者と結び付けられない。画面と通信の利用者が食い違うタブ（#298・#376）で、別の利用者への応答を根拠に、消すと戻らない下書きを消すおそれがある |
| D（採用） | `BroadcastChannel` を**確かめのきっかけ**にだけ使う。受けたタブは、合図の利用者が自分のセッションの利用者と同じで、その案件の参加者の概要を持つときだけ、自分で概要を取り直して確かめ、非参加・404 なら、**画面を隠して読み込み直すだけ**（片付け・下書きの消去・合図の送り返しはしない） | 残らない（保存しない）。消すと戻らないものを、確かめられない答えで消さない。取り違えても、新しい文書がセッションを取り直して正しい利用者になるので、失うのは保存していない入力に限られる。サーバー・API を変えない | 受けたタブでは、下書きを消さない（書き戻しの隙間は完全には塞がらない）。取り違えた場合、別の利用者に種類だけの知らせが1回出る |

## 決定

案 D を採る。

- 伝える手段は、ブラウザに組み込みの`BroadcastChannel`だけ（ライブラリを足さない）。チャンネルの名前・合図の形（版・利用者の ID・案件の ID だけ）・Zod での検証・送る関数・受ける関数は、`frontend/src/features/access-loss/access-loss-broadcast.ts`の1か所に置く。保存先には何も残さない
- 送るのは、喪失が**確定した**ときだけ（確かめられない場合・参加者だったことを見ていない非参加・参加者のままの 403・退出の失敗では送らない）。読み込み直しの予約の印とは**別の印**で、1回だけ送る（確かめられないまま予約した後に、確定した場合も伝えるため）。順序は「入口 → 合図 → 下書きの消去」
- 受けたタブの処理は、`frontend/src/features/cases/case-access-loss-relay.ts`の`installCaseAccessLossRelay`が持ち、`main.tsx`で1回登録する。入口が`idle`・合図の利用者とセッションの利用者が同じ・その案件の参加者の概要をキャッシュに持つ、の全部を満たすときだけ、概要を**キャッシュの外で**1回取る。非参加・404 のときだけ、入口`requestAccessLossReload`（理由`lost`）を呼ぶ。参加者のまま・5xx・通信の失敗なら、何もしない
- 画面の側の想定外の例外は、ブラウザの標準のエラーの報告`reportError`に渡す（利用者の決定。画面の側のログの仕組みは #372）

## 理由

- 消すと戻らない下書きを、認証された利用者を確かめられない答えで消さない（#340 で得た教訓。#376）。読み込み直しは、取り違えても、新しい文書がセッションを取り直すので、失敗の害が小さい
- 合図は保存しないので、読み込み直した後の文書が、古い合図を受け取り直さない。`storage`のイベントのような、残った値を消す処理が要らない
- 「合図の利用者」を通信の利用者の証明にしない。合図は、確かめを始めるきっかけにだけ使い、喪失の根拠は、受けたタブ自身が取る、サーバーの概要の答えだけにする（Skill「security」）
- API を変えない（要件の変更に当たらない）。#298 の方式を先取りしない

## #239 の「`BroadcastChannel`は入れない」との関係

#239（C-117）の決定は、下書きの、別のタブのログアウトの後の書き戻しについてのものである。この ADR は、**資格の喪失の確かめのきっかけ**にだけ使う（利用者の決定。2026-11-23 の Q1）。ログアウト・利用者の切り替え（#298）には広げない。下書きの`storage`イベントの非購読も、変えない。[drafts.md](../design/drafts.md)の記述に、この範囲を注記した。

## 影響

- 別のタブで確定した喪失は、同じ保存の区画で、**その案件の参加者の概要をキャッシュに持つ**タブへ、自分の通信を待たずに届く。その案件を表示していないタブも、読み込み直す（利用者の決定。Q3）。入力中で保存していない内容は消える。知らせは`lost`の文（本人が別のタブで退出した場合も同じ。Q2）
- テストでは、`BroadcastChannel`を、`frontend/src/test/setup.ts`で、テスト専用の`frontend/src/test/fake-broadcast-channel.ts`に差し替える（本物は、閉じないとテストの間で値が混ざりうるため。本番のコードには、テスト専用の分岐を入れない）。`reportError`は、jsdom にないので補う
- **残る範囲**（この決定では解消しない。「別のタブの全部を、解消した」とは言わない）：
  - 参加者の概要を持たないタブ：一覧・スレッド・検索などに、中身が残りうる（#339）【追記（2026-11-27。Issue #339・C-210・[ADR-0036](0036-case-access-loss-outside-view.md)）：中継の対象を、「参加者の概要をキャッシュに持つタブ」から、「参加者の概要、または同じ案件の部屋・スレッドの取得の実績を持つタブ」に広げた（概要を持たず、スレッドだけを取得したタブにも効く。実績は Query のキャッシュから求め、台帳は作らない）。受けたタブは、これまでどおり入口だけを呼び、片付け・下書きの消去・合図の送り返しはしない。合図を**送る**場所も、画面の外の確定（見張りの`settleOutside`。返信・部屋の拒否、一覧の行の消失からの確かめ）に広がった。実績も概要も持たないタブと、検索だけの経路は残る。この ADR の決定（案 D）は変えない。上の記述は元のまま残す】
  - 別のタブの下書きの書き戻し（#340 の既知の限界）：受けたタブは下書きを消さない。受けたタブが、非参加・404 で入口に進んだ場合だけ、入口が待機に入ると入力欄が隠れ、隙間が縮む。入口に進む処理がなく入力欄が操作できる状態（確かめが 5xx・通信の失敗・参加者のまま、合図を捨てた、`BroadcastChannel`が使えない）では、これまでどおり書き戻しが続く。残った下書きは、保存から7日・ログアウトで消える
  - 画面を離れた後に、確かめられないまま終わり、作り直した画面で、後から確定した場合は、合図を送らない（参加者だったことを見ていないため。ADR-0033 の「作り直しの経路」と同じ）
  - `BroadcastChannel`が使えない環境・別の保存の区画（別のブラウザ・プロファイル・プライベートウィンドウ）：これまでどおり、各タブが自分の通信で検出する
  - 取り違え（#376 と同じ条件）で読み込み直した場合：種類だけの知らせ（案件の中身は含まない）が、新しい文書の最初の利用者に、1回出る【追記（2026-11-24。ADR-0035）：別の利用者に替わって読み込み直す場合は、切り替えの入口が、読み込み直す前に保存済みの知らせを消すので、出ない（`clearAccessLossNotice`）。それ以外の経路で、この動きが残るかは、`access-loss-notice.test.tsx`の既知の動きのテストが固定している】
  - **この Issue の範囲の外**：画面の利用者と通信の利用者が食い違うタブでの取り違え（#376。#341 の次に優先して直す）、書き込みの取り違え（#298）
    - 【追記（2026-11-24。Issue #298・#376・C-209・[ADR-0035](0035-session-user-mismatch-header.md)）：この2つは ADR-0035 で扱った。画面が想定の利用者を要求ヘッダーで伝え、サーバーが食い違いを 409 `SESSION_USER_MISMATCH` で断る。受けたタブの確かめ（概要の直接の取得）も、そのヘッダーを付けて送るので、食い違うタブでは 409 になり、「分からない」として何もしない（入口を呼ばず、下書きも消さない）。画面の利用者を替えたい場合は、ADR-0035 の入口が、ページごと読み込み直す。この ADR の決定（案 D）は変えない。上の記述は元のまま残す】
  - bfcache（#342）
- 見直す条件：#298 で、画面の利用者と通信の利用者の食い違いが根本から扱われたとき（受けたタブでも確定して消す案を、改めて検討できる）。#376 は、喪失を確定する前に、セッションの API で利用者を確かめる画面だけの変更で直す方針（利用者に確認中）で、応答と利用者を結び付けるものではないので、受けたタブの書き戻しは塞がない。`BroadcastChannel`の用途を、資格の喪失の外へ広げるとき【追記（2026-11-24。ADR-0035）：#376 は、画面だけの方式をやめ、#298 とまとめて、サーバーが食い違いを断る方式（ADR-0035）で直した。受けたタブでも確定して消す案を改めて検討できる条件（#298 の根本の対応）は、ADR-0035 で満たされたが、この ADR の決定（受けたタブは消さない）は、まだ変えていない】
