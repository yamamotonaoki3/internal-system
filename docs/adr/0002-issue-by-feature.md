# 0002：Issueを実装する機能の単位で立てる

- 状態：採用（利用者の承認。2026-10-19）
- 日付：2026-10-19
- 関係：Issue #34（AC-5）

## 背景

利用者の指示（2026-10-19）により、Issueを作業領域ごとに分けず、実装する機能の単位で立てることにした。ハーネスを更新すると、AGENTS.mdに反映した変更が消えるおそれがあるため、プロジェクト固有のルールとして記録する。

緩めるハーネスのルールは、AGENTS.md「作業の流れ」1と「要件定義とIssueへの分割」3、Skill「実装の進め方」の「3. Issueへの分割」である。「作業領域ごとに子Issueに分ける」「対象の作業領域を書く」は適用しない。

## 選択肢

1. 作業領域ごとにIssueを分ける
   - 領域ごとに作業を分けられるが、1つの機能の確認が複数のIssueとPRに分かれる
2. 実装する機能の単位でIssueを立てる
   - 必要な領域の変更をまとめ、1つのPRで機能が動くことを確かめられるが、Issueが大きくなりすぎないようにする必要がある

## 決定

選択肢2（実装する機能の単位でIssueを立てる）を採る。

Issueは、実装する機能の単位で立てる。フロントエンド・バックエンド・DBなどの作業領域では分けない。1つのIssueで、必要な領域の変更をまとめて行う。複数の機能にまたがる大きな要求は、機能ごとのIssueに分け、必要なら親Issueでまとめる。

## 理由

領域ごとに分けると、1つの機能の確認（動作確認・レビュー）が複数のIssueとPRに分かれ、全体を確かめにくい。機能の単位なら、1つのPRで、機能が動くことを確かめられる。

利用者の指示（2026-10-19）に基づく。

## 影響

- ハーネスのルールより緩める決定として、`docs/project-rules.md`に記録する
- 1つのIssueが大きくなりすぎないよう、Skill「実装の進め方」の「単独でレビュー・マージできる大きさ」を守る。大きすぎる場合は機能を分けてIssueを立てる
