# 0003：認証にクッキー方式のセッションを使う

- 状態：提案
- 日付：2026-10-20
- 関係：Issue #46、Skill「セキュリティ」（`.claude/skills/security/SKILL.md`の「認証・セッション・トークン」「CSRF・HTTPメソッド・Cookie」）、`docs/requirements/nonfunctional.md`の3章、`docs/requirements/00-foundation.md`の0-2・0-3

## 背景

社内のSlack風ワークスペース（学習用）の認証方式を決める必要があった。前提と制約は次のとおり。

- ブラウザ向けのWebアプリである。画面（React）とAPI（Cloudflare WorkersのHono）は、1つのWorkersにまとめ、同じドメインから配信する（`docs/tech-stack.md`の「Vite＋React Router」）。スマートフォンもブラウザの画面で使い、専用のアプリは作らない
- 認証はアプリ独自（ユーザーIDとパスワード）で、Googleなど外部のログインは使わない。アカウントは全体管理者が発行し、自己登録はない（`docs/requirements.md`の認証方式の判定、0-1、0-2）
- セッションについての要件は、`00-foundation.md`の0-2・0-3にある
  - 無操作のまま30分でログアウトされ、ログインから1日が経つと操作中でもログアウトされる（0-2 AC-5）
  - 同じアカウントで複数の端末・ブラウザに同時にログインできる。ログアウトは、その端末のセッションだけが対象（0-2 AC-6）
  - ログアウトすると、セッションが破棄される（0-2 AC-2）
  - パスワードを変更すると、ほかのセッションが無効になる（0-3 AC-4）
  - パスワードを再発行すると、その社員のすべてのセッションが無効になる（0-3 AC-8）。社員を無効化するとログインできなくなる（0-1 AC-9）。非機能要件（`nonfunctional.md`の3章）は、無効化でもすべてのセッションを無効にする案としている
- Skill「セキュリティ」は、認証のCookieを`SameSite=Lax`・`Secure`・`HttpOnly`にすること、状態を変える操作で`Origin`を確認すること、ブラウザではJavaScriptから読めるWeb Storageに認証トークンを保存しないことを定めている
- `nonfunctional.md`は、現在「案（利用者の確認前）」である。ここで参照する数値・前提のうち、0-2・0-3に由来するものは要件定義書の受け入れ条件、それ以外（無効化によるセッションの失効など）は案である
- 既存の要件では、利用者とセッションを保存するDBに D1 を使う（`docs/requirements.md`）。保存の構造・失効の処理などの詳細は、この ADR では決めない（実装の計画で決める）

## 選択肢

1. クッキー方式：サーバーがセッションを持ち、セッションIDを`HttpOnly`のクッキーで運ぶ
   - 良い点：ブラウザが自動で送る。画面のJavaScriptから読めない。サーバー側で即座に無効にできる。同じサイトの画面とAPIでは単純に使える
   - 悪い点：CSRF（ほかのサイトから、ログイン中の利用者の権限で操作させられる攻撃）への対策が要る。別ドメイン・アプリ・外部システムからは使いにくい。サーバー側にセッションの保存先が要る
2. JavaScriptが保持し、`Authorization`ヘッダーで送るトークン方式（JWTなど）
   - 良い点：別ドメイン・スマートフォンのアプリ・外部システムに向く。サーバーが状態を持たなくてよい場合がある
   - 悪い点：JavaScriptから読める保存先では、XSS（悪意のあるスクリプト）によるトークンの窃取のリスクがある。自己完結型のJWTを、サーバー側の状態を照合せずに検証する場合は、期限前の失効に追加の仕組み（失効リスト、短い有効期間と更新トークンなど）が要る（Skill「セキュリティ」に規則がある）。上記の要件（端末ごとのログアウト、パスワード変更・再発行での無効化）を満たすには、サーバー側に失効の状態を持つ必要があり、サーバーで照合する不透明なトークンにすれば、クッキー方式のセッションと同様に失効できる

## 決定

選択肢1（クッキー方式のセッション）を採る。

セッションの保存の構造・失効の処理、パスワードの規則など細部は、この ADR では決めない（実装の計画と、要件定義書・Skill「セキュリティ」で決める）。

## 理由

- 画面とAPIが同じドメインなので、クッキーをブラウザが自動で送る方式で足りる
- 認証情報（セッションID）を`HttpOnly`のクッキーに置くので、XSSがあっても、画面のJavaScriptからは読めない
- 要件のセッション無効化（その端末だけのログアウト、パスワード変更でのほかの端末の失効、パスワードの再発行ですべての失効）を、サーバー側で確実に行える。案として検討中の、社員の無効化によるすべてのセッションの失効にも、同じくサーバー側でセッションを無効にできるため対応できる
- スマートフォンもブラウザで使うので、同じ方式で足りる。これは要件にある事実ではなく、設計上の整理である（スマートフォンのブラウザも、同じサイトのログイン用クッキーを通常どおり扱う）

## 影響

- CSRFへの対策として、状態を変える操作で`Origin`を確認し（`docs/tech-stack.md`の`originCheck`、Skill「セキュリティ」の「CSRF・HTTPメソッド・Cookie」）、クッキーは`SameSite=Lax`・`Secure`・`HttpOnly`を標準とする
- セッションを保存するDBに D1 を使うことは、既存の要件のとおりである。保存の構造・失効の処理は、実装の計画で決める
- 見直す条件：スマートフォンの専用アプリを作る、外部システムがAPIを使う、複数のドメインにまたがる構成になるとき。必要になった時点で、対象のAPIへのトークン方式の追加を含め、別のADRで再検討する
- アプリ内のブラウザ（LINEなど）で開く運用では、クッキーの扱いが通常のブラウザと違う場合があるので、実機で確認する
