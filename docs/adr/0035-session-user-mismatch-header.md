# 0035：画面が想定の利用者を要求ヘッダーで伝え、セッションの利用者と食い違えば、サーバーが 409 で断る

- 状態：採用（Issue #298。決定記録 C-209）。サーバーの側は実装済み（PR-1。2026-11-24 にマージ）。画面の側は PR-2b で実装した（下の「画面の側の決定」。2026-11-24）
- 日付：2026-11-23
- 関係：Issue #298（この ADR）・#376・#300・#377・#338・#341・#380・#382・#383、決定記録 C-187・C-206・C-208・C-209、[ADR-0030](0030-clear-cache-on-user-switch.md)・[ADR-0033](0033-reload-page-after-access-loss.md)・[ADR-0034](0034-cross-tab-access-loss-hint.md)・[ADR-0020](0020-test-scope-mutation-e2e.md)、[docs/design/auth-session.md](../design/auth-session.md)、[API 仕様書の下書き 2.2・2.3](../requirements/api-draft.md)、Skill「security」「error-api」

## 背景

- セッションの Cookie は、ブラウザ全体（同じ保存の区画）で1つである。あるタブで別の利用者がログインすると、ほかのタブの画面は、前の利用者のまま残っていても、以後の通信は、新しい利用者のセッションとして扱われる
- このため、画面の利用者と、通信の利用者が食い違うタブでは、次の取り違えが起きうる
  - 書き込みの取り違え（#298）：古い画面で入力した操作が、別の利用者の名前で受理される
  - 応答の取り違え（#376）：別の利用者への応答を、画面の利用者の資格の喪失と取り違える（[ADR-0034](0034-cross-tab-access-loss-hint.md) の「残る範囲」）
- [ADR-0030](0030-clear-cache-on-user-switch.md) は、同じタブでの切り替えの表示の側だけを守る。別のタブでの切り替え・進行中の操作・通信の宛先は、守れない

## 選択肢

| 案 | 内容 | 良い点 | 悪い点 |
| --- | --- | --- | --- |
| A（採用）| 画面が、想定の利用者を要求ヘッダー `X-Expected-User-Id` で付け、サーバーが、有効なセッションの利用者と食い違えば、409 `SESSION_USER_MISMATCH` で断る | 食い違いを、要求を処理する前に、サーバーが同じ要求の中で判定できる。画面の状態や古い処理の数え上げに頼らない | 画面の側が、ヘッダーを付ける作りを持つ必要がある。ヘッダーを付けない通信（添付の配信など）は守れない |
| B | 画面だけで、通信の前後にセッションの API で利用者を確かめ直す | サーバーを変えない | 確かめと本体の通信は別の要求で、その間に Cookie が替わりうるので、応答の宛先を画面だけで証明することは、原理的にできない（確かめ直しを重ねても、隙間は閉じない） |
| C（乙）| 要求を始めた時点の利用者の ID を、各 API の関数の必須の引数で運ぶ | 付け忘れを型で止められる | 約100の API の関数と、その呼び出し元・テストの部品の書き換えが、全機能に及ぶ。古い処理はメモリに残り、後処理の書き戻しは別に守る必要がある |
| D（丙）| 画面の木ごとに利用者を持ち、閉じ込めた関数で通信を作る | 木の中で始めた処理に、木の利用者が付く | C とほぼ同じ範囲の書き換え。古い処理が残る点も同じ |
| E | ヘッダーが無い認証の要る書き込みも、断る | 古い版の画面や付け忘れの書き込みも止まる | デプロイ直後の古い版のタブの書き込みが、読み込み直すまですべて失敗する。社内の利用者が少なく、古いタブが残る期間は短いことから、採らない |
| F | 食い違いに 401 または 403 を使う | 既存のコードを使える | 403 は資格の喪失の契機になり（C-190）、取り違えを増やす。401 は、ログインが切れた意味になり、ログイン画面へ移る処理が動く。どちらも意味が違う |

画面の側で、ヘッダーの値を何に結び付けるかは、案 A の中で、次の3つを比べた：甲（文書の利用者に固定し、替わったらページごと読み込み直す）・乙（C）・丙（D）。甲は、変更が局所的で、古い処理を数え上げて止める必要がなく、ADR-0033 と同じ考え方である。

## 決定

案 A を採る。

### サーバーの契約

- 画面は、要求ヘッダー `X-Expected-User-Id` に、想定の利用者の ID を付けられる。名前は `shared/session-user-header.ts` の1か所に置く（バックエンドと画面の両方が同じ名前を参照する）
- サーバー（`loadSession`。認証のミドルウェア）は、Cookie のセッションが有効で、ヘッダーがあり、その値がセッションの利用者の ID と文字列として完全に一致しないときは、409 `SESSION_USER_MISMATCH` で断る。`Cache-Control: no-store` を付ける。公開の経路（ログアウトを含む）でも、同じに扱う
- **ヘッダーは、断る向きにだけ使う**。認可・利用者の特定には使わない。利用者は、これまでどおり Cookie のセッションだけで決まる。ヘッダーの値は、ログにも応答にも出さない（応答の文は固定）
- **ヘッダーが無い要求は、これまでどおり通す**。セッションが無い・使えない（期限切れ・失効・無効化）ときは、ヘッダーがあっても、これまでの結果（401 など）のままにする
- **空・形の崩れた値は、食い違いとして断る**（500 にしない）。一致しない値は、すべて断る
- 比べる位置は、セッションの期限・失効の判定の**後**で、最終操作の時刻の更新の**前**（`resolveSession`）。食い違いのときは、最終操作の時刻を更新せず、セッションの失効・Cookie の削除もしない（別の利用者のセッションは有効なまま）。認可・初回パスワードのゲート・業務の処理・監査・DB の書き込みより前に断る
- API 仕様書（`docs/api/openapi.json`）は、全操作に 409 と共通の応答 `SessionUserMismatch` を足し、ヘッダーの説明を書く。既存の 409（`CONFLICT`）の説明は残す

### 画面の側の方針（PR-2b で実装した。細部は下の「画面の側の決定」）

- 画面は、**その文書（ページ）で最初に確定した利用者**に、ヘッダーの値を固定する。401・ログアウトでキャッシュが消えても変えない。セッションの取得・ログインには付けない
- セッションの利用者が、文書の利用者と違うと分かったら、受理済みの操作を最大5秒待ち、ページごと1回だけ読み込み直す。同じタブでの別の利用者のログインも、その場の作り直しではなく、読み込み直しにする
- 既存の画面の 409 の分岐は、ステータスではなく、エラーコード `CONFLICT` で判定する
- 409 `SESSION_USER_MISMATCH` を、資格の喪失と取り違えない（#376）。確かめられないときは、中身を隠す（安全な側）
- PR は3本に分けた：PR-1（サーバー）・PR-2a（画面の 409 の分岐を `CONFLICT` のコード判定へ置き換え。#379）・PR-2b（画面の側と #376）。PR-1 の時点では、画面はヘッダーを付けず、画面の動きは変わらなかった。PR-2b で画面の側を実装し、ADR-0030 の「別のタブは範囲外」「同じタブの切り替えは、その場の作り直し」の部分（決定記録 C-187 の該当部分）を置き換えた

### 画面の側の決定（PR-2b。2026-11-24 に実装）

**この決定が置き換えるもの**：[ADR-0030](0030-clear-cache-on-user-switch.md)（決定記録 C-187）の「別のタブで別の利用者がログインした場合は範囲外（Issue #298）」と、「同じタブでの別の利用者のログインは、その場でキャッシュを捨てて画面を作り直す」の部分。ADR-0030 のキャッシュを捨てる見張り（`installUserSwitchGuard`）と、認証の枠の作り直し（`RequireAuth`）は、**読み込み直すまでの二重の守りとして残す**。[ADR-0033](0033-reload-page-after-access-loss.md)（C-206）の「別の利用者に替わったら待機を取りやめる」は、#338 の入口の中では変えない。別の利用者に替わったと分かった後は、利用者の切り替えの入口が優先する（下の「入口どうしの交錯」）。[ADR-0034](0034-cross-tab-access-loss-hint.md)（C-208）の「取り違え（#376）は範囲の外」は、この決定で扱った（下の「資格の確かめ」）。

- **ヘッダーの値**：文書（ページ）で最初に確定したセッションの利用者に固定する（`frontend/src/features/auth/document-user.ts`の`installDocumentUser`・`expectedUserIdFor`）。401・ログアウトでセッションのキャッシュが消えても、別の利用者に替わっても変えない。付けるかどうかは、`frontend/src/services/api-client.ts`が、登録された関数（`setExpectedUserIdProvider`）に尋ねて決める。**セッションの取得（GET `/auth/session`）とログイン（POST `/auth/login`）には付けない**（いまの利用者を知るため・利用者を替えるための要求のため）。ログアウトなど、ほかの要求には、確定済みなら付ける
- **別の利用者に替わったと分かったとき**：ページごと1回だけ読み込み直す（入口`requestUserSwitchReload`。`frontend/src/features/access-loss/reload-after-access-loss.ts`）。見つけるのは、(1) セッションのキャッシュの利用者が、文書の利用者と別の値になったとき（`installUserSwitchGuard`）と、(2) 409 の後のセッションの取り直し（下の「409 を受けたとき」）の2つで、どちらも`reportOtherUser`を通るので、文書の間に1回だけ呼ぶ。最初に確定した利用者（最初のログイン）・同じ利用者の再ログインでは、読み込み直さない。同じタブでの別の利用者のログインも、その場の作り直しではなく、読み込み直しになる
  - 入口は、#338 の状態（`idle`・`waiting`・`reloading`）・覆い（`AccessLossBoundary`）・離脱の確認の抑止（`beforeunload`）・待ち方（受理済みの操作を、最初の要求から最大5秒待つ。1つ後のタスクの後に確かめ直す）を使い回す。持ち主・取りやめ・知らせ・読み込み先の決め方は使わない（文書の利用者は変わらないので、戻っても読み込み直す）
  - 受理済みの操作を待つ理由：Cookie が替わる前に A として送られた書き込みは、サーバーで A として受理されうるため、その成功の後処理（投稿の後の下書きの消去など）を走らせる。Cookie が替わった後に送られる A の要求は 409 になるので、待ちは長くならない（利用者の決定の Q13）
  - 知らせは出さない（Q7）。読み込み直す直前に、前の文書で保存済みの喪失の知らせを消す（`clearAccessLossNotice`。新しい文書の最初の利用者に、前の利用者の知らせを出さないため）。#338 が読み込み直しを始めた後に切り替えを検知した場合も消す
  - 入口どうしの交錯：#338 の待機中に切り替えを検知したら、抑止を途切れさせず待機を引き継ぐ（`handOver`）。切り替えの入口が動き出した後は、#338 の入口は、持ち主に関わらず何もしない。読み込み直しが2回にならず、抑止が外れない
- **409 を受けたとき**（`frontend/src/features/auth/session-user-mismatch-handler.ts`。`main.tsx`が`setSessionUserMismatchHandler`に1回だけ登録）：セッションを1回取り直し、結果を4つに分ける。同時の 409 は、進行中の1つの取り直しに合流する。進行中の取得は、取り消してから新しく取る（データが無いとき、TanStack Query は新しい取り直しを既存の取得に合流させるため。409 より前に送られた通信の答えを使わない）
  - `switched`：別の利用者が返った。切り替えの入口を呼ぶ
  - `same`：文書の利用者が返った（Cookie が元に戻った等）。**続けて3回目の`same`は、`unknown`にする**（食い違いの応答と、同じ利用者の答えが繰り返す矛盾した状態で、回り続けないため）。数える単位は、完了した取り直し（同時の 409 は1回）。`same`以外の結果・`unknown`を返したとき・最後の`same`から30秒、409 が無かったときに、数を戻す
  - `unauthenticated`：401。既存の 401 の処理が動く
  - `unknown`：5xx・通信の失敗・答えが分からない。中身を隠す（既存の「ログイン状態を確認できませんでした」と再試行。Q5）
  - 取り直しの答えは、取り直しの間にその Query に届いた更新の種類で見分ける（`frontend/src/lib/refetch-answer.ts`）。手での書き換え（`setQueryData`）が混ざった・答えが1つに決まらないときは、「答えなし」として、安全な側（`unknown`。切り替えの入口が動いていれば`switched`）に倒す。成功の回数だけでは、手での書き換えと取り消しが重なったときに、答えを見誤るため
- **資格の確かめ**（`frontend/src/features/cases/hooks/useCaseAccessLoss.ts`の`verifyParticipant`。#376）：概要を取り直した答えで決める（キャッシュを後から読まない。取り直しの後にキャッシュから捨てられても、不在を喪失の証拠にしない）。答えが 409 `SESSION_USER_MISMATCH` のときは、409 の後の取り直しの結果を待ち、**別の利用者が確かで、切り替えの入口が動いているときだけ**`switched`とする。`switched`では、片付け・読み込み直しの予約・合図・下書きの消去・表示の切り替えをしない（文書ごと替わる）。それ以外（`same`・`unauthenticated`・`unknown`、見分けられない・あいまいなとき）は`unverified`（中身を隠し、再試行と読み込み直しを促す。下書きは消さない。Q14）。**動きの変化**：取り直しの答えが得られないとき（オフラインなど）も、`unverified`になる
- **既存の画面の 409 の分岐**：ステータスではなく、エラーコード`CONFLICT`で判定する（PR-2a。`isConflictError`）。食い違いは、競合の表示にならない
- **つなぎ方**：`frontend/src/main.tsx`が、文書の利用者の登録（見張りより前）・ヘッダーの関数・409 の処理・見張りへ、切り替えの入口を関数として渡す。`features/auth`は`features/access-loss`を取り込まない（`npm run deps:check`）

#### 統括の決定（2026-11-24）

テストの作成で見つかった、計画に書かれていなかった細部。利用者の決定（Q5・Q14：確かめられないときは、安全な側に倒す）の範囲の中で、統括が決めた。要件は変えていない。

1. 既存のテスト T23（未ログインで始まり、最初に確定する利用者が B の流れ）は、「最初に確定した利用者では読み込み直さない」ので、読み込み直しは0回。計画の表の誤りで、T23 の期待は変えない
2. `same`が続く数え方：完了した取り直しを単位とし、3回目を`unknown`にする。数を戻す条件は上のとおり。「取り直しは2秒に最大1回」の保証は、3回で止まるので、取り下げる
3. 資格の確かめが結果を求めたとき、進行中の取り直しが無ければ、新しく始める。取り直しがほかの処理（ログインなど）に取り消されたときは、その時点のセッションが別の利用者なら`switched`、それ以外は`unknown`。取り消しを理由に、セッションの状態を失敗にはしない
4. 取り直しの最中に、ほかから書き換えられた・成功と失敗の両方の回数が増えた：見分けられないので`unverified`
5. `switched`が返ったが、切り替えの入口が動いていない：`unverified`
6. 文書の利用者が確定する前のセッションの取得の失敗は、いまと同じ（ヘッダーは付かない）。ログアウトの直後の 409 は、ふつうの 409 と同じ処理（取り直し → 未ログイン → 既存の 401 の扱い）
7. 新しいテストは、既存の大きなファイルに足さず、別のファイルにしてよい

## 理由

- 画面だけで、通信の宛先を証明する方式（案 B）は、原理的に閉じない。確かめと本体の通信は別の要求で、その間に Cookie が替わりうる。サーバーが、同じ要求の中で、Cookie のセッションと想定の利用者を比べるのが、唯一、競合なしに判定できる位置である
- ヘッダーは、断る向きにだけ使う。クライアントの値を信用して利用者を決めない（Skill「security」）。偽の値を付けても、断られる側にしか働かず、権限を得ることはない。別の利用者の ID を付けて、その利用者になりすますことはできない
- 最終操作の時刻の更新より前に比べる。食い違った要求が、別の利用者のセッションの無操作の期限を延ばさない
- ヘッダーが無い要求を通すのは、古い版の画面・API の検査・テストを壊さないため。守られない範囲は、下の「残る隙間」に書く
- 409 は、`CONFLICT` と別のコードにする。画面が、競合の表示と取り違えない。401・403 は、上の案 F の理由で使わない

## 残る隙間（この決定では解消しない）

- **添付の配信**（画像の表示・ダウンロード）：ブラウザが直接取りに行く通信にはヘッダーを付けられない。そのとき見えるのは、その時点の Cookie の利用者が見られる添付だけで、書き込みではない
- **古い版の画面**（デプロイの前から開いているタブ）：ヘッダーを付けないので、読み込み直すまで、これまでどおり
- **文書の利用者が決まる前の通信**：ログイン画面・初回セットアップだけ。守る対象の画面の利用者がいない
- **取り直しが未ログインだったとき**、内部の結果の名前が`unauthenticated`でなく`unknown`になる経路がある（ログイン画面への移動・`unverified`・数の戻しは維持される）：Issue #382
- **別のタブのログインの直後に、古いタブの 401 が、新しい Cookie を消すことがある**：以前からのサーバーの動きで、この決定では変えない：Issue #383
- 一部のテストが、全体の実行のときだけ不安定：Issue #380

- 添付の配信を、ヘッダーで守る必要が出たとき
- ヘッダーが無い通信を断る必要が出たとき（案 E の条件が変わったとき）
