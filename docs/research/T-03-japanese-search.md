# T-03 日本語全文検索の方式（D1のFTS5・LIKE・分かち書き・外部サービス）

## 1. 目的と範囲

- 目的：機能4（メッセージ・案件の検索）を、Cloudflare D1（SQLite）でどう実現できるかの選択肢を絞る。Issue #105（全体設計の方針）の前提にする。
- 範囲：公式ドキュメント（developers.cloudflare.com、sqlite.org）と、公開されている実例記事の調査のみ。D1の作成・課金・実機での計測はしていない。
- 対象の要件：4-1 AC-1〜AC-3（検索語は1〜100文字、1文字の検索も認める。C-90）、4-2、非機能要件（検索のp95を2秒以下、メッセージは1チャンネル1万件程度・全体で数十万件程度。C-88）、データモデルの`messages.body`（マークダウンの原文）。
- 決定はしない。「推奨案」は理由つきの参考にとどめる。

## 2. 調べた日

2026-11-02（システムの日付）。Cloudflareの制限や仕様は変わりうるため、設計の確定前・実装前に再確認する。数値は`WebFetch`の要約を介して取得しているため、転記ミスの可能性がある（確定時は原文のページで確認する）。

## 3. 結論（要点）

- D1はSQLiteのFTS5（`fts5vocab`を含む）を使える。ただしSQL文のページには「SQLite拡張の一部だけをサポート」とあり、どのトークナイザが使えるかは公式ページから確認できなかった。**trigramトークナイザがD1で動くかは未確認**であり、設計の最初に1行のSQLで確かめる必要がある。（出典1・2）
- FTS5の標準のトークナイザ`unicode61`は、空白と記号でしか区切らない。日本語は文字の連続が1つの長い「語」になり、語の一部では一致しない。日本語の検索には、そのままでは使えない。（出典3。CJKへの言及はなく、規則からの推論）
- 現実的な方式は次の3つ。(A) FTS5の`trigram`（部分一致ができる。3文字未満の語は一致しない）、(B) アプリ側で分かち書き（`Intl.Segmenter`など）してからFTS5に入れる、(C) 1文字ずつ空白で区切って`unicode61`に入れる（1〜2文字の検索ができる）。LIKEだけの方式は、**D1の「LIKE/GLOBのパターンは50バイトまで」という制限**のため、要件の「検索語は100文字」を満たせない（日本語は1文字3バイトで、前後の`%`を除くと約16文字まで）。（出典4）
- 規模（全体で数十万件）では、FTS5の索引に十分収まる。DBサイズの上限は10GB（Workers Paid）。メッセージの本文が1件数百バイトとして、全体で数百MB以下の見込み（概算。未計測）。
- **FTS5の仮想テーブルを含むD1は、`wrangler d1 export`で書き出せない**（T-05と同じ）。C-127で「定期エクスポートは設けない」と決めているため、バックアップ方針とは衝突しないが、手動エクスポートとマイグレーションの扱いに影響する（6章）。
- 外部の検索サービスは、本調査の範囲では「採用する根拠がない」。Cloudflareの`AI Search`は意味検索とキーワード検索を合わせた別の用途のサービスで、日本語の対応・料金・上限が公式ページから確認できなかった。社内の個人情報を含む本文を外部へ複製するコストもある。
- 推奨案（参考）：まずD1上で**(A) trigramを試し、使えて性能が足りるなら採用**。1〜2文字の検索は別扱いが要る。trigramが使えない、または1〜2文字の性能が足りないなら**(C) 1文字区切り**を検討する。確定には、7章の方法で実測する。

### 4-2. FTS5の`unicode61`と`trigram`

出典3：https://www.sqlite.org/fts5.html（2026-11-02。ページの前半10万文字を読んだ。後半は未読）

- `unicode61`：文字（カテゴリL*・N*・Co）の連続が1つの語になり、空白と記号で区切る。漢字・ひらがな・カタカナはどれも「文字」なので、日本語の文が空白なしで続くと1つの長い語になる。語の途中の一致はできない。（CJKへの言及はなく、規則からの推論。公式ドキュメントに明記はない）
- `trigram`：3文字ずつの並びを索引にし、本文中の任意の部分文字列に一致する。例：`CREATE VIRTUAL TABLE tri USING fts5(a, tokenize="trigram");`。オプションは`case_sensitive`（既定0＝区別しない）と`remove_diacritics`（既定0）。
- trigramの制約：3文字（Unicodeの文字数）未満の検索語は、全文検索では**1件も一致しない**。`LIKE`・`GLOB`は、`remove_diacritics`を使わなければ索引で解けるが、3文字以上の連続した非ワイルドカード文字がないパターンは全件走査になる。`ESCAPE`つきの`LIKE`は索引で解けない。
- `detail`オプション：`detail=none`か`column`にすると索引は小さくなるが、全文検索の語は3文字までになる（`LIKE`・`GLOB`は使える）。
- 導入の版：ページ前半には記載なし。検索結果の要約では「SQLite 3.34.0で追加」とある（出典8。D1が使うSQLiteの版は未確認）。
- 外部コンテンツ表（`content='テーブル名'`）：索引だけをFTS5が持ち、本文は元のテーブルから読む。元の表の追加・更新・削除をトリガーで索引へ伝える必要がある（伝えないと索引がずれる）。既存の行は`'rebuild'`コマンドで索引を作り直す。
- コンテンツなし表（`content=''`）：本文は保存せず、`DELETE`・`UPDATE`は使えない（削除は`'delete'`コマンドで元の値が必要）。`contentless_delete=1`は3.43.0以降で、`DELETE`・`INSERT OR REPLACE`が使える。

### 4-3. 日本語に使える実例

- 出典6：https://dev.to/riversea/fts5-on-cloudflare-d1-cut-my-korean-keyword-search-from-220ms-to-22ms-heres-what-almost-broke-it-3l9p（2026-11-02）。D1上で、韓国語のキーワード約40万行を`unicode61`のFTS5で検索。`LIKE '%語%'`が180〜220msだったのが、FTS5でP50が22ms・P95が45ms未満（390K行）。つまずき：`bm25()`は小さい（負の）値ほど関連が高く、`DESC`で並べて悪い結果を3日間出した／外部コンテンツ表のトリガーを忘れた／韓国語は単語の切れ目が不定で、1形態素の検索で再現率が下がった。**行が短いキーワードで、メッセージ本文とは性質が違う**ため、数値はそのまま当てはめられない。
- 出典7：https://zenn.dev/cybozu_frontend/articles/cloudflare-d1-fts（2026-11-02）。日本語を`Intl.Segmenter`（`ja`・`word`）で分かち書きし、空白でつないで`segments`列だけのFTS5表に入れ、原文は別の`contents`表に`rowid`で結ぶ。D1の組み込みトークナイザは日本語に弱いとしている。つまずき：エクスポートできない／drizzle-ormが仮想テーブルに未対応で生SQLを使った／仮想テーブルでは`ON CONFLICT`が使えず`INSERT OR REPLACE`を使った。性能・件数は書かれていない。trigramの実測もない。
- 出典9（検索結果の要約のみ。原文は読んでいない）：trigramは「東京」「検索」のような2文字の語で一致しないため、日本語では単独では実用しにくいという指摘がある。

### 4-4. 外部の検索サービス

- Cloudflare `AI Search`（https://developers.cloudflare.com/ai-search/ 、2026-11-02）：自動で索引を作り、意味検索とキーワード検索を合わせたハイブリッド検索（既定で有効）、メタデータでの絞り込み、画像・スキャンPDFのOCR、Workersバインディング・REST・MCPで使える。ページには、対応する言語・料金・上限・正式版かどうかの記載がなかった。用途はRAG（文書を意味で探す）寄りで、**1文字・部分一致のような正確な文字列検索の代替にはならない見込み**（推論）。
- その他のサービス（Algolia、Meilisearch、Elasticsearchなど）：今回は調べていない。社内の本文（個人情報を含みうる）を外部へ複製する構成になり、権限の判定（4-1 AC-1・4-2 AC-1〜AC-3）を外部側にも持たせる必要が出る。新しいサービス・ライブラリの追加は利用者の承認が要る（`AGENTS.md`）。
- Cloudflareに、D1とは別の「全文検索のマネージドサービス」があるという記載は、今回確認した範囲では見つからなかった。

## 5. 要件への影響と選択肢

### 5-1. 要件との関係

| 要件 | 影響 |
| --- | --- |
| 検索語1〜100文字、1文字も可（4-1 AC-3、C-90） | 1文字・2文字の検索が通る方式が要る。trigramは3文字未満が一致しない。`LIKE`のパターンは50バイト（日本語で約16文字）までのため、長い検索語を`LIKE`だけで受けられない |
| 見られるメッセージだけ（4-1 AC-1・AC-2） | 全文検索の結果に、権限（参加している部屋・公開チャンネル・案件の参加者）の絞り込みを必ず付ける。検索は索引で候補を出し、権限は結合で絞る形になる。絞り込みの後に件数が減るため、ページ送りの設計が要る |
| 案件の検索で、参加者限定の添付名・内容を漏らさない（4-2 AC-2） | 添付名を同じ索引に入れる場合は、公開可否ごとに分けて持つなど、索引の持ち方で漏れを防ぐ設計が要る（本書の範囲外） |
| 検索のp95が2秒以下（C-88） | 数十万件規模での実測が要る（7章） |
| 本文は`messages.body`のマークダウン原文（データモデル） | 索引に入れる文字列が、`**`・`#`・URLなどの記号を含む。記号を除いた「検索用の本文」を別に持つか、原文のまま入れて許容するかを決める（未決定） |
| メッセージの編集・削除・物理削除の反映 | 索引にも反映する。削除したメッセージ（個人情報を含みうる）が索引に残らないよう、削除のたびに索引からも消す（外部コンテンツ表では元の値を使う`'delete'`が要る） |

| --- | --- | --- | --- | --- | --- | --- |

| 規模での性能の見込み | 索引で解くため速い見込み（要実測） | 速い見込み（要実測） | 速い見込み（要実測） | 全件走査。数十万行で数百msから数秒の見込み（要実測）。読み取り行数が毎回数十万行 | 通常の索引で速い見込み（要実測） | サービス次第 |

- 補足：BとCは「索引に入れる文字列」と「検索語」に同じ変換を通すのが必須。片方だけ変えると一致しなくなる。
- 補足：AとCは、`LIKE`による絞り込みを索引の補助に使う案もある。ただし50バイトの制限と、3文字未満での全件走査に注意する。
- 補足（1〜2文字の補い方）：Aで1〜2文字の検索を通すには、(i)全件走査の`LIKE`（数十万行。性能は実測が要る）、(ii)Cと同じ1文字区切りの索引を併設、(iii)検索結果を絞る範囲（部屋・期間）を必須にして走査量を減らす、などがある。要件の「1文字の検索も認める」を維持する前提で選ぶ。

### 5-3. 推奨案（決定ではない）

- 第1候補：**A（trigram）を試し、3文字以上の検索を索引で解く。1〜2文字の検索は、実測の結果で(i)〜(iii)から選ぶ**。理由は、SQLだけで書けて実装が軽く、部分一致が日本語でそのまま使えるため。
- 第2候補：**C（1文字区切り）**。1文字・2文字を同じ仕組みで解けるのが利点。Aが使えない、またはAの短い検索語の性能が足りない場合に検討する。
- 避けるもの：**D（LIKEだけ）は、検索語100文字を満たせないため、単独では不可**。B（分かち書き）は、分け方の違いで検索漏れが出るため、「メール検索の代替」（4-2）という用途には向きにくい（推論）。F（外部サービス）は、今回の規模では理由が弱い。
- Aの採用はD1でtrigramが動くことが前提。動かなければC、またはB＋Cの併用に切り替える。

## 6. D1のエクスポート制約との関係

出典10：https://developers.cloudflare.com/d1/best-practices/import-export-data/（2026-11-02）

- 公式の記載：「Export is not supported for virtual tables, including databases with virtual tables.」「A running export will block other database requests.」回避策は「仮想テーブルを削除→エクスポート→再作成」。
- 影響：FTS5（A・B・C）を使うと、`wrangler d1 export`が使えない。C-127は「定期エクスポートは設けない。復旧はTime Travel」と決めているため、**バックアップ方針とは衝突しない**。復旧の手段として残るのはTime Travel（Workers Paidで30日。復元は10分間に10回まで。出典2・11）。Time Travelが仮想テーブルを含むDBでも動くかは、公式ページに記載がなく**未確認**（検証環境で、FTS5を含むDBを復元して確かめる）。
- 手動エクスポートが必要になった場合（データの移行・調査）は、仮想テーブルを削除して書き出し、`'rebuild'`で索引を作り直す手順になる。手順の文書化と、検証環境での手順確認が要る。
- マイグレーション：drizzle-ormが仮想テーブルに未対応との報告がある（出典7。記事の日付と現在のdrizzle-ormの対応は未確認）。仮想テーブルとトリガーは、生SQLのマイグレーションで作る必要が出る可能性があり、Skill「data-access-drizzle」の生SQL・マイグレーションのルールに従う。drizzle-kitが仮想テーブルの差分を誤って消さないかも、導入前に確かめる。
- D、Eは通常の表のため、この制約を受けない。

## 7. 社内規模での現実的な方式と、実測の方法

### 7-1. 規模の見積もり

- 登録する社員数は数百人以内、同時利用は50人程度、メッセージは1チャンネル1万件程度・全体で数十万件程度（C-88）。
- 仮に30万件・1件あたり100文字（日本語で約300バイト）とすると、本文は約90MB。trigramの索引は、本文の数倍の大きさになりうる（未計測）。いずれもD1の10GBの上限には遠い。
- 全件走査の読み取りは、毎回30万行。Workers Paidの月250億行の込み量では、月に約8万回の全件走査まで込みに収まる計算（30万行×8.3万回＝250億行）。課金より、応答時間（p95で2秒）が先に問題になる見込み。

### 7-2. 実測の方法（案）

- 準備：Skill「testing」の標準に従い、テスト用のD1（ローカルのminiflareと、検証環境のD1）に、架空の本文（`[PERF_TEST]`のタグつき、`perfuser_%`の投稿者）を30万件入れる。実在の人名・メールは使わない。後始末用の削除スクリプトを一緒に用意し、残数0を確かめる。本番のDBには接続しない。
- 本文の性質：日本語の短文（20〜200文字）、英数字、URL、マークダウンの記号を混ぜる。ヒット件数が多い語（例：「確認」）と少ない語（例：架空の固有名）の両方を用意する。
- 比較する方式：A（trigram）、C（1文字区切り）、D（LIKE）。BはAとCが不足の場合に追加。
- 検索語：1・2・3・10・50・100文字。DはLIKEの50バイト制限で落ちることも記録する。
- 測るもの：応答時間（p50・p95。各検索語で100回以上）、D1が返す`meta`の読み取り行数・書き込み行数、索引を作った後のDBサイズ（`meta.size_after`）、投稿・編集・削除の応答時間と書き込み行数（索引の同期の重さ）、権限の絞り込みを付けたときの変化、ページ送り（50件目以降）の応答時間。
- 先に確かめること（数分で済む）：(1)trigramの仮想テーブルがD1で作れるか、(2)100文字の`MATCH`が通るか、(3)`LIKE`の50バイト制限が実際にエラーになるか、(4)FTS5を含むDBでTime Travelの復元ができるか。
- 注意：ローカルのSQLiteの版は、D1の版と同じとは限らない。最終の判断は、検証環境のD1の数値で行う。

## 9. 次に利用者が決めること（質問の素案）

1. **1〜2文字の検索の扱い**：要件（検索語1文字から）を維持するか。維持する場合、性能の許容（全件走査のp95）か、範囲の必須化（部屋・期間を選ばせる）か、1文字区切りの索引の併設か。
2. **方式の候補の絞り込み**：A（trigram）を第1候補として実測に進んでよいか。trigramが使えない場合にC（1文字区切り）へ切り替えてよいか。
3. **索引に入れる本文**：マークダウンの原文のままか、記号を除いた検索用の文字列か。添付名・案件の件名・TODOも同じ索引に入れるか、別にするか。
4. **エクスポートの扱い**：仮想テーブルのため`wrangler d1 export`が使えないことを許容するか（C-127の「定期エクスポートなし」との整合）。手動エクスポートの手順（削除→エクスポート→再構築）を文書にする前提でよいか。
5. **外部サービス**：今回の規模では採用しない前提でよいか。
6. **実測の実施**：7章の方法での実測を、設計の確定前（#105の中）に行うか、実装の最初のIssueで行うか。
