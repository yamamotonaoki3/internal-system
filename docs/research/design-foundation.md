# 全体設計の方針の下調べ（I-01・I-05・I-09・DBの使い分け・管理者MFAのADR）

## 1. 目的と範囲

- 目的：Issue #105（全体設計の方針）で決める前提として、次の5点の現状と選択肢を整理する。
  1. DBの使い分け（本番D1とローカル・テスト）
  2. IDの形式・一覧のページ送り・索引・未読件数の持ち方（I-01）
  3. セッションの保存と失効、接続元単位の試行制限（I-05・I-09）
  4. 管理者にMFAを求めない理由のADRに書くべき論点
  5. 実装前に必要な npm パッケージと `docs/tech-stack.md` との差
- 範囲：リポジトリ内の文書とひな形の読み取り、Cloudflare公式ドキュメントの確認。環境構築・実機計測・コードの変更はしていない。実際の `.env` の値は読んでいない。
- 決定はしない。「推奨案」は理由つきの参考にとどめる。数値の案は、利用者が決めるまで「案」である。

## 3. 結論（要点）

- DB：本番もローカルもテストも、実質すべて D1（SQLite）で一貫している。PostgreSQL（pg・Hyperdrive）は、ひな形の設定スクリプトに使われない経路が残っているだけで、アプリのコードは D1 だけを向いている。推奨は「D1 のみ」。困る点は、対話型トランザクションがないこと（`db.batch()` だけ）と、1文あたりの束縛値が100個までであること。
- ID：時刻順に並べられるランダムなテキストID（ULID 相当）を推奨する。メッセージの並び順・既読位置の比較・カーソル方式のページ送りが、IDの順序だけでできるため。案件番号・ユーザーID（ログイン用）は別物として扱う。
- ページ送り：カーソル方式（並び替えの値＋IDの組）を推奨する。一覧ごとに、並び順と索引を揃える。
- 未読件数：既読位置（`read_positions`）と、メッセージの数え直し（上限つき）を推奨する。件数のカウンターは持たない。
- セッション：保存先は D1（`sessions` テーブル。データモデルの案どおり）を推奨する。KV は失効の反映が遅く、要件（即時の失効）に合わない。無操作30分・1日の判定は、読み取り時に行い、最終操作時刻の書き込みは間引く。
- 接続元単位の試行制限：D1 の `login_attempts` を推奨する。Workers の Rate Limiting は窓が10秒・60秒だけで、15分の窓を表せない。接続元は `CF-Connecting-IP` を取り、IPv6 は /64 に丸め、秘密の鍵つきでハッシュ化して保存する。
- 要件どうしの緊張が1点ある：「社員ID単位の制限（15分で5回失敗なら15分制限）」は、第三者が他人のIDを使って他人をロックできる。Skill「セキュリティ」は「第三者が他人をロックできないようにする」と定めている（6-5 で扱う）。
- 管理者MFA：要件は「求めない」と決定済み。ADRには、理由（学習用・再認証・監査ログで補う）に加えて、管理者が他人の初期パスワードを見られることなどの残るリスクと、見直す条件を書く。ASVSレベル2との関係の確認が必要（要確認）。
- パッケージ：実装前に決める・入れる必要があるのは、マークダウン（react-markdown・remark-gfm）、絵文字（条件つき）、パスワードハッシュ、ID生成、CSV読み取り、画像の中身判定・位置情報の除去など。`docs/tech-stack.md` は、`package.json` と20件でバージョンが違う。

## 4. 現状のDB構成と、要件で困る点

### 4-1. 現状（リポジトリで確認したこと）

| 項目 | 現状 | 根拠 |
| --- | --- | --- |
| 本番のDB | Cloudflare D1（バインディング `DB`、DB名 `internal-system-db`） | `wrangler.jsonc`、`docs/requirements.md` 6章（「DBはD1を使う」） |
| ローカルの開発DB | wrangler が再現する手元の SQLite。DB用のコンテナは作らない。状態は `.wrangler/state`（Docker では名前付きボリューム） | `docker-compose.yml` の冒頭コメント |
| テストのDB | `@cloudflare/vitest-pool-workers` の中の、Vitest専用の一時D1。`readD1Migrations`で読み、`applyD1Migrations`で適用する | `vitest.config.ts`、`backend/test/apply-migrations.ts` |
| Drizzle | 方言 `sqlite`、ドライバ `drizzle-orm/d1`。マイグレーションは `drizzle-kit generate` で作り、wrangler で適用 | `drizzle.config.ts`、`backend/src/db/database.ts` |
| スキーマ | 例の1テーブル（`sample_users`）だけ。要件のテーブルは未実装 | `backend/db/schema.ts` |

Skill「データアクセス（Drizzle）」の D1 の規則：トランザクションは `db.transaction()` を使わず `db.batch([...])` を使う（途中で失敗すれば全体が取り消される）。「読んだ結果を見て次の文を決める」処理は `batch` にできないため、楽観的ロック（`update ... where version = ?` の更新件数が0なら `409`）と組み合わせる。

### 4-2. 要件で困る点

| 困る点 | 内容 | 影響する要件 | 対応の方向（案） |
| --- | --- | --- | --- |
| 対話型トランザクションがない | 「読む → 判断 → 書く」を1つの塊にできない。二重承認・同時更新（I-04）は、条件つきの1文（`update ... where status = 'pending'` の更新件数を見る、`insert ... select ... where not exists`）で表す | I-04、案件の承認、チャンネル作成の承認 | 1文で条件を持たせる。複数文は `db.batch()`。更新件数0を衝突として扱う |
| `batch` の中で前の文の結果を使えない | 先に作ったIDを次の文で使うには、IDを先に（Workers側で）生成しておく必要がある | 案件＋専用チャンネル＋参加者の同時作成、アカウント登録 | IDをアプリ側で先に作る（5-1 の推奨と相性がよい。連番のIDだとこれができない） |
| 1文の束縛値は100個まで | D1の制限：1クエリの束縛パラメータは100個（公式。出典1）。CSVの100人一括登録（0-1 AC-6）で、1行の列数×行数が100を超える | 0-1 AC-6、一括更新 | 行を小分けにして `batch` に入れる（`batch` 全体は「1クエリ」と数えられる。出典1） |
| 案件番号の連番の採番 | 同時承認での重複防止（設計-12）。欠番は再利用しない（C-122） | 5-3、設計-12 | 採番専用の行を `update ... returning` で増やす。ユニーク制約を最後の守りにして、衝突は `409` とやり直し |
| 全文検索の仮想テーブル | FTS5 の仮想テーブルは `wrangler d1 export` で書き出せない（T-05 の出典2）。方式は T-03 で未調査 | 4-1・4-2、T-03、バックアップ | 検索方式の決定（T-03）の後で、復旧手順に影響を書く。Time Travel は仮想テーブルも戻せるかは未確認 |
| D1の書き込みの直列性 | D1 は1つのDBへの書き込みが直列。50人程度の同時利用（C-88）なら足りる見込みだが、実測はしていない | 非機能1章 | 負荷テスト（k6）で実測する。実測前は「見込み」とする |

### 4-3. 選択肢と推奨

| 選択肢 | 内容 | 良い点 | 悪い点 |
| --- | --- | --- | --- |
| A：D1のみ（推奨） | 本番・ローカル・テストとも D1（SQLite）。ローカルは wrangler、テストはVitestの一時D1 | 現状のひな形と一致。本番と同じ実行エンジン（workerd）で試せる。Time Travel（C-127）が使える。追加の費用・運用が少ない | 対話型トランザクションがない。SQLite の機能の範囲に制約される |
| B：D1＋PostgreSQL（Hyperdrive） | 本番を PostgreSQL にする、または併用する | 通常のトランザクションが使える | 要件（`requirements.md` 6章、C-127 の復旧）が D1 前提。pg は vitest-pool-workers の中で読み込めず、テストが二重になる（`docs/tech-stack.md`）。外部DBの費用・運用が増える |
| C：D1＋Durable Objects（SQLite付き） | 強い一貫性が要る部分（例：厳密な試行制限、リアルタイム）だけ DO に置く | 厳密な制限・直列化ができる | 構成が増える。T-01（リアルタイム）の結論と合わせて決める |

- 推奨：A。必要になった部分だけ C を足す（T-01 の結論と同時に判断）。B は、要件と復旧方式が D1 前提のため、採らない理由を設計文書に1行残す。
- 付随して決めること：ひな形に残る pg 経路（`scripts/local-env.ts` の `DATABASE_URL`・`HYPERDRIVE`、`docs/tech-stack.md` の pg の注記）を、削除するか残すか。これはハーネス管理のファイルを含むため、別Issue（またはハーネス改善の提案）にする。今回は変更しない。

## 5. ID・並び順・ページ送り・索引・未読件数（I-01）

### 5-1. 現状の文書

- データモデルは「IDの形式は要確認（案：推測しにくいランダムな文字列）」とし、型は `text`。`users.id` は「内部ID 再利用しない」（`data-model.md` 29行・181行）。
- ページ送りは API 共通仕様 2.4 に【案】がある：カーソル方式、`limit`・`cursor`、応答は `items`・`nextCursor`。1回の件数は、メッセージ50件・その他20件・最大100件（C-90。決定）。「監査ログのページ送りの方式は実装設計で決める（I-01）」。
- 未読は、`read_positions.last_read_message_id` より新しいメッセージがあるか（決定。Issue #42）。数を保存するか毎回数えるかは未決定（設計-9）。スレッドごとの未読も同じ段階で決める（`data-model.md` 581行）。

### 5-2. IDの形式

| 選択肢 | 例 | 良い点 | 悪い点 |
| --- | --- | --- | --- |
| 連番（`integer` の自動採番） | `1, 2, 3` | 小さく速い。並び順がそのままIDの順 | 推測できる（列挙しやすい）。`batch` の中で先にIDを知れない。件数が外部に分かる。ひな形の `sample_users` が採用 |
| UUID v4 | `3f2b…`（36文字） | 標準。`crypto.randomUUID()` で作れる（パッケージ不要） | 時刻順にならない。索引の局所性が悪い |
| UUID v7 | `0192…` | 時刻順。標準化されている | Workers に標準の生成関数はない（自前かパッケージ） |
| ULID | `01J9…`（26文字、時刻＋乱数） | 文字列の辞書順が時刻順。推測しにくい | 同じ1ミリ秒内の順序は、単調に増やす工夫が必要。Workers では時刻が処理中ほぼ進まない（I/O のときだけ進む）ため、同じ要求の中で連続して作ると同じ時刻になる（公式で再確認） |
| ナノID | `V1StGXR8_Z5jdHi6B-myT` | 短い。推測しにくい | 時刻順にならない |

- 推奨：ULID 相当（時刻部分＋乱数部分のテキスト）を、Workers 側で生成する。理由：
  1. メッセージの「新しい順」、既読位置の「より新しい」、カーソル方式のページ送りが、IDの順序だけで書ける（`messages.id > last_read_message_id`）。
  2. 推測しにくく、`batch` の中で参照するIDを先に作れる。
  3. 同じ要求内で連続して作るときは、直前のIDより必ず大きくする（単調増加）実装にする。
- 実装方式：`ulid` などのパッケージを足すか、Web Crypto で自前の十数行にするか。パッケージの追加は利用者の承認が要る（`AGENTS.md`）。自前なら追加不要。
- ID以外の識別子は分ける：ユーザーIDの文字列（`login_id`。大文字小文字を区別せず一意。0-1 AC-2）、案件番号（形式・採番は C-89）、`direct_key`（DMの2人の組）は、内部IDとは別の列にする。内部IDは変更しない・再利用しない。
- 注意：IDは認可の代わりにならない（X-3）。推測しにくくても、対象のリソースごとに権限を確認する。

### 5-3. 並び順とページ送り

| 方式 | 内容 | 良い点 | 悪い点 |
| --- | --- | --- | --- |
| カーソル方式（推奨） | 最後の行の「並び替えの値＋ID」を印として渡し、`where (key, id) < (?, ?) order by key desc, id desc limit n+1` で続きを取る | 件数が増えても速い。メッセージの追加で行がずれても重複・欠落しない。メッセージの遡り表示（S-05）に合う | 「3ページ目へ直接移動」ができない。総件数は別に数える必要がある |
| オフセット方式 | `limit n offset m` | ページ番号で移動できる | 大きい `offset` は遅く（その行数を読み捨てる）、D1の読み取り行数の課金にも効く。追加・削除でずれる |

- 推奨：全一覧をカーソル方式にそろえる（API 2.4 の【案】と一致）。方針の詳細：
  - 印（`cursor`）は、最後の行の「並び替えの値＋ID」を符号化した文字列にし、入力として必ず検証する（Zod）。壊れた印は `422：VALIDATION_ERROR`。
  - 次があるかは `limit + 1` 件取って判定する。`nextCursor` は続きがなければ `null`。
  - 並び替えの値が重複しうる一覧（名前順、最終返信順、日時）は、IDを第2キーにして順序を一意にする。SQLite は行値の比較（`(a, b) < (?, ?)`）に対応する。
  - メッセージ・返信・監査ログは、ID（時刻順）または発生日時＋IDで並べる。
  - 「ページ番号で移動」が画面の要件になった場合（監査ログなど）だけ、その一覧にオフセットを許す。これは利用者の判断（9章）。
  - 総件数の表示が要る一覧は、別の数え直しのAPIか、上限つき（「100件以上」）にする。

### 5-4. 索引の方針

- 原則：「一覧の絞り込み条件＋並び順」と同じ並びの索引を、一覧ごとに作る。索引は書き込みのたびに更新され、D1 の書き込み行数の課金にも効くため、使われる一覧だけに限る。
- 候補（データモデルの読み取り経路からの案。確定は実装の計画で、`EXPLAIN QUERY PLAN` で確認する）：

| 対象 | 索引の案 | 使う場面 |
| --- | --- | --- |
| `messages` | （ルーム, ID）。スレッド用に（親メッセージ, ID） | ルームの新しい順の一覧、スレッドの返信、未読の数え直し |
| `read_positions` | 主キー（ユーザー, ルーム） | 未読の判定。ユーザーの全ルームをまとめて引く |
| `channel_members` / `case_participants` | （ユーザー, 状態）など | サイドバー、見られる範囲の判定 |
| `audit_logs` | （発生日時, ID）。絞り込み列は使われ方を見て追加 | 監査ログの絞り込みとページ送り。1年保持の掃除（日時で削除） |
| `sessions` | 主キー（ID＝トークンのハッシュ）。（ユーザー）。失効の掃除用に（作成日時） | 認証、全端末の失効、掃除 |
| `login_attempts` | 主キー（種別, キー） | 試行制限 |
| 通知 | （ユーザー, 状態, ID） | 未読の通知 |

- 一意制約が必要なもの（ユーザーIDの正規化値、チャンネル名の大文字小文字を区別しない重複、`direct_key`、案件番号）は、アプリの確認だけでなく、DBの一意索引を最後の守りにする。
- 検索（4-1・4-2）の索引は T-03（日本語全文検索の方式）の結論の後で決める。

### 5-5. 未読件数の持ち方

| 選択肢 | 内容 | 良い点 | 悪い点 |
| --- | --- | --- | --- |
| A：カウンターを保存 | ユーザー×ルームの未読数の列を、投稿のたびに全参加者分更新する | 読むのが速い | 投稿1件で参加者の数だけ書き込む。削除・非表示・アーカイブ・参加の出入りで食い違う。`batch` が重くなる。同じ事実を2か所に持つ（設計-2と同種の問題） |
| B：既読位置＋数え直し（推奨） | `read_positions.last_read_message_id` だけを正とし、未読数は `count(*) ... where room_id = ? and id > last_read` で数える。表示は上限つき（例：99件以上）にする | 持つ事実が1つ。削除・非表示が自然に反映される。IDが時刻順なので、索引（ルーム, ID）の範囲を読むだけ | ルームの数だけ数える。サイドバーで多数のルームを一度に数えると読み取り行数が増える（上限で抑える） |
| C：Bに「ルームの最新メッセージID」を足す | `rooms.last_message_id` を投稿のたびに更新し、「未読があるか」は `last_message_id > last_read` で判定。数は開いたルームだけ数える | サイドバーの印が1行の比較で済む | 投稿ごとに1行の更新が増える。削除時の整合の扱いが要る |

- 推奨：B。サイドバーの「未読があるか」の判定が重い場合だけ、実測してから C を足す。数を画面に出すかは、画面の洗い出しの後に #15 で見直す（設計-9）。
- スレッドごとの未読（C-91）：スレッド単位の既読位置（親メッセージ×ユーザー）を持つ案が自然。テーブルを足すかは実装の計画で決める。
- 上限つきの数え方：`select count(*) from (select 1 from messages where ... limit 100)`。表示は「99+」にできる。

## 6. セッション（I-05）と接続元単位の試行制限（I-09）

### 6-1. ADR-0003（状態：提案）の要約

- 決定：クッキー方式のセッション（サーバーがセッションを持ち、セッションIDを `HttpOnly` のクッキーで運ぶ）。トークン方式（JWT）は採らない。
- 理由：画面とAPIが同じドメイン。JavaScript から読めない。端末ごとのログアウト・パスワード変更や再発行での失効・無効化での失効を、サーバー側で確実に行える。
- 影響：CSRF対策として状態を変える操作で `Origin` を確認する。クッキーは `SameSite=Lax`・`Secure`・`HttpOnly`。保存の構造・失効の処理は決めていない（実装の計画で決める）。見直す条件：専用アプリ、外部システムのAPI利用、複数ドメイン。アプリ内ブラウザ（LINE など）はクッキーの扱いが違う場合があり、実機で確認する。
- ADR の状態が「提案」のままである。#105 で「承認（採用）」にするかは、利用者の判断（9章）。

### 6-2. 要件（セッション）

| 要件 | 出典 |
| --- | --- |
| 無操作30分、またはログインから1日（24時間）で失効 | 0-2 AC-5、X-2 |
| 複数の端末で同時ログイン。ログアウトはその端末だけ | 0-2 AC-6 |
| ログアウトでサーバー側のセッションを破棄 | 0-2 AC-2 |
| パスワード変更で、ほかのセッションを無効 | 0-3 AC-4 |
| 再発行で、その社員のすべてのセッションを無効。無効化でもすべて（案） | 0-3 AC-8、nonfunctional 3章 |
| 再認証から5分は再入力不要 | 0-5 AC-2。`sessions.reauthenticated_at` |
| 初回ログインは、パスワードを変えるまで他の画面・APIが使えない | 0-3 AC-5 |
| セッションのトークンそのものは保存せず、ハッシュを持つ | `data-model.md` 694行 |

データモデルの案：`sessions`（ID＝トークンのハッシュ、ユーザー、ログイン日時、最終操作日時、再認証日時、無効にした日時）。

### 6-3. 保存先の選択肢

| 保存先 | 良い点 | 悪い点 |
| --- | --- | --- |
| D1（`sessions` テーブル。推奨） | 強い一貫性。失効が即時。ユーザーとの結合で無効化・パスワード変更を確認できる。データモデル・要件（`requirements.md` 6章）と一致。Time Travel でバックアップされる | 認証のたびに読み取りが1回。最終操作時刻の更新が書き込みになる（間引く） |
| KV | 読み取りが速く、TTLで自動削除できる | 結果整合：他の場所に変更が伝わるまで約60秒以上かかりうる（出典2）。ログアウト・パスワード変更後の「即時の失効」という要件に合わない。全端末の失効のための一覧が引きにくい |
| Durable Objects | 強い一貫性。1ユーザー1つにして、全端末の失効・試行制限・リアルタイムの接続をまとめられる | 構成が増える。T-01（リアルタイム）の結論に依存。学習用の規模では過剰になりうる |

### 6-4. 失効・端末ごとのログアウト・30分と1日の実現（案）

| 項目 | 方法（案） |
| --- | --- |
| トークン | 暗号学的な乱数32バイト（Web Crypto）を、URLに安全な文字列にしてクッキーで運ぶ。DBにはSHA-256のハッシュを保存する（トークンは高いエントロピーなので、パスワード用の遅いハッシュは不要）。ログイン成功のたびに新しく発行する（固定化攻撃の防止） |
| クッキー | `HttpOnly`・`Secure`・`SameSite=Lax`・`Path=/`。`__Host-` 接頭辞は `Secure` と `Path=/` と `Domain` なしを要求するので使える（ローカルの `http://localhost` は一部のブラウザで扱いが違う。実機で確認する）。`Max-Age` は付けても、失効の正は常にサーバー側 |
| 1日の失効 | `created_at + 24時間` を読み取り時に判定する（操作中でも切る） |
| 無操作30分 | `last_active_at + 30分` を読み取り時に判定する。更新は毎回ではなく、前回の更新から一定時間（例：1分）以上たったときだけ書く。30分の精度が1分ずれても要件上は許容できるかを、利用者が判断する |
| 端末ごとのログアウト | 要求のセッションの行だけに `revoked_at` を入れる（または削除）し、クッキーを消す |
| パスワード変更 | 同じ `db.batch()` で、パスワードのハッシュ更新と「自分以外のセッションの失効」を行う |
| 再発行・無効化 | 同じ `batch` で、対象ユーザーの全セッションを失効 |
| 毎回の認証 | `sessions` と `users` を結合し、失効・期限・ユーザーの状態（無効化）・初回パスワード変更の必要を確認する |
| 再認証 | 成功したら `sessions.reauthenticated_at` を更新。5分の判定は読み取り時 |
| 掃除 | 期限切れ・失効後一定期間のセッションとログイン試行の記録を、Cron Triggers（`scheduled`）で定期的に削除する。保持期間は実装の計画で提案する（`nonfunctional.md` 75行） |
| 書き込みの失敗 | 失効の書き込みが失敗したら成功扱いにせず、エラーとして返す（`AGENTS.md` のエラーの扱い） |

### 6-5. 接続元単位の試行制限（I-09）

要件：ログイン・現在のパスワード確認・再認証は、社員ID単位と接続元単位の別々の制限（C-41、0-2 AC-4）。社員ID単位は15分以内に5回連続失敗で15分制限し、自動解除。接続元単位の上限・窓・解除時間は I-09 で決める。制限中は、アカウントの有無・制限の種類・残り回数を明かさず、共通の案内と `429`・`Retry-After` を返す。手動解除なし。

#### 実現方式の選択肢

| 方式 | 内容 | 良い点 | 悪い点 |
| --- | --- | --- | --- |
| D1の `login_attempts`（推奨） | データモデルの案どおり。種別（account／source）×キーで、失敗回数と制限の終了時刻を持つ | 強い一貫性。15分などの任意の窓にできる。社員ID単位と同じ仕組みで、再認証・パスワード確認にも使える。バックアップ・テストが容易 | 失敗のたびに書き込み。ログイン前の攻撃で行が増える（掃除が要る） |
| Workers の Rate Limiting バインディング | `wrangler.jsonc` の `ratelimits`。窓は10秒または60秒だけ。各拠点ごとの近似値で、結果整合（出典3） | 設定だけで使える。書き込み不要 | 15分の窓を表せない。数が拠点ごとに分かれ厳密でない。公式も「IPアドレスをキーにするのは避ける」と注意している（出典3）。一般のAPIのレート制限（X-8の後半）には向く |
| Durable Objects で自作 | キーごとに1つの DO で数える | 厳密・全拠点で一貫 | 構成が増える（出典3も厳密な制限には DO を勧める） |
| Cloudflare の WAF レート制限ルール | ゾーンの設定で、IP単位の制限 | アプリのコードが不要 | 独自ドメインとゾーンの設定が前提。アプリ内の「共通案内」「アカウント単位」とは別になる。プランの条件は未確認 |

- 推奨：ログイン・パスワード確認・再認証の失敗の制限は D1（`login_attempts`）。一般のAPIのレート制限（X-8の後半。上限値は未決定）は、Rate Limiting バインディングで足りるかを、別に判断する。

#### 接続元情報の取得

- Workers では、リクエストヘッダー `CF-Connecting-IP`（Cloudflareのエッジが付けるクライアントのIP）を使う。`X-Forwarded-For` などクライアントが付けられる値は使わない。公式には、同じゾーンの Worker から別の Worker を呼ぶ場合などで値が変わりうる記載がある（出典4）。本アプリは単一の Worker に直接アクセスするので該当しない見込みだが、構成が変わったら再確認する。
- IPv6：`/64` に丸めたものをキーにする（1台の端末が/64の中でアドレスを変えられるため）。Pseudo IPv4 が有効な場合、`CF-Connecting-IP` が疑似IPv4になる設定がある（出典4）。ゾーンの設定を確認する。
- ローカル・テスト：`CF-Connecting-IP` は付かないので、テストでは明示的にヘッダーを付ける。ヘッダーが無い場合は、既定値で通さず、「接続元不明」という共通のキーに集約するか、エラーにするかを決める（エラーのもみ消しをしない原則）。
- プライバシー（C-41）：生のIPを保存せず、秘密の鍵つきハッシュ（HMAC-SHA256。鍵は Workers の秘密情報。値は利用者が `docs/secrets.md` の手順で入れる）にした値を `bucket_key` に入れる。ログにも生のIPを出さない（Skill「ログ」「個人情報」と合わせて確認する）。
- 共有の出口IP：社内の全員が同じ出口IP（NAT）から使うと、接続元単位の上限が全員に効く。上限を社員ID単位より十分に大きくしないと、1人の失敗が全員のログインを止める。

#### 数値の案（利用者が決める）

| 項目 | 案 | 理由 |
| --- | --- | --- |
| 接続元の窓 | 15分（社員ID単位と同じ） | 実装を共通にできる |
| 接続元の上限 | 失敗30回／15分（社員ID単位の6倍） | 数百人規模の社内の共有出口を想定した初期値。実測と運用で見直す。根拠となる実データはない |
| 解除時間 | 15分で自動解除 | C-41 の社員ID単位に合わせる |
| 成功時 | 社員ID単位は0に戻す（連続失敗の定義）。接続元は戻さない案 | 他人のIDを試し続ける攻撃を、1回の成功で帳消しにされないため |

#### 要件の緊張（確認が必要）

- 社員ID単位で「15分以内に5回連続失敗で15分制限」は、第三者が他人のユーザーIDで5回失敗させれば、その人を15分ログイン不能にできる。Skill「セキュリティ」は「第三者が他人をロックできないようにする」を求める。決定済みの C-41 とどちらを優先するかは、利用者が判断する。軽減策の案：正しい端末（信頼済みクッキー）からのログインは制限の対象外にする、制限中も最終的に正しいパスワードで入れる猶予を設ける（ただし設計が大きくなる）。この調査では決めない。
- 存在しないユーザーIDの試行も数える（`login_attempts` が `users` と外部キーで結ばない設計。`data-model.md` 63行）。このため、ランダムなIDで行を大量に作る攻撃で表が膨らむ。キーの長さ制限と、掃除（Cron）と、接続元単位の上限で抑える。
- 存在しないIDでも、存在するIDと同じ時間・同じ表示にする（0-2 AC-7）。ダミーのハッシュ計算で処理時間をそろえる（T-04 のパスワード計算方式と合わせる）。制限の確認はパスワード計算より先に行い、計算の負荷を攻撃に使わせない。

## 7. 管理者にMFAを求めない理由のADRに書くべき論点

### 7-1. 要件の該当箇所（引用）

- 要件定義書 6章（`docs/requirements.md` 114行、「要件定義で決める機能の項目」の注記）：「管理者のMFAは求めない（管理者の機能がある（B）ため、理由をADRに記録する。0-5）」

- 7章 未決定事項 #8：「（決定済み：管理者のMFAは求めない。理由をADRに記録する。0-5に反映）」

### 7-2. ADRに書くべき論点（整理）

| 論点 | 書く内容（案） |
| --- | --- |
| 背景・前提 | 学習用の社内アプリ（G：止まったときの影響は小さい）。管理者機能あり（B）、個人情報あり（A。本名はログイン後の全員が見られる。C-75）、重要な操作あり（C）。ASVSレベル2。メール送信サービスは使わない（C-39）。アカウントは管理者が発行（自己登録なし） |
| 守る対象と、管理者が持つ力 | 全体管理者ができること：アカウント登録・無効化・再有効化、他人のパスワード再発行（初期パスワードを管理者が一度だけ見る。0-3 AC-7）、権限・ロールの変更、オーナーの任命、監査ログの閲覧、チャンネル・案件の物理削除。再発行したパスワードで、その人としてログインできる（監査ログには残る）ため、管理者のアカウント奪取の影響は全社員分に及ぶ。このことを正直に書く |
| 脅威の想定 | パスワードの推測・使い回し・フィッシング・端末の盗難・社内の悪意。試行制限（C-41）は推測を、MFAはパスワード漏えい後の不正ログインを防ぐ。MFAを求めないと、後者に対する層が1つ減る |
| 代わりに補う仕組み | 再認証（重要な操作の前にパスワード再入力。5分間は不要。C-139）、監査ログ（1年保持、画面から変更・削除できない、書き出し機能なし）、試行制限（社員ID単位・接続元単位）、セッション（無操作30分・1日）、パスワード規則（8文字以上＋大文字・数字・記号。NISTの推奨とは異なることを認識済み。0-3 AC-3）、管理者の自己操作の制限（自分自身のパスワード再発行不可など） |
| 補えない点（残るリスク） | 再認証もパスワードだけなので、パスワードが漏れた攻撃者は再認証も通る。再認証の5分間は、操作の種類によらず再入力が不要（C-139(1)）。監査ログは事後の確認で、防止ではない。唯一の全体管理者の復旧はアプリ外の運用手順（0-3 AC-9）で、手順が未定 |
| 検討した選択肢 | (1) MFAなし（採用）。(2) 管理者だけTOTP（認証アプリ）。(3) 全員にTOTP。(4) パスキー（WebAuthn）。(5) 重要な操作のたびに追加の確認（ステップアップ）。それぞれの利点・費用（登録・紛失時の復旧・テスト・追加パッケージ・秘密の保管）を比較する |
| MFAを採らない理由 | 学習用でリスクの影響が小さい（G）。メール送信を使わない方針で、復旧手段（再設定のコードの送信）が作りにくい。唯一の管理者がMFAを失うと復旧が難しい。実装・テスト・復旧手順の費用が、学習用の範囲を超える。再認証・監査ログで一定の抑止になる |
| ASVSレベル2との整合（要確認） | ASVSのレベル2は、多要素認証に関する要求を含む。「採用する」レベルと「MFAなし」の判断が矛盾しないよう、適用した ASVS のバージョンと該当項目を確認し、不適合なら「逸脱として受け入れる」と明記する。項目の番号は、この調査では確認していない |
| 見直す条件 | 実データ・実際の社員を入れるとき。外部に公開するとき。本番運用に移すとき。全体管理者が複数になる・外部から管理画面に入る運用になるとき。個人情報の範囲が広がるとき。インシデントが起きたとき |
| 影響・運用 | 管理者のパスワードの強度・保管（パスワードマネージャーの利用など）を運用の注意に書く。監査ログの確認を定期的に行う運用を書く |
| 承認 | 決めたのは利用者（7章#8）。ADRの状態（提案／承認）、日付、関係（0-5、nonfunctional 3章、Skill「セキュリティ」）を入れる |

## 12. Workers の時刻の仕様の再確認（Issue #118。2026-11-03）

ULID の単調増加（ADR-0006）の実装前に、公式の記載を確認した。

- 確認できたこと：本番の Workers では、コードの実行中は `Date.now()` が進まず、I/O の後に進む（タイミング攻撃への対策。公式のセキュリティモデルの記載）。ローカル（`wrangler dev`・Vitest の実行環境）では時刻が進む。
- 実装への反映：ULID は、同じ要求の中（同じファクトリ）で単調に増える。同時刻・時計が戻った場合は、直前の乱数に1を足す（`backend/src/lib/ulid.ts`）。別のインスタンス間の順序は保証せず、時刻順になるだけ。
- 未確認：D1・KV・Durable Objects へのアクセスごとに時刻が更新されるか。進む時刻が I/O の完了時刻か開始時刻か。Vitest の実行環境で時刻がどう進むか。
