# T-01 リアルタイム更新の方式（Durable Objects+WebSocket／ポーリング／ロングポーリング／SSE）

## 1. 目的と範囲

- 目的：要件1-9（リアルタイム更新）の方式を、Issue #105（全体設計の方針）で決める前提として、Cloudflare Workers（Hono）+D1+R2、フロントはReactの構成で実現できる方式と、その制限・費用・運用・テストのしやすさ・障害時の挙動を整理する。
- 範囲：Cloudflare公式ドキュメント（developers.cloudflare.com）とWebSearchの調査のみ。試作・課金・実機での計測はしていない。
- 決定はしない。「推奨案」は理由つきの参考にとどめる。
- 読んだ文書：`docs/requirements/01-messaging.md`の1-9、`docs/requirements/nonfunctional.md`、`docs/requirements.md`、`docs/tech-stack.md`、`docs/adr/0003-auth-cookie-session.md`、決定記録C-88（規模・反映時間）。

## 2. 調べた日

2026-11-02。Cloudflareの料金・制限は変わりうるため、決める前・契約前に再確認する。

## 3. 前提（要件側）

- 規模（C-88）：登録する社員は数百人以内、同時に使う人数は50人程度。1チャンネルあたり1万件程度。
- 反映時間（C-88）：他の人の投稿が3秒以内に表示される。
- 1-9 AC-1：同じチャンネル・DMを開いている他の人のメッセージが、再読み込みなしで表示される。
- 1-9 AC-2（案）：案件のTODOの追加・完了・進捗の変更も、同じ案件を開いている他の参加者に反映される。
- 対象は「メッセージ・リアクション・通知」（`requirements.md`の判定F）。未読数は「アプリを開いている間の更新」（1-9の関連：C-65、C-91）。
- 認可（R-38）：見られる範囲（参加している部屋・当事者のDM・参加者の案件）の更新だけを届け、見られない人に内容も存在も届けない。接続の確立時にログインを確認する。
- 認証（ADR 0003）：クッキー方式のセッション（`SameSite=Lax`・`Secure`・`HttpOnly`）。状態を変える操作は`Origin`を確認する（`originCheck`）。画面とAPIは同じドメインで、1つのWorkersにまとめる。
- テスト環境：`@cloudflare/vitest-pool-workers`（0.23.0）。

## 4. 結論（要点）

- 3方式とも、技術的にはWorkers上で実現できる。ただし、Workerの1リクエストは別のリクエストや別のisolateへ直接メッセージを送れないため、サーバーから接続中の利用者へ「今すぐ押し出す」方式（WebSocket・SSE）には、接続を束ねる場所（実質Durable Objects）が要る。押し出しが不要なポーリングだけが、Durable Objectsなしで成り立つ。
- Durable Objects+WebSocket（Hibernation API）：反映は即時に近く、3秒以内の要件に余裕がある。接続の待機中は、ハイバネーションにより時間課金（duration）が発生しない。着信メッセージは20件で1リクエスト相当、発信は課金対象外。数十〜数百人規模では、費用はWorkers Paidの月5ドルに対し無視できる程度と見積もれる（8章）。弱点は、仕組みが増えること（Durable Objectsのクラス、バインディング、マイグレーション設定）、テストの難易度、取りこぼしの復旧を自前で設計する必要があること。
- ポーリング（短い間隔）：実装が最も単純でテストも容易。3秒以内の要件は、間隔2秒程度なら平均1秒・最大2秒+処理時間で満たせる見込み。ただし、同時50人・間隔2秒でも、空振りのリクエストが大量に発生し、Workers Freeの1日10万リクエストは、同時50人でも約半日の利用で超えると見積もれる（8章）。Paid前提なら費用は小さい。D1の読み取りも増える。
- ロングポーリング：Workers単体では、待機中にD1を何度も見るか、Durable Objectsに待たせるかになり、ポーリングの単純さもWebSocketの即時性も中途半端になる。単独で選ぶ理由は見つからなかった。
- SSE：`ReadableStream`を`text/event-stream`で返せば、Workers・Durable Objectsとも実現できる（公式のAgentsドキュメントにも記載）。ブラウザの`EventSource`が自動再接続し、クッキーも標準で送る。ただし、サーバーから利用者への一方向のみで、ブラウザの`EventSource`は6接続の制限（HTTP/1.1）に当たる場合がある。送信は通常のHTTPのPOST（現行のAPI）で行う。押し出しにはDurable Objectsが要る点はWebSocketと同じで、ハイバネーションのような「待機中は課金しない」仕組みの記載は確認できなかった。
- 要件1-9のAC-1・AC-2は、3方式とも満たせる。違いは、反映時間の余裕、取りこぼしの扱い、運用の複雑さにある。
- 推奨案（参考）：Durable Objects+WebSocket（Hibernation API）を「通知だけ」を押し出す使い方にして、メッセージ本体の取得は既存のHTTP API（D1）で行う構成。理由は9章。決める前に検証すべきことは10章。

## 5. 項目ごとの調査結果

### 5-1. Durable Objects+WebSocket（Hibernation API）

出典1：https://developers.cloudflare.com/durable-objects/best-practices/websockets/（2026-11-02）
出典2：https://developers.cloudflare.com/durable-objects/platform/pricing/（2026-11-02）
出典3：https://developers.cloudflare.com/durable-objects/platform/limits/（2026-11-02）

| 項目 | 内容 |
| --- | --- |
| 仕組み | Workerが`Upgrade: websocket`のリクエストをDurable Object（DO）へ転送し、DOが`this.ctx.acceptWebSocket(server)`で受け付ける。DOは同じIDなら同じインスタンスに到達する。1つのDOが複数の接続を持てるので、「部屋ごとに1つのDO」を作り、投稿があったらそのDOに通知して接続全員へ送る、という構成が取れる |
| Hibernation API | `acceptWebSocket`で受け付けると、一定時間イベントがないときDOがメモリから退避され、接続はCloudflareのネットワーク上で維持される。イベントが来るとコンストラクタが再実行され、メモリ上の状態は失われる。接続ごとの情報は`serializeAttachment`（1接続16,384バイトまで。接続が閉じると失われる）か、DOのストレージに置く。`ws.accept()`や`addEventListener`の標準APIではハイバネーションしない |
| ハイバネーションを妨げるもの | アラーム、受信リクエスト、`setTimeout`・`setInterval`。外向きのWebSocketはハイバネーションしない |
| 時間課金 | ハイバネーション中はdurationの課金が発生しない |
| 生存確認 | ping frameには自動でpongを返し、ハイバネーションを妨げない |
| 料金（Paid） | リクエスト：月100万件込み、超過は100万件あたり0.15ドル。duration：月40万GB-s込み、超過は100万GB-sあたり12.50ドル。SQLite：読み取り月250億行込み、書き込み月5,000万行込み、保存5GB-month込み。WebSocketの着信メッセージは20件で1リクエスト相当、接続の確立は1リクエスト、発信メッセージとpingは課金対象外 |
| 料金（Free） | SQLiteを使うDOだけ使える。リクエスト1日10万件、duration1日13,000GB-s。超えるとその種類の操作が失敗する（UTC 0時にリセット） |
| 制限 | 1つのDOあたり、1秒に1,000リクエスト程度のソフトリミット（超えると「overloaded」エラー）。着信メッセージは32MiBまで。CPU時間は1回の呼び出し（HTTPリクエスト・WebSocketメッセージ・アラーム）ごとに既定30秒（最大5分）で、メッセージごとにリセット。SQLiteのDOは1つ10GB。DOのクラスはPaidで500、Freeで100まで。1つのDOが持てる同時WebSocket接続数の公式な上限は、調べたページには記載がなかった（未確認） |
| 更新時の注意 | コードの強制更新（デプロイ）では、接続中のWebSocketが切断されることがある（遅延更新の`max_delay`到達、`immediate`の場合）。クライアントに再接続の処理が必要 |
| スループット | 公式は、複数の論理メッセージを1フレームにまとめる（50〜100ミリ秒ごと、または50〜100件ごと）ことを勧めている |

認証・Originの確認（出典4：https://developers.cloudflare.com/agents/runtime/routing/authentication/、2026-11-02。補足：WebSearchの結果）：

- ブラウザのWebSocketは`Authorization`などのカスタムヘッダーを付けられない。ブラウザは同じドメインへのアップグレード要求にクッキーを付けて送るため、ADR 0003のクッキー方式のセッションと併用できる。クッキーが届くのは、アップグレード要求を最初に受ける**Worker**である（DOではない）。
- 構成の考え方：Worker（Hono）で、(1)`Origin`ヘッダーが自分のドメインと一致するかを確認し、(2)クッキーのセッションをD1で確認して利用者を特定し、(3)その部屋・案件を見る権限があるかを確認してから、DOへ転送する。DOには、確認済みの利用者IDなどを、`serializeAttachment`で接続に付ける。公式のAgentsドキュメントも、「確認はWorkerで行い、DOには確認済みのリクエストだけを通す」ことと、「DOに他の経路から直接届くなら、Workerが付けたヘッダーは信頼できない」ことを述べている。
- `Origin`の確認：WebSocketのアップグレード要求は、ブラウザの同一生成元ポリシーの対象外で、クッキーが付くため、他のサイトのページから接続される（Cross-Site WebSocket Hijacking）おそれがある。`SameSite=Lax`のクッキーは、他のサイトから開始される子リソースの要求（WebSocketを含む）には付かないが、サブドメイン間は同一サイト扱いになるなどの抜けがあるため、`Origin`の確認を併用するのが安全。Cloudflareのプラットフォーム側が`Origin`を検証するかは公式の記載を確認できず、フォーラムでも意見が分かれていた。自前でWorkerの中で必ず確認する前提にする（`originCheck`の対象はPOST等の状態を変える操作で、GETのアップグレードには別途かける必要がある）。
- 権限の変更への追随：接続の確立時の確認だけでは、その後に部屋から外された・退職で無効化された利用者の接続が残る。ADR 0003の「無効化ですべてのセッションを失効させる」案と合わせ、切断の仕組み（DOへの切断指示、または定期的な再確認）を設計する必要がある。

D1との役割分担（考え方。公式の記載ではなく本調査の整理）：

- メッセージ・リアクション・TODOの正本はD1に置く（要件・data-modelのとおり）。DOは「どの接続がどの部屋を見ているか」の管理と、更新があったことの通知の配送だけを担当し、メッセージの内容を持たない（または通知のIDだけを持つ）。
- 投稿の流れ：クライアント→HTTP API（Hono）→D1に保存→DOへ「部屋Xに新着あり（メッセージID）」と通知→DOが接続中のクライアントへ送る。クライアントは通知を受けたら、HTTP APIで差分を取得する（またはDOが内容ごと送る）。
- この構成なら、DOの状態が失われても、データは失われない。
- DO内のSQLite（DOのストレージ）に、直近のイベントを短く持たせる使い方もできるが、正本が二重になるため、必要性は10章で検証する。

### 5-2. ポーリング（短い間隔・ETag／差分）

出典5：https://developers.cloudflare.com/workers/platform/limits/（2026-11-02）
出典6：https://developers.cloudflare.com/workers/platform/pricing/（2026-11-02）

| 項目 | 内容 |
| --- | --- |
| 仕組み | 画面が一定間隔で「最後に受け取ったメッセージID以降」を取得するGETを送る（`?after=<ID>`）。新着がなければ`304`（ETag）または空の配列を返す。Honoの通常のAPIで実装でき、DOもWebSocketも要らない |
| 反映時間 | 平均で間隔の半分、最大で間隔の分だけ遅れる（それにAPIの処理時間）。間隔2秒なら最大でおよそ2秒+α。C-88の3秒以内を満たす見込み。ただし、タブが裏に回るとブラウザがタイマーを間引く（Chromeなど）ため、裏のタブでは遅れうる（ブラウザの一般的な挙動。この調査では計測していない） |
| 費用 | Workersのリクエスト：Paidは月1,000万件込み、超過は100万件あたり0.30ドル。Freeは1日10万件まで。D1の読み取りも毎回発生する（行の読み取り数は、`WHERE id > ?`の索引を使えば小さい） |
| 制限 | Free：HTTPリクエストのCPU時間は10ミリ秒。ポーリング用のAPIはD1の小さな読み取りで足りるが、余裕は小さい。1リクエストの待機時間に上限はない（クライアントが切断しない限り）。サブリクエスト：Freeは1回の呼び出しで50まで |
| 画面側 | React側は、TanStack Queryなどのデータ取得の`refetchInterval`相当で実装できる（採用ライブラリは`docs/tech-stack.md`の方針に従う。本調査では未確認） |
| 弱点 | 空振りのリクエストが多い。部屋ごとに間隔を変える、開いている部屋だけ短くする、非表示のタブでは止める、などの調整が要る。通知（ベルの数）と未読数の更新も、別途ポーリングするか、まとめて1回で取る設計が要る |

### 5-3. ロングポーリング

- 仕組み：クライアントが「after=ID」で要求を出し、サーバーは新着があるまで（例：25秒）応答を保留し、新着があれば即応答する。クライアントは応答のたびにすぐ次の要求を出す。
- Workersでの可否：HTTPリクエストの待機時間に固定の上限は記載されていない（クライアントが接続している間は上限なし。出典5）。待機中はCPU時間を使わない（CPU時間は`fetch()`やD1の待ち時間を含まない。出典5）。ただし、待機中に新着を検知するには、(a)Workerの中でD1を一定間隔で読む（結局ポーリングを内側に移しただけで、D1の読み取りが増える）、または(b)DOに待たせて、投稿のときにDOが起こす（DO必須）、のどちらかになる。
- 評価：(a)は単純なポーリングと比べ、クライアントのリクエスト数が減るだけで、D1の読み取りは減らない。(b)はWebSocket・SSEと同じくDOが要り、HTTPの1リクエストを保留する間のduration課金は、WebSocketのようなハイバネーションの恩恵が公式に確認できない。単独で選ぶ利点は小さい。ほかの方式が使えない環境（社内のプロキシがWebSocketを切る等）でのフォールバックとして考えられる。

### 5-4. SSE（Server-Sent Events）

出典7：https://developers.cloudflare.com/agents/runtime/routing/http-sse/（2026-11-02）
出典8：https://developers.cloudflare.com/durable-objects/examples/readable-stream/（2026-11-02）

| 項目 | 内容 |
| --- | --- |
| 仕組み | `ReadableStream`を`Content-Type: text/event-stream`で返す。サーバー→クライアントの一方向。送信は通常のHTTPのPOST（既存のAPI）。ブラウザの`EventSource`が自動で再接続し、`Last-Event-ID`ヘッダーで最後に受け取ったイベントIDを送ってくれる（ブラウザの標準の仕様） |
| Workersでの可否 | 可能。公式のAgentsドキュメントに、DOの`onRequest()`でSSEのストリームを返す例がある。Workerが取り消したストリームの取り消しは、DOへ伝わる（出典8） |
| 制限 | HTTPリクエストの待機時間に固定の上限はない（出典5）。CPU時間は実際に使った分だけ。ただし、WebSearchでは、Workersの「1リクエストあたり約50ミリ秒のCPU」という古い記述が出た。現行の公式ページ（出典5）では、Freeは10ミリ秒、Paidは既定30秒（最大5分）で、待機時間はCPUに含まれないため、SSEで接続を保持すること自体は問題ない見込み。長時間接続中にどれだけCPU時間を使うか（キープアライブの送信など）は実測していない |
| 切断と取りこぼし | 公式のAgentsドキュメントには、「クライアントが切断するとストリームは終わり、切断中のイベントは失われる」とある。再接続時の取りこぼしは、`Last-Event-ID`と、サーバー側がイベントIDを保持している必要がある（D1の`id > ?`で補える） |
| 認証 | 通常のHTTP GETなので、クッキーのセッションが自動で付く。`Origin`は`EventSource`の要求に付くが、同一生成元の`GET`では付かない場合があり、`Sec-Fetch-Site`などと合わせた確認の設計が要る（未確認） |
| 弱点 | 一方向のため、入力中の表示などのクライアント→サーバーの高頻度の送信には向かない（要件にはない）。HTTP/1.1ではブラウザがドメインあたり同時6接続に制限される（複数タブで問題になりうる）が、HTTP/2・3なら緩い。Cloudflareのエッジは通常HTTP/2・3で終端する見込みだが、利用者側のプロキシ次第で変わる（未確認）。待機中の課金について、WebSocketのHibernation相当の仕組みは確認できなかった |

| 観点 | DO+WebSocket（Hibernation） | 短い間隔のポーリング | ロングポーリング | SSE |
| --- | --- | --- | --- | --- |
| Durable Objects | 必要 | 不要 | 実質必要（(b)の場合） | 実質必要 |
| 反映時間 | 即時に近い。3秒以内に余裕 | 間隔次第（2秒で最大2秒+α）。裏のタブは遅れうる | 即時に近い | 即時に近い |
| 実装の複雑さ | 高い（DOのクラス、バインディング、マイグレーション設定、接続管理、再接続、権限変更時の切断） | 低い（既存のHono APIで足りる） | 中〜高 | 中（DOが要る。再接続はブラウザ任せ） |
| 運用 | DOの設定・デプロイ時の切断への配慮が増える | 負荷の調整（間隔）が運用の中心 | タイムアウトの調整が要る | 接続数・プロキシの確認 |
| 費用（社内規模） | 小さい（8章）。待機中は時間課金なし | Paidなら小さい。Freeは1日10万件を超えうる | ポーリングとWebSocketの中間 | 小さい見込み（待機中の課金は未確認） |
| テストのしやすさ | 低〜中。`@cloudflare/vitest-pool-workers`はDOを直接扱えるAPIがある（5-5）。WebSocketのアップグレードのテスト方法は公式ページに記載がなく要検証 | 高い（通常のAPIのテスト） | 中 | 中（ストリームの読み取りのテストが要る） |
| 切断時の挙動 | 切断を検知して再接続する処理が必要。切断中の更新は届かない | 次の周期で自然に回復する。取りこぼしがない | 再接続で回復する | `EventSource`が自動で再接続。取りこぼしは`Last-Event-ID`で補う設計が要る |
| 取りこぼしの対策 | 再接続時に「最後のID以降」をHTTPで取得して補う | 構造的に起きない（最後のID以降を取るため） | 同左 | 同左（`Last-Event-ID`） |
| 未読数・通知との整合 | 通知も同じ接続で押し出せる。未読数の正本はD1で、押し出しは「再取得せよ」の合図にすると整合を保ちやすい | 未読数・通知も同じAPIで取れる。単純で整合しやすい | 同左 | WebSocketと同様 |
| 双方向性 | あり | なし | なし | なし（送信は通常のHTTP） |
| 認可（R-38） | 接続時にWorkerで確認、権限変更時の切断が要る | 要求ごとに確認される（権限変更に自然に追随） | 要求ごとに確認される | 接続時に確認（権限変更時の切断が要る） |

### 5-5. テストのしやすさ（補足）

出典9：https://developers.cloudflare.com/workers/testing/vitest-integration/test-apis/（2026-11-02）

- `@cloudflare/vitest-pool-workers`には、DOのためのテスト用API（`runInDurableObject()`、`runDurableObjectAlarm()`、`evictDurableObject()`、`listDurableObjectIds()`、`abortAllDurableObjects()`など）がある。ハイバネーション対応のWebSocketは、退避（eviction）時に既定でハイバネーションする（`webSockets: "close"`で閉じることもできる）。
- 取得したページに、WebSocketのアップグレードのテスト方法の記載はなく、`SELF`は`exports`に置き換えられたと書かれている。WebSocket接続をテストの中で張って、メッセージの受信を確かめる方法は、実際に試すまで分からない（未確認）。
- DOを使うコードは、自分のMainのWorkerで定義したDOだけが対象になる。
- E2E（Playwright）では、2つのブラウザの画面を開いて反映を確かめられる（`nonfunctional.md`の方針）。方式によらず可能。反映時間の測定は、方式が決まってから行う。
- ポーリングは、時間を進める（フェイクタイマー）ことでテストしやすい。

## 8. 費用の概算（社内規模）

前提（仮定。実測ではない）：同時50人（C-88）、1日8時間、月22営業日。1人が1日に送る投稿・リアクションを合計100件とする。公式の料金（出典2・6）で計算した。

- 月の合計：Workers Paidの基本料金は月5ドル（出典6）。以下は、これに対する追加分の概算。
- DO+WebSocket：
  - 接続の確立：50人が1日に数回再接続しても、月に数千件程度。
  - 着信メッセージ：50人×100件×22日＝11万件／20＝約5,500リクエスト相当。
  - 通知用のWorker→DO呼び出し：投稿ごとに1回。11万回程度。
  - 合計で月数十万リクエスト程度となり、DOのPaidの月100万件の枠に収まる見込み。durationはハイバネーション中は課金されず、枠（40万GB-s）に収まる見込み。DO分の追加費用はほぼ0。
  - 最悪ケース（ハイバネーションが効かず、常時稼働）：1つのDOが128MBで常時稼働すると、128MB＝0.125GB×86,400秒×30日＝約324,000GB-s／DO。部屋ごとにDOがあり、同時に複数が稼働するなら枠の40万GB-sを超えうる。ハイバネーションが実際に効くか、DOの数を何個に分けるかで変わるため、10章で検証する（128MBは課金計算上の既定値と理解しているが、本調査では公式ページで確認していない）。
- ポーリング（Paid）：
  - 同時50人×間隔2秒×8時間×22日＝50×(28,800÷2)×22＝約1,584万リクエスト／月。込みの1,000万件を超える約584万件×0.30ドル／100万＝約1.75ドル／月。
  - 間隔5秒なら約634万件で、込みの枠に収まる。
  - D1の読み取りは別に発生する。
- ポーリング（Free）：1日あたり同時50人×8時間÷2秒＝72万リクエスト。1日10万件を大きく超える（出典6）。間隔2秒のポーリングはFreeでは成り立たない。
- 数百人が登録されていても、同時に使うのは50人程度（C-88）なので、費用は同時接続数で決まる。同時100人なら、上の数字がほぼ倍になる。
- ロングポーリング・SSE：待機中のduration課金がどうなるか（ハイバネーション相当がない見込み）を、10章で検証する。

## 9. 推奨案（参考）

推奨：**Durable Objects+WebSocket（Hibernation API）を、「更新の合図」を押し出す用途に絞って使い、メッセージ・未読数・通知の中身は既存のHTTP API（D1が正本）で取得する構成**。ポーリングを、フォールバック（WebSocketが使えない・切れている間）として併用する。

理由：

1. 3秒以内の反映（C-88）に余裕があり、接続の切断・再接続の状態も画面に出しやすい（screens.mdの「接続が切れました。再接続しています」）。
2. 正本をD1に置き、WebSocketは「再取得せよ」の合図に絞れば、取りこぼしや切断があっても、再接続時に「最後のID以降をHTTPで取得」するだけで回復でき、未読数・通知とも整合を保ちやすい。
3. Hibernation APIにより、接続の待機中はduration課金が発生しない（出典1・2）。社内規模なら費用は無視できる程度に収まる見込み。
4. 接続時にWorkerでクッキーのセッションと`Origin`と権限を確認でき、ADR 0003の方式と矛盾しない（5-1）。
5. 通知・TODO・未読数など、複数の種類の更新を、同じ接続で扱える。

ただし、次の理由で、単純な方式（ポーリング）を最初の実装にして、DOは後から足す、という進め方も十分に成り立つ。

- 実装とテストが最も単純で、DOのバインディングやマイグレーション設定が要らない。
- 同時50人、間隔3〜5秒なら、Paidで月の費用は微小（8章）。ただしC-88の「3秒以内」は間隔2秒以下を要するため、間隔と要件の整合を決める必要がある。
- WebSocketにあとから切り替える場合も、「最後のID以降を取るAPI」を共通にしておけば、画面側の差し替えで済む。

つまり、どちらを選んでも、「最後のID以降を取るHTTP API」と「再接続時の取りこぼしの補完」を共通の土台にするのが、方式によらず安全だと考える。

## 10. 未確認・決める前に検証すべきこと

1. **WebSocketのテスト方法**：`@cloudflare/vitest-pool-workers`（0.23.0）で、WebSocketのアップグレード要求を送り、DOを介してメッセージを受け取るテストが書けるか。ハイバネーション（退避）後の再開が確かめられるか。最小の試作で確認する。
2. **ハイバネーションの実効性とduration課金**：実際に接続を張ったまま放置したとき、durationがどれだけ課金されるか。通知のたびにDOが起きる構成で、月40万GB-sの枠に収まるか。DOを何個（部屋ごと・全体で1つ）にするかで変わる。
3. **1つのDOが持てる同時WebSocket接続数の上限**：公式のDOの制限のページには記載がなかった。「全員が1つのDOに接続する」設計にできるか。同時50人なら問題になる可能性は低いが、公式の記載は未確認。
4. **`Origin`の確認**：Cloudflare側が自動で検証するかは確認できなかった。Honoのミドルウェアで、GETのアップグレード要求にも`Origin`の確認をかけ、不一致を拒否する実装とテストが必要。`SameSite=Lax`のクッキーがアップグレード要求に付くことの実機確認（LINE等のアプリ内ブラウザを含む。ADR 0003の注記）。
5. **権限変更・無効化時の切断**：部屋から外された・無効化された利用者の接続を、どう切断するか（DOへの指示、またはメッセージ送信のたびに再確認）。
6. **SSEの課金とCPU**：待機中の課金、キープアライブの送信によるCPU時間、HTTP/1.1で複数タブが6接続の制限に当たるか。SSEを選ぶ場合に必要。
7. **ポーリングのD1負荷**：同時50人・間隔2秒でのD1の行の読み取り数と、応答時間（p95で500ミリ秒以下）の実測。
8. **Workers FreeでCPU時間10ミリ秒の影響**：Freeで運用する場合、認可の確認（D1のセッション照会）を含む1リクエストが10ミリ秒に収まるか。DOはFreeでも使えるが、SQLiteのDOだけで、1日のリクエスト10万件・duration13,000GB-sの上限がある（出典2）。
9. **デプロイ時の切断**：DOのコードを更新するとWebSocketが切断されうる（出典1）。再接続の挙動と、デプロイの頻度・時間帯の運用。
10. **iOS Safari・スマートフォンの挙動**：バックグラウンドに回ったときのWebSocket・タイマーの停止。復帰時の再取得の設計（`nonfunctional.md`の要調査#17と関連）。
11. **スクリーンリーダーへの通知**：新着の知らせ方（`aria-live`など）は、方式によらず別途検討（`nonfunctional.md`の要確認）。
12. **参加していない公開チャンネルの更新を受け取るか**（permissions.mdのR-38の未決定事項）：決まると、購読の単位（部屋ごと／利用者ごと）が変わり、DOの設計に影響する。
13. 取得は、WebFetch（ページ内容の要約）とWebSearchの結果による。公式ページの数値は逐語確認ではなく、決める前に原文で再確認する。
