# スパイク：D1のみ構成でのパスワードのハッシュ（PBKDF2・scrypt）と、D1の検索・採番・一括登録

## 1. 目的と範囲

- 目的：Issue #105（全体設計の方針）の決定前に、次の2点を事実で確かめる。
  - 更新が止まったライブラリ（argon2id 1.0.1）を使わず、Cloudflareが公式に用意している仕組み（WebCrypto PBKDF2、`node:crypto`のscrypt）で、OWASPの推奨に沿ったハッシュが実現できるか。
  - D1だけの構成で、全文検索（FTS5 trigram）・案件番号の連番採番・CSVの一括登録が書けるか。
- 範囲：公式ドキュメントの確認と、ローカルのWorkers実行環境（`wrangler dev --local`）での実測。本番へのデプロイ・本番での計測はしていない。
- 決定はしない。「推奨案」は理由つきの参考にとどめる。

## 2. 調べた日

2026-11-02。Cloudflareの仕様は変わりうるため、実装前に再確認する。

## 3. 結論（要点）

- ローカルでは、PBKDF2-SHA256は100,000・210,000・600,000回（さらに1,000,000回まで）がエラーなしで動いた。反復回数の上限は、ローカルでは見つからなかった。一方、**本番にはPBKDF2の反復回数が100,000回までという上限がある、という第三者の報告がある**（公式ドキュメントには記載がなく、未確認）。OWASPの推奨（600,000回）を本番で満たせるかは、本番での確認が必要。
- `node:crypto`のscryptは動いた（N=2^17,r=8,p=1も、N=2^14,r=8,p=5も）。公式ドキュメントは「`argon2`は非対応」と明記する一方、scrypt・pbkdf2は例外に挙げていない。ただしscryptのN=2^17はメモリが約128 MiB必要で、Workersのメモリ上限（isolateあたり128 MB）と同じ大きさのため、本番で動くかは未確認（ローカルでは通った）。
- ローカルでの所要時間は、PBKDF2 600,000回で約190ミリ秒、scrypt N=2^17で約230ミリ秒、scrypt N=2^14,p=5で約110ミリ秒。100件の逐次計算は、PBKDF2 210,000回で約7.0秒、600,000回で約20秒、scrypt N=2^14で約2.6秒、scrypt N=2^17は20件で約4.7秒（100件なら約23秒の見込み）。1回の計算が本番のCPU時間として計上されるため、1リクエストで100件のハッシュは、Paidの既定のCPU時間（30秒）に近い。
- `node:crypto`は、互換性日付が2026-08-04以降なら`nodejs_compat`の指定なしで使える。それより前の日付で指定しないと、起動時に`No such module "node:crypto"`で失敗する。WebCrypto（PBKDF2）はフラグなしで使える。
- D1（ローカル）では、FTS5のtrigramトークナイザの仮想テーブルが作れ、日本語の3文字以上・100文字の`MATCH`が通った。1〜2文字の`MATCH`はエラーにならず0件を返した。`LIKE`のパターンが50バイトを超えると、ローカルでも`LIKE or GLOB pattern too complex`で失敗した。
- 案件番号の連番は、1文の`INSERT ... ON CONFLICT DO UPDATE ... RETURNING`で採番でき、20件を同時に発行しても重複しなかった。CSV100人は、`db.batch`で入れられた（1文に束縛値300個を並べる書き方は、`too many SQL variables`で失敗した）。

## 4. 項目ごとの調査結果

### 4-1. 公式資料の確認（A）

| 項目 | 内容 | 出典 |
| --- | --- | --- |
| `node:crypto` | 「`node:crypto`のAPIは、次の例外を除きすべて対応」。例外は、DSA・DHの鍵ペア生成、`argon2`・`argon2Sync`、`randomUUIDv7`、ed448・x448曲線、FIPSモードの手動切り替え。scrypt・pbkdf2は例外に挙がっていない（個別の言及はなく、対応と読める） | 出典1 |
| `nodejs_compat`の要否 | 互換性日付が2026-08-04以降なら`nodejs_compat`が既定で有効。それ以前は、設定ファイルに`nodejs_compat`の追加が必要。WebCryptoは不要 | 出典1 |
| WebCrypto | PBKDF2は`deriveBits()`・`deriveKey()`・`importKey()`で対応と表にある。反復回数の上限・パスワードのハッシュの推奨・例は、このページにない | 出典2 |
| CPU時間 | HTTPリクエストあたり。Free：10ミリ秒。Paid：既定30秒、最大5分。メモリはFree・Paidとも128 MB（isolateあたり） | 出典3 |
| D1の制限 | 1クエリの束縛値：100個。SQL文の長さ：100,000バイト。`LIKE`/`GLOB`のパターン：50バイト。Workerの1回の呼び出しあたりのクエリ数：Paid 1,000・Free 50（`db.batch()`は1回で1クエリと数える）。`db.batch()`内の文の数の上限は明記なし | 出典4 |
| D1のSQL | FTS5（`fts5vocab`を含む）に対応。trigramトークナイザの記載は、このページにはない | 出典5 |
| OWASPの推奨 | PBKDF2-HMAC-SHA256：600,000回。scrypt：N=2^17,r=8,p=1（代替：N=2^16/p=2、2^15/p=3、2^14/p=5、2^13/p=10、いずれもr=8）。Argon2id：m=19456,t=2,p=1（ほか） | 出典6 |
| PBKDF2の上限（第三者） | 「Cloudflareの`crypto.subtle`が許す最大値は100,000回と思われる」（2024年のブログ）。「Cloudflareは反復回数を100,000回に制限し、変更できない。210,000回を指定すると失敗する」（あるプロジェクトの変更履歴、2026-08-15付。公式ではなく、再確認が必要と本人が注記） | 出典7・8 |

CPU時間への計上について、公式ページに「パスワードのハッシュは何ミリ秒かかる」という記載は見つからなかった。CPU時間は処理に使った時間の合計で、暗号計算もこれに含まれる（出典3の「CPU time」の定義による）。

### 4-2. ローカルでの実測（B）

- 環境：wrangler 4.151.3、`wrangler dev --local`、Node.js v24.22.1、Windows 11。試験コードはリポジトリの外のスクラッチパッドに作成（リポジトリは変更していない）。互換性日付は2026-08-04。
- **ローカルの実測は本番のCPU時間と同じではない**（ローカルの実行はこのPCのCPUで、時間は壁時計。本番の`performance.now()`は処理中に進まない仕様の可能性があり、そもそも計測方法が異なる）。

#### (1) PBKDF2-SHA256（WebCrypto、32バイト出力）

| 反復回数 | 結果 | 所要時間（1回） |
| --- | --- | --- |
| 100,000 | できた | 約26ミリ秒 |
| 210,000 | できた | 約60ミリ秒 |
| 600,000 | できた | 約189ミリ秒 |
| 1,000,000 | できた | 約324ミリ秒 |

- 上限のエラーは、ローカルでは出なかった。第三者が報告する100,000回の上限は、ローカルのworkerdには効いていない（本番だけの制限か、報告が古いかは未確認）。

#### (2) `node:crypto`のscrypt

| N | r | p | 結果 | 所要時間（1回） |
| --- | --- | --- | --- | --- |
| 2^14 | 8 | 1 | できた | 約22ミリ秒 |
| 2^14 | 8 | 5（OWASP代替） | できた | 約110ミリ秒 |
| 2^15 | 8 | 1 | できた | 約45ミリ秒 |
| 2^16 | 8 | 1 | できた | 約107ミリ秒 |
| 2^17（OWASP推奨） | 8 | 1 | できた | 約231ミリ秒 |

- `maxmem`を512 MiBに指定して呼んだ。既定の`maxmem`（32 MiB）ではN=2^17は`memory limit exceeded`になる可能性が高く、今回は既定値では試していない。
- メモリの実測値は取っていない。理論上の必要量は128 × N × r バイトで、N=2^17,r=8なら128 MiB。本番のisolateのメモリ上限（128 MB）に収まるかは未確認で、本番では失敗する可能性がある。N=2^14,r=8,p=5は16 MiB程度（理論値）。
- `nodejs_compat`：互換性日付2026-07-01（フラグなし）では、起動時に`Uncaught Error: No such module "node:crypto"`で失敗した。2026-08-04では指定なしで動いた。

#### (3) 100件を1リクエストで逐次計算

| 方式 | 所要時間（100件） |
| --- | --- |
| PBKDF2 210,000回 | 約7.0秒 |
| PBKDF2 600,000回 | 約20.0秒 |
| scrypt N=2^14,r=8,p=1 | 約2.6秒 |
| scrypt N=2^17,r=8,p=1 | 20件で約4.7秒（100件は約23秒の見込み） |

- いずれもエラーにはならなかった。ただしCSV100人の一括登録で全員のハッシュを同じリクエストで作ると、Paidの既定のCPU時間（30秒）に近づく。Freeは10ミリ秒で、1件のハッシュも収まらない。

#### (4) D1（ローカル）の検索

- 前提：ローカルのD1と本番のD1は、SQLiteのビルド・無効化している機能が異なる可能性がある。ここでの結果は本番の保証にならない。
- 注意：ローカルのD1は、永続化先のパスが長いと`internal error`になった（スクラッチパッドの深いパス）。短いパス（`--persist-to`で指定）にすると動いた。Windows固有のパスの長さの問題の可能性がある。

| 試した内容 | 結果 |
| --- | --- |
| `CREATE VIRTUAL TABLE ... USING fts5(body, tokenize='trigram')` | できた |
| 日本語3文字（`"会議室"`）の`MATCH` | 1件ヒット（正しい） |
| 100文字の`MATCH` | 1件ヒット（正しい） |
| 日本語2文字（`"会議"`）の`MATCH` | エラーなし、0件（本来は1件あるはずだが、trigramは3文字未満を索引で引けない） |
| 日本語1文字（`"会"`）の`MATCH` | エラーなし、0件 |
| 仮想テーブルへの`LIKE '%会議%'`（2文字） | 1件ヒット（`MATCH`でなく`LIKE`なら2文字でも引ける） |
| `LIKE`のパターンが50バイト超（日本語30文字＝92バイト） | エラー：`D1_ERROR: LIKE or GLOB pattern too complex: SQLITE_ERROR`（ローカルでも発生） |
| `LIKE`のパターンが50バイト超（英数字60文字） | 同上のエラー |
| `SELECT sqlite_version()` | エラー：`not authorized to use function: sqlite_version`（D1が一部の関数を禁止している） |

- つまり、1〜2文字の検索は`MATCH`では0件になる。2文字までは`LIKE`で補う設計が考えられるが、その場合も50バイトの制限と全件走査に注意する（日本語は1文字3バイトのため、約16文字までが`LIKE`の上限）。

#### (5) 採番とCSVの一括登録（ローカルD1）

- 連番の採番（1文）：
  - `INSERT INTO seq(year,last) VALUES (2026,1) ON CONFLICT(year) DO UPDATE SET last=last+1 RETURNING last`
  - 20件を`Promise.all`で同時に発行した結果：1〜20がすべて出て、重複なし。
  - 1文で「読む・足す・返す」が完結するため、同時に2つのリクエストが来ても同じ番号にならない。ただしローカルの単一プロセスでの結果で、本番の複数リージョン・複数isolateでの同時実行は未確認（D1は1つのデータベースへの書き込みを直列に処理する仕様）。
- CSV100人の登録：
  - `db.batch()`に100個のINSERT（各3個の束縛値）を渡す方法：できた（100件、約14ミリ秒）。束縛値の上限は1文ごとに判定されるため、100個の制限は問題にならない。
  - 1つのINSERT文に100行分（束縛値300個）を並べる方法：失敗。`D1_ERROR: too many SQL variables`。
  - JSONを1つの束縛値で渡し、`json_each`で展開して1文で100行を入れる方法：できた（100件）。束縛値の制限を回避できる。
- 注意：`db.batch()`は1つのトランザクションとして扱われ、途中で失敗すると全体が取り消される（公式の記載による）。CSV取り込みの「全件成功か全件失敗か」の設計に合う。

## 5. 要件への影響と選択肢（決定はしない）

- PBKDF2：OWASPの推奨（SHA-256で600,000回）は、ローカルでは動く。本番に100,000回の上限があれば満たせない。その場合の選択肢は、(a) 上限内の回数で運用し、OWASPの推奨を下回る理由をADRに記録する、(b) scryptに切り替える、(c) 別の仕組みを探す、の3つ。
- scrypt：OWASPの推奨（N=2^17）はメモリ上限と同じ大きさで、本番で動かない可能性がある。代替構成（N=2^14,r=8,p=5）は16 MiB程度で、メモリの面では安全側。ただしpが5なので計算時間はN=2^17と同程度かかる（ローカル約110ミリ秒）。
- 100件のCSV取り込み：ハッシュ込みで同じリクエストに入れる場合、CPU時間の面で重い。選択肢は、(a) 初期パスワードを作らず、初回にパスワード設定のリンクを送る（取り込み時はハッシュ不要）、(b) 分割して複数のリクエストで処理する、(c) 件数を制限する。
- 推奨案（参考）：まず本番相当の環境（Workersの無料枠ではなく、Paidの検証用Worker）で、6章の確認を行ってから、PBKDF2かscryptかを決める。ライブラリ（argon2id）を使わない方針は、事実の面では実現可能（確認済み）。

## 6. 未確認・不確かなこと（本番での確認手順）

次の確認は、検証用のWorkers（Paid・本番と同じ設定、秘密情報なし）で行う。本番のデータ・実際のパスワードは使わない。

1. PBKDF2の上限：検証用Workerに、反復回数を100,000・210,000・600,000にして`crypto.subtle.deriveBits`を呼ぶエンドポイントを置き、デプロイして呼ぶ。エラーの名前・文言と、`wrangler tail`または管理画面のCPU時間を記録する。
2. scryptの本番での動作：同様に、N=2^17,r=8,p=1と、N=2^14,r=8,p=5を呼び、成功するか（メモリ超過で`Exceeded Memory`などにならないか）と、CPU時間を記録する。`maxmem`の指定が必要かも確かめる。
3. 100件の逐次計算が、1リクエストのCPU時間（既定30秒、`limits.cpu_ms`で引き上げ）に収まるか。
4. D1（本番）で、FTS5のtrigram仮想テーブル、1〜2文字の`MATCH`、`LIKE`の50バイト制限、連番採番の同時実行（2つのリクエストを同時に発行）を同じ手順で確かめる。T-03（日本語の検索）の結果と食い違わないかも照合する。
5. ローカルのD1が長いパスで`internal error`になる件は、プロジェクトの配置先（`internal-system`のパス）で再現するかを確かめる。再現するなら、開発手順に注意を書く。
   - **結果（2026-11-03、Issue #118のAC-7）**：再現しなかった。環境は、OS Windows 11 Home 10.0.26300、wrangler 4.151.3、プロジェクトのルート`C:/Users/3219b/Desktop/RaiseTech/internal-system`（48文字）。D1の保存先`.wrangler/state/test/v3/d1/miniflare-D1DatabaseObject/<64桁のハッシュ>.sqlite`までの絶対パスは174文字。手順は`db:reset:test`→`db:migrate:test`→`npm test`（142件）で、`internal error`は出なかった。意図的に長いパスでの試験はしていない。つまり「この配置先では再現しない」という記録であり、長いパスに置いた場合の動作は未確認のまま。開発手順への注意書きは、現時点では足さない。
6. 第三者の「100,000回の上限」報告（出典7・8）は、公式ドキュメントで裏付けられなかった。Cloudflareのドキュメントの更新を、実装前に再確認する。
