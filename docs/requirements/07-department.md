# 機能7：部署の連絡と所属一覧

部署の専用チャンネル、部署のお知らせ（お知らせ専用チャンネル）、社員の一覧。全体の入口は [要件定義書](../requirements.md)。

## 機能一覧

| # | 機能 | 概要 |
| --- | --- | --- |
| 7-1 | 部署の専用チャンネル | 部署を作ると、公開チャンネルの専用チャンネルと、投稿を制限した公開のお知らせ専用チャンネルを自動で作る。専用チャンネルには部署の社員を自動参加させる（C-95・C-108） |
| 7-2 | 部署のお知らせ | 部署ごとのお知らせ専用チャンネルで扱う（専用画面S-21は廃止。C-108）。自部署のオーナーと全体管理者が投稿し、全社員が全部署のものを読める（C-96）。オーナーは他人の投稿を直接編集・削除できず、依頼と緊急削除の申請になる（C-109） |
| 7-3 | 社員の一覧 | 社員の一覧を見て、部署で絞り込む |

## 機能要件

### 7-1 部署の専用チャンネル

部署を作ると、「部署の専用チャンネル」が公開チャンネルとして自動で作られ、その部署の社員が自動で参加する（C-95）。部署の作成は、[2-1](02-workspace-channel.md)と同じ操作である。部署を作れるのは全体管理者のみ（決定）。作成時に、オーナー（別名：部署管理者）を1人指名できる（指名しなければ、作った全体管理者が自動でオーナーになる。2-1）。部署内だけの機密連絡は、非公開チャンネルを通常の申請（オーナー承認。[2-2](02-workspace-channel.md)）で作る（部署の専用チャンネルは公開のままで、他部署の社員が自分で参加できる点も変わらない。C-95・C-109）。専用チャンネルの名前・説明の規則は【未決定】（C-95）。あわせて、部署のお知らせ用に、投稿を制限した公開の「お知らせ専用チャンネル」も自動で作る（7-2、C-108）

**受け入れ条件**

- AC-1：部署の作成と同時に、その部署の専用チャンネルが公開チャンネルとして自動でできる（申請・承認は要らない。C-95）。同時に、部署のお知らせ専用チャンネル（公開。投稿できるのは自部署のオーナーと全体管理者だけ。7-2）も、専用チャンネルとは別に自動でできる（C-108）。お知らせ専用チャンネルの名前は「{部署名}のお知らせ」で自動作成し、会社内で一意とする（C-105）。自部署の社員は自動参加し、他部署の社員は任意で参加できる（C-111）。説明の規則は【未決定】
- AC-2：専用チャンネルは公開チャンネルであり、他の部署の社員も参加せずに読める（2-3、C-94）。投稿・リアクション・未読・通知は参加者だけが使える。部署の社員は自動で参加する。異動したら、旧部署の専用チャンネルから外れ、新部署の専用チャンネルに参加する（0-1 AC-17、C-30・C-95）
- AC-3：部署を作成できるのは、全体管理者のみ。オーナー・一般のメンバーには、作成の画面もメニューも出ず、APIも使えない

### 7-2 部署のお知らせ

部署のお知らせは、専用画面（S-21）ではなく、部署ごとの「お知らせ専用チャンネル」で扱う（C-108。C-78の専用画面は廃止）。お知らせ専用チャンネルは公開チャンネルで、部署の作成時に自動でできる（7-1）。投稿できるのは、自部署のオーナーと全体管理者（全部署）だけで、この制限は `channels.purpose = announcement` で判定する（専用の列は足さない。C-111）。全社員は参加しなくても全部署のお知らせ専用チャンネルを読める（C-94・C-96）。リアクション・未読・通知・検索は、参加したチャンネルの通常の機能を使う。

編集・削除は、自分の投稿は自分でできる。オーナーは、他人の投稿（他のオーナー経験者・全体管理者の投稿を含む）を直接編集・削除できず、投稿者に編集・削除を「依頼」できる。どうしても緊急に削除が必要な場合は、オーナーが理由を添えて緊急削除を申請し、全体管理者に通知される。全体管理者が承認した場合に限り削除される（C-109。C-107の「オーナーが他人の投稿も直接編集・削除できる」は取り消し）。依頼・緊急削除の対象は、お知らせ専用チャンネルだけとする（ほかのチャンネルへの拡張は別途。C-111）。依頼・緊急削除の具体（API・データ・画面）は【未決定】（別Issue #69で設計）。【C-114で決定（2026-10-28）：API・データ・画面の具体と、取消・重複・理由・印・承認の画面を、AC-6・AC-7に書いた。元の記述は残す】

**受け入れ条件**

- AC-1：お知らせ専用チャンネルに投稿できるのは、自部署のオーナーと、全体管理者だけ。メンバーは、参加していても投稿できない（C-96・C-108）。投稿の制限は、`channels.purpose = announcement` を判定に使い、専用の列は足さない（C-111）
- AC-2：全社員が、全部署のお知らせ専用チャンネルを、参加しなくても読める（C-94・C-96。C-78の「他部署のお知らせは一般社員に表示しない」を改訂）
- AC-3：投稿の編集・削除は、次のとおり（C-109）。①自分の投稿は、自分で編集・削除できる。②オーナーは、他人の投稿を直接編集・削除できない。投稿者に編集・削除を「依頼」できる。③緊急の削除は、オーナーが理由を添えて緊急削除を申請し、全体管理者に通知される。全体管理者が承認した場合に限り削除される。削除の再認証は、[0-5](00-foundation.md)（投稿の削除）による。④依頼（C-111）：アプリ内通知と、投稿に印を出して届ける。応じなかった場合は期限を設けず、必要ならオーナーが緊急削除を申請する。依頼は監査ログに残す。⑤緊急削除（C-111）：対象はお知らせ専用チャンネルのみ（拡張は別途）。全体管理者が承認し、承認・却下に再認証を求める。申請者が全体管理者本人の場合は、通常の削除権限（⑥）で足りるので、承認の仕組みは使わない。⑥全体管理者は、お知らせ専用チャンネルで他人の投稿を直接削除できる（非表示方式。C-57）が、直接編集はできない。編集は投稿者本人だけで、他人の投稿は投稿者に編集を「依頼」する（C-112。C-111の「通常の編集・削除は維持」のうち編集の部分を改訂）。通常のチャンネルでは、他人のメッセージの削除は全ロール不可のまま（R-29）（C-112）。⑦削除後の表示：通常のメッセージの削除（[1-3](01-messaging.md)、C-57）と同じ方式。ただし、お知らせでは「削除されました」と表示する（C-111）。**未決定**（別Issue #69で設計）：依頼・緊急削除の申請のAPI・データ・画面の具体、依頼・申請の取消、通知・印の文言、承認・却下の理由の規則。【C-114で決定（2026-10-28）：依頼・緊急削除の申請のAPI・データ・画面の具体、申請の取消、承認・却下の理由の規則は、AC-6・AC-7に書いた。通知・印の文言は案を書き、未決定のまま残る。元の記述は残す】
- AC-4：お知らせの題名と本文の長さの規則は【未決定】（C-108に伴い再検討。旧：題名1〜100文字・本文1〜5,000文字。C-90。題名の有無を含めて、チャンネルのメッセージの規則との関係を決める）。本文のマークダウンは、メッセージと同じ書式に対応する（[1-5](01-messaging.md) AC-2）
- AC-5：お知らせ専用チャンネルの出し方と部署の変更時の扱い（C-111）。①サイドバーでは、自部署のものを自部署のセクションの先頭に固定し、他部署のものは「他部署」のセクションに出す（C-106）。②部署の無効化（C-103）では、お知らせ専用チャンネルも読み取り専用にする。③部署の異動（C-30）では、自動参加を新しい部署のお知らせ専用チャンネルのものに付け替える
- AC-6：編集・削除の「依頼」（C-114。AC-3②④の細部）。①依頼できるのは、自部署のオーナー（自部署のお知らせ専用チャンネルの他人の投稿。編集・削除の両方）と、全体管理者（他人の投稿の編集の依頼のみ。削除は直接できるため、削除の依頼は要らない。C-112）。メンバーは依頼できない。自分の投稿には依頼できない。②依頼の理由は任意で、最大500文字。③同じ投稿への、同じ種類の未処理の依頼は1件まで。2件目は拒否する。④依頼は取り消せない。期限は設けない。⑤投稿者が自分でその投稿を編集または削除すると、未処理の依頼は自動で「対応済み」になる。「応じない」は記録しない。⑥依頼は、投稿者へのアプリ内通知と、投稿の印で届ける。印は、投稿者・依頼者・自部署のオーナー・全体管理者だけに見せる（投稿者・依頼者は本人として見え、交代・異動後も本人の分は現在のロールを条件にしない）。⑦依頼は監査ログに残す。依頼に再認証は求めない
- AC-7：「緊急削除の申請」と承認・却下（C-114。AC-3③⑤の細部）。①申請できるのは、自部署のオーナー（自部署のお知らせ専用チャンネルの他人の投稿）だけ。全体管理者本人は申請の仕組みを使わず、直接削除する（C-111）。申請に再認証は求めない。②申請の理由は必須で、最大500文字。③同じ投稿への申請中の申請は1件まで。2件目は拒否する。④申請した本人は、承認・却下の前なら取り消せる（申請者本人であれば、申請後にオーナーでなくなっても取り消せる）。承認・却下の後は取り消せない。⑤全体管理者が、申請一覧（S-37）で承認または却下する。承認・却下にだけ再認証を求める（S-26）。却下の理由は任意で、最大500文字。承認までの期限は設けない（期限なし）。⑥承認すると、投稿は非表示（C-57）になり、「削除されました」と表示される（C-111）。⑦投稿者が自分でその投稿を編集または削除すると、申請中の申請は自動で「無効」になる。⑧申請の通知は全体管理者へ、承認・却下の結果の通知は申請者へ、アプリ内通知で届ける。**未決定**（C-114）：通知と印の文言、S-37の絞り込み・並び順の細部、投稿が別の経路（全体管理者の直接削除・緊急削除の承認）で消えたときに残る依頼・申請の扱い、部署の無効化後（読み取り専用）の未処理の依頼・申請の扱い、自動で「対応済み」「無効」にしたことと、緊急削除の申請・取消を監査ログに残すか、取消・無効を関係者へ通知するか

### 7-3 社員の一覧

有効で所属部署がある社員の表示名・部署・内線番号・メールアドレス・ステータスを一覧で見る。部署で絞り込める。無効化済み・所属なしのアカウントは一般社員の一覧に表示しない（C-36）。新入社員は登録時に所属部署を指定する。

**受け入れ条件**

- AC-1：ログインしたメンバーは一覧を閲覧できる。一覧には有効で所属部署がある社員だけを表示し、無効化済み・所属なしのアカウントは除く（C-36）。全体管理者向けのアカウント管理一覧（S-22）は別に扱い、再有効化に必要な無効化済みアカウントを表示できる
- AC-2：一覧に表示する項目は、表示名・部署・内線番号・メールアドレス・ステータスのみ（本名は一覧に出さない。AC-4）。メールアドレスはメール作成リンク（mailto）として表示し、内線番号はリンクにせず番号の表示のみとする（C-79）
- AC-3：部署で絞り込める
- AC-4：一覧の表示名を押す（タップする）と、プロフィールカード（画面S-27）で、その人の本名を確認できる（[0-4](00-foundation.md) AC-10。本名を見られるのは、ログイン後の全員。登録は全体管理者が行い、変更は本人の届出を全体管理者が承認する（C-75））
