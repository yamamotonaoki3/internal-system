# 共通（土台）

アカウントの発行・ログイン・パスワード・プロフィール・重要な操作の再認証・監査ログの閲覧。すべての機能が前提にする土台の機能である。全体の入口は [要件定義書](../requirements.md)。

## 機能一覧

| # | 機能 | 概要 |
| --- | --- | --- |
| 0-1 | アカウントの発行 | 全体管理者が社員のアカウントを登録する（画面・CSV）。無効化と、無効化したアカウントの再有効化 |
| 0-2 | ログイン・ログアウト | ユーザーIDとパスワードでログイン・ログアウトする |
| 0-3 | パスワードの変更・再発行 | パスワードの変更と、全体管理者による再発行 |
| 0-4 | プロフィール設定 | 表示名・アバター画像・ステータスを設定する。表示名を押すと本名を確認できる |
| 0-5 | 重要な操作の再認証 | 重要な操作の前にパスワードの再入力を求める |
| 0-6 | 監査ログの閲覧 | 全体管理者が監査ログを専用ページで閲覧する |
| 0-7 | ロールの編集 | ロールの権限（束ねる権限）を、広げる・狭める。安全のしくみ（再認証・監査ログなど） |
| 0-8 | オーナーの任命・交代 | 全体管理者が、ワークスペース（＝部署）のオーナーを任命・交代する |
| 0-9 | ロールの名前と新規作成（第2段階） | ロールに名前を付ける・ロールを新しく作る。実装の2段階 |
| 0-10 | 全体管理者の引き継ぎ | 現在の全体管理者が、後任を選び、再認証して引き継ぐ。前の全体管理者は一般メンバーに戻る |

## 機能要件

### 0-1 アカウントの発行

全体管理者が、社員のアカウントを登録する。ユーザーID、メールアドレス（会社が支給したもの。全体管理者が確認する）、初期パスワード（全体管理者が入力する）、表示名、所属ワークスペース（＝部署。1人1つ。全体管理者が決める）を登録する。内線番号・役職は任意。画面での登録に加えて、CSVでの一括登録ができる（各行で所属ワークスペースを指定する）。利用者が自分で新規登録することはできない。本名は、全体管理者がアカウント登録時に登録する（決定。「未決定事項」[#21](../requirements.md)。CSVに本名の列を含めるかは未決定）。退職した社員は無効化し、出戻りのときは、全体管理者が同じアカウントを再有効化して戻す

**受け入れ条件**

- AC-1：アカウントを登録できるのは、全体管理者のみ（オーナーは登録できない）。登録時に、所属ワークスペース（＝部署）を必ず指定する
- AC-2：ユーザーIDは、半角英数字と一部記号の3〜32文字。大文字小文字を区別せず、すでに使われているもの（無効化したアカウントのIDを含む）は登録できない
- AC-3：メールアドレスは、全体管理者が確認した状態で登録され、確認した人と日時が記録される（メールを送る認証は行わない）
- AC-4：全体管理者以外（オーナー・一般のメンバー）には、登録の画面もメニューも出ず、APIも使えない
- AC-5：登録の操作が、誰が・いつ・何をしたかとして記録される（監査ログ）。初期パスワードの平文は、画面・ログ・記録に残さない
- AC-6：CSVの登録で1件でもエラー（ID重複・形式不正・所属ワークスペースの指定なし／存在しないなど）があれば、全件を取り消し、エラーの行と理由を一覧で示す。CSVは、各行で所属ワークスペースを指定する
- AC-7：アップロードしたCSVは保存せず、処理の後に破棄する
- AC-8：1人が所属できるワークスペース（＝部署）は1つ（全体管理者は、この制限の対象外。全社ワークスペースは所属の数に数えない。AC-15）。オーナーが「メンバーを削除」（[2-6](02-workspace-channel.md)）すると、その社員の所属が外れて「所属なし」になる。所属なしの間は、どの部署のワークスペースにも入れない（全社ワークスペースには参加したまま。AC-15）。所属なしの社員は、他のワークスペースのオーナーが招待できる（[2-5](02-workspace-channel.md)）。所属の変更（別のワークスペースへの移動）は、全体管理者だけが行う（[0-4](00-foundation.md) AC-7）
- AC-9：退職した社員は削除せず無効化する（ログインできなくなり、過去のメッセージは残る）。無効化できるのは全体管理者のみで、再認証される。オーナーを無効化するには、先に全体管理者がオーナーを交代させる必要がある（[0-8](00-foundation.md)。オーナーは常に1人いるため、交代前のオーナーは無効化できない）
- AC-10：最初の全体管理者は、開発者が手元のスクリプトで作る。公開された初回登録の画面は作らない。それ以降の全体管理者の交代は、[0-10](00-foundation.md) の引き継ぎで行う
- AC-11：無効化したアカウントを再有効化できるのは、全体管理者のみ。オーナー・一般のメンバーには、再有効化の操作もメニューも出ず、APIも使えない
- AC-12：再有効化は重要な操作として、再認証の対象にする（案。「未決定事項」[#23](../requirements.md)。0-5に反映）。失敗すると操作されない
- AC-13：再有効化は、誰が・いつ・誰のアカウントを戻したかとして、監査ログに残る
- AC-14：再有効化は、同じユーザーID（同じアカウント）で戻す。新しいアカウントは作らず、ユーザーIDの重複の規則（AC-2）は変えない。再有効化すると、再びログインできる。再有効化のときのパスワードの扱い（再発行して初回変更を強制するか）、以前の所属・ロール・参加と、過去のメッセージとの関係は未決定（[#23](../requirements.md)）
- AC-15：全社ワークスペース（[2-1](02-workspace-channel.md) AC-5）には、全社員が自動で参加する。全社ワークスペースは、AC-8の「1つのワークスペースにだけ所属する」の所属の数に数えない（所属ではなく、全員が参加する扱い）。このため、AC-8の「メンバーを削除」による所属の解除・所属なし・所属なしの社員の招待は、部署のワークスペースだけに当てはまる。全社ワークスペースからは、誰も外れず、誰も外せない（無効化（AC-9）による場合を除く）。全社ワークスペースは、最初の全体管理者（AC-10）と同じく、初期データの一つとして用意する（投入方法は設計の段階で決める。[2-1](02-workspace-channel.md) AC-9）。新入社員は、アカウントを登録した時点で、自分の部署のワークスペースと全社ワークスペース（名前は「全体コミュニティ」）の両方に参加している状態にする。無効化した社員（AC-9）は、どのワークスペースにも属さない（全社ワークスペースからも外れる）。再有効化のときの所属・参加の扱いは、AC-14のとおり未決定（[#23](../requirements.md)）。詳細は [2-1](02-workspace-channel.md) AC-9

### 0-2 ログイン・ログアウト

ユーザーIDとパスワードでログイン・ログアウトする。ログインは独自の方式のみで、Googleなど外部のログインは使わない

**受け入れ条件**

- AC-1：ユーザーIDとパスワードでログインできる
- AC-2：ログアウトすると、セッションが破棄され、戻る操作でも画面が見られない
- AC-3：ログインしていない人は、どの画面・APIも使えない
- AC-4：5回続けて失敗すると、15分間は試せない。時間が経てば自動で解除され、管理者による手動の解除は作らない
- AC-5：無操作のまま30分でログアウトされ、ログインから1日が経つと、操作中でもログアウトされる
- AC-6：同じアカウントで、複数の端末・ブラウザに同時にログインできる。ログアウトは、その端末のセッションだけが対象
- AC-7：ログインの失敗時は、ユーザーIDとパスワードのどちらが違うかを示さない。無効化したアカウントも同じ表示にする

### 0-3 パスワードの変更・再発行

本人がパスワードを変更できる。初回ログイン時は、初期パスワードの変更が必須。パスワードを忘れたときは、全体管理者が新しい初期パスワードを発行する

**受け入れ条件**

- AC-1：現在のパスワードを入力して、新しいパスワードに変更できる
- AC-2：新しいパスワード欄に確認入力欄があり、表示の切り替えがある。一致しないとAPIを呼ばない
- AC-3：新しいパスワードの長さ・禁止の規則は、Skill「セキュリティ」のC-12〜C-20に従う
- AC-4：変更すると、ほかのセッションが無効になる
- AC-5：初回ログイン時（初期パスワードの発行直後を含む）は、パスワードを変更するまで、ほかの画面・APIが使えない
- AC-6：パスワードを再発行できるのは、全体管理者のみ（オーナーは再発行できない）。再発行は重要な操作として再認証され、監査ログに残る
- AC-7：再発行した初期パスワードの平文は、画面・ログ・記録に残さない（0-1 AC-5と同じ）
- AC-8：再発行すると、その社員のすべてのセッションが無効になる

### 0-4 プロフィール設定

本人が、表示名・アバター画像・ステータスを変更する。表示名は本人が変更できる（決定）。また、表示名を押す（タップする）と、その人の本名を確認できる（小さなカード。画面S-27）。ステータスは、在席・外出・欠席・休暇の4種類で、戻り予定の日時と一言メッセージ（どちらも任意）を付けられる。ステータスは、オーナー（別名：部署管理者）が、自分のワークスペース（＝部署）の社員について代わりに設定することもできる（全体管理者は全部署）。所属ワークスペース（部署）・役職・メールアドレス・内線番号の変更は全体管理者のみが行える（本人・オーナーは変更できない）。変更は監査ログに残る。本名は、登録・変更は全体管理者のみ、見られるのはログイン後の全員（決定。「未決定事項」[#21](../requirements.md)）。本名は個人情報のため、扱い（監査・保存・検索）は未決定（[#22](../requirements.md)）

**受け入れ条件**

- AC-1：本人が、アバター画像とステータス（戻り予定・一言メッセージを含む）を変更できる
- AC-2：アバター画像は画像のみ受け付け、形式・サイズ・位置情報の安全対策を行う（C-63）。形式とサイズの上限は、一般的な値（目安：JPEG・PNG・WebP、2MB以下）を暫定とし、実装前に確定する。未設定のときは、表示名の頭文字を表示する
- AC-3：一言メッセージは文字数に上限があり、表示するときにスクリプトが実行されない
- AC-4：戻り予定の日時を過ぎたら、「戻り予定を過ぎています」と表示する。ステータスは、本人か、代理で設定できる人（AC-5：自分のワークスペースのオーナー、全体管理者）が変更するまで自動では変わらない
- AC-5：オーナーは、自分のワークスペース（＝部署）の社員のステータスだけ、代わりに設定できる。全体管理者は、全部署の社員について設定できる
- AC-6：代理で設定したとき、誰が設定したかが監査ログに残る
- AC-7：所属ワークスペース（＝部署）・役職・メールアドレス・内線番号を変更できるのは、全体管理者のみ（所属の変更、つまり別のワークスペースへの移動は、オーナーはできない。オーナーができるのは、自分のワークスペースからの解除（[0-1](00-foundation.md) AC-8）と、所属なしの社員の招待だけ）。本人・オーナー・一般のメンバーは、変更の画面もAPIも使えない。全体管理者による変更は、誰が・いつ・誰の・どの項目を変更したかとして、監査ログに残る（変更前後の値を残すかは未決定。メールアドレスなどの個人情報は記録に入れない方針と両立させる）。表示名は本人が変更できる（AC-9）
- AC-8：全体管理者がメールアドレスを変更したとき、0-1 AC-3の「確認した人と日時」の記録をどう扱うかは未決定（[#19](../requirements.md)）。変更に再認証（0-5）を求めるかも未決定（#19）
- AC-9：本人が、自分の表示名を変更できる。変更は、ほかの人の画面にも反映される。他の人の表示名は変更できない。表示名は、表示するときにスクリプトが実行されない（AC-3と同じ）。長さ・重複・使えない文字の規則と、変更を監査ログに残すかは未決定（[#25](../requirements.md)）
- AC-10：表示名を押す（タップする）と、その人の本名を確認できる（プロフィールカード。画面S-27）。カードには本名を出し、必要なら部署・ステータスも出す（出す項目は未決定）。カードは、キーボードで開閉でき、閉じるボタンがある
- AC-11：本名を登録・変更できるのは、全体管理者のみ（本人・オーナー・一般のメンバーは、変更の画面もAPIも使えない）。本名を見られるのは、ログイン後の全員（AC-10。ログインしていない人には出さない）。本名の表示・登録・変更を監査ログに残すか、検索の対象にするかは未決定（[#22](../requirements.md)）

### 0-5 重要な操作の再認証

権限の変更（ロールの編集（0-7）・オーナーの任命・交代（0-8）。どちらも全体管理者のみ）・社員の無効化（全体管理者のみ）・無効化したアカウントの再有効化（全体管理者のみ。再認証の対象にするかは案。「未決定事項」[#23](../requirements.md)）・パスワードの再発行（全体管理者のみ）・見せる範囲を広げる操作（チャンネルへの招待、ワークスペースへの招待）・投稿やファイルの削除・チャンネル作成の承認の前に、パスワードの再入力を求める。案件の参加者の追加・削除は、再認証の対象にしない（決定）。アカウントの登録（CSVの一括登録を含む）は対象にしない。管理者のログインに追加の認証（MFA）は求めない（他人のメッセージ・添付を削除できる人は、初期値では本人のみ。「未決定事項」[#11](../requirements.md)）

**受け入れ条件**

- AC-1：対象の操作の前に再認証が求められ、失敗すると操作されない
- AC-2：一度再認証すると、5分間は再入力を求めない
- AC-3：実行した操作が、誰が・いつ・何をしたかとして記録される（監査ログ）
- AC-4：再認証の失敗が続いたときの試行制限は、ログインと同じ（0-2 AC-4）
- AC-5：管理者のMFAを求めない判断は、理由（学習用で、再認証・監査ログで補う）をADRに記録する

### 0-6 監査ログの閲覧

監査ログ（これまでの「誰が・いつ・何をしたか」の記録）は、記録するだけでなく、専用のページで閲覧できる。閲覧できるのは、一番トップの管理者である全体管理者だけ。表示項目と絞り込みの細部は案であり、「未決定事項」[#16](../requirements.md)で確定する

**受け入れ条件**

- AC-1：閲覧できるのは全体管理者のみ。オーナー・一般のメンバーは、画面もAPIも使えない
- AC-2：一覧に、日時・操作した人・操作の種類・対象・結果が出る（案）
- AC-3：期間・操作した人・操作の種類で絞り込め、ページ送りで続きを見られる（案）
- AC-4：監査ログは、画面から変更・削除できない
- AC-5：パスワードなどの秘密の値（平文）は、記録にも画面にも出ない

### 0-7 ロールの編集

権限ベースで設計する。権限（権限ID）の一覧を作り、ロールが権限を束ねる。ロールの中身（どの権限を束ねるか）を、画面で編集できる。権限は、初期値より広げることも、狭めることもできる。ロールごとの権限の初期値は [permissions.md](permissions.md) の権限表（シード）にまとめた。編集の画面は第2段階で作る（0-9）。判定の仕組み（誰が・どの範囲で・どの権限を持つか）は両段階で同じで、第2段階で作り直さない（決定）

**受け入れ条件**

- AC-1：権限の一覧（権限ID）と、ロールが束ねる権限の対応があり、操作の可否は、この対応で決まる
- AC-2：一般メンバーの権限は、初期設定で固定で、編集できない
- AC-3：全体管理者は全権限を持つ。全体管理者のロールは、編集できない
- AC-4：オーナーの権限は、ワークスペース（＝部署）ごとに別々の組を持てる（初期値は権限表の「オーナー」の列）。編集できるのは全体管理者だけで、オーナー自身は自分の権限を変えられない
- AC-5：第2段階で作るワークスペース範囲のロール（0-9）の権限は、ワークスペースごとに編集できる。編集できるのは、全体管理者（オーナーに任命されたワークスペースのみ）と、そのワークスペースのオーナー（自分のワークスペースのみ）
- AC-6：権限を、初期値より広げる操作も、狭める操作もできる
- AC-7：安全のしくみ①：自分が持っていない権限は、他のロールに与えられない
- AC-8：安全のしくみ②：全体管理者のロールは編集できない（AC-3）
- AC-9：安全のしくみ③：編集するときは再認証を求める（0-5）。失敗すると編集されない
- AC-10：安全のしくみ④：編集の内容（変更前後）を監査ログに記録する。AC-7〜AC-10 は、広げる場合も狭める場合も同じ

### 0-8 オーナーの任命・交代

ワークスペース（＝部署）のオーナーを、任命・交代する。オーナーはワークスペースごとに1人だけ。「部署管理者」はオーナーの別名で、部署管理者の任命とオーナーの任命は同じ操作である。ワークスペースの作成時の指名は [2-1](02-workspace-channel.md) に書く

**受け入れ条件**

- AC-1：オーナーを任命・交代できるのは、全体管理者のみ。オーナー・一般のメンバーには、画面もメニューも出ず、APIも使えない
- AC-2：任命・交代は、重要な操作として再認証される（0-5）。失敗すると操作されない。誰が・いつ・誰を任命したかが、監査ログに残る
- AC-3：オーナーは、ワークスペースごとに1人だけで、常に1人いる
- AC-4：交代は、全体管理者が別の人を任命して行い、任命と同時に交代する。前のオーナーは、一般メンバーに戻る。前のオーナーが全体管理者の場合は、そのワークスペースのオーナーの兼任が外れるだけで、全体管理者のままである（導いた内容：権限表の D-1・I-3 から。4.1に明記はない）
- AC-5：全体管理者は、オーナーに任命されたワークスペースでだけ、オーナーを兼ねる。任命されていないワークスペースでは、オーナーの権限を持たない（例外：[2-2](02-workspace-channel.md) AC-8、[5-3](05-case.md) AC-3）。全体管理者は、所属の制限（0-1 AC-8）の対象外で、複数のワークスペースで、任命されたワークスペースだけオーナーを兼ねられる
- AC-6：第1段階では、運営を任せる手段は置かない（オーナーが1人で行う）。任せる手段は、第2段階のロールの新規作成（0-9）で作る
- AC-7：ワークスペースの作成時などにオーナーに指名された社員（全体管理者以外）は、指名と同時に、所属がそのワークスペースに移る（前のワークスペースからは外れる）。全体管理者は、所属の制限の対象外のため、この扱いを受けない
- AC-8：オーナーを無効化するには（[0-1](00-foundation.md) AC-9）、先に全体管理者がオーナーを交代させる必要がある（オーナーは常に1人いる。交代前のオーナーは無効化できない）
- AC-9：全社ワークスペースは、AC-3・AC-4・AC-7の例外である。オーナーは全体管理者で、任命・交代は行わない（[2-1](02-workspace-channel.md) AC-9 ③・AC-6）。全体管理者は1人で確定している（2-1 AC-10）

### 0-9 ロールの名前と新規作成（第2段階）、実装の2段階

ロールは名前を持つ。ロールを新しく作って名前を付けること（例：「経理担当」）もできるようにする。ただし実装は2段階に分ける。

**受け入れ条件**

- AC-1：【第1段階】権限表の初期値を、固定のシードとして入れる。ロール名も初期値で固定する。初期ロールは3つ（一般メンバー・オーナー・全体管理者）
- AC-2：【第1段階】ロールの編集画面・ロール名の変更・ロールの新規作成・編集の安全のしくみ（0-7 AC-9・AC-10）は作らない。「管理役」という名前のロールは作らない
- AC-3：【第2段階】ロールの編集画面（0-7）、ロール名の変更、ロールの新規作成、安全のしくみ（再認証・監査ログ）を足す。ロール名を変更できる人は、第2段階の設計で決める（未決定）
- AC-4：【第2段階】ロールの範囲の種類は、「会社全体」と「ワークスペース（＝部署）」の2つ
- AC-5：【第2段階】会社全体のロールを新しく作れるのは、全体管理者。ワークスペース範囲のロールを新しく作れるのは、そのワークスペースのオーナー。与えられる権限は、作る人自身が持つ範囲まで（0-7 AC-7）
- AC-6：【第2段階】ワークスペース範囲のロールを、メンバーに与える・外すのは、そのワークスペースのオーナー（自分のワークスペースのみ）と、全体管理者（オーナーに任命されたワークスペースのみ）。再認証・監査ログに記録する（第2段階。想定であり未決定）
- AC-7：旧「ワークスペース内の管理役」は、第1段階の初期ロールに含めず、特別な仕組みも作らない。必要なら、第2段階のロールの新規作成で賄う（権限の例は [permissions.md](permissions.md) の 3.10）

### 0-10 全体管理者の引き継ぎ

全体管理者は会社創設者の1人で確定している（[2-1](02-workspace-channel.md) AC-10）。その全体管理者を、後任の社員に引き継ぐ。オーナーの交代（0-8）と同じ考え方で、引き継ぎと同時に後任が全体管理者になり、前の全体管理者は一般メンバーに戻る（決定。権限表 P-2）

**受け入れ条件**

- AC-1：引き継ぎを実行できるのは、現在の全体管理者のみ。オーナー・一般のメンバーには、画面もメニューも出ず、APIも使えない。後任は、有効な社員（無効化したアカウントは選べない）から、現在の全体管理者が選ぶ
- AC-2：引き継ぎは、重要な操作として再認証して実行する（0-5）。失敗すると実行されない。後任の同意は不要である
- AC-3：引き継ぎと同時に、後任が全体管理者になり、前の全体管理者は一般メンバーに戻る。全体管理者は常に1人である（2-1 AC-10）
- AC-4：引き継ぎで、前の全体管理者の「任命されたワークスペースでのオーナーの兼任」（0-8 AC-5）と「全社ワークスペースのオーナーの権限」（2-1 AC-6）は外れ、後任に付く
- AC-5：引き継ぎの実行は、誰が・いつ・誰に引き継いだかとして、監査ログに残る（0-6）
- AC-6：最初の全体管理者は、開発者が手元のスクリプトで作る（0-1 AC-10）。それ以降の全体管理者の交代は、この引き継ぎ（AC-1〜AC-5）で行う
- AC-7：前の全体管理者が一般メンバーに戻るときに、どのワークスペース（＝部署）に所属するか（所属なしか、元の部署か、引き継ぎ時に選ぶか）と、後任が全体管理者になる前に所属していたワークスペースの扱い（全体管理者は所属の制限の対象外。0-1 AC-8。後任の所属が残るのか）は未決定（権限表 4.2 の O-11）
