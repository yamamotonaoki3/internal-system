- 表の左端の「権限ID」は、案である。形は `perm.<領域>.<対象>.<操作>` で、最後の区切りが操作（`create`・`view`・`approve` など）。対象が領域と同じときは対象を省く。本人のもの・他人のものを分ける場合は、操作の後に `.own`・`.others` を付ける。本人のものだけの操作にも `.own` を付ける（例：`perm.notification.own`、`perm.personal_space.manage.own`）。実装の計画で確定する。同じ権限IDで足りる複数の行は、1つの権限IDに集約した（集約した行の備考に「R-xx と同じ権限ID」と書いた）。全ロールが不可で、権限を作る意味のない行は、権限ID欄を「—」とした（「できないことの記載」として行は残す）。権限IDの名前に、旧称（「部署管理者」「管理役」）は含めない（J-2）。R番号は、R-01〜R-73 が3章の表の上から順の連番である（旧番号との対応は末尾の「付録」）。**R-74〜R-76 は Issue #30、R-77 は Issue #40 で追加した行。表の出現順ではなく追加順である**（既存の R-01〜R-73 は振り直さない。R-74・R-75 は3.3、R-76・R-77 は3.6 に置いた）

### 読み方の前提

- オーナー・全体管理者も社員であり、メンバーとしての操作（投稿・閲覧など）は、メンバーと同じ条件でできる（決定。Q-5）
- 「条件付き（参加者のみ）」などの条件は、ロールによらず同じ条件である。参加していないチャンネル・非公開チャンネル・ダイレクトメッセージ・案件・他のワークスペース（＝部署）の専用チャンネルは、全体管理者・オーナーも見られない（決定。Q-15）
- 表はすべてログイン後の操作であり、ログインしていない人は全操作が不可（0-2 AC-3）
- 再認証（[0-5](00-foundation.md)）が必要な操作は、備考に「再認証」と書いた。再認証はロールの違いではなく、操作の性質で決まる
- 旧「管理役」の値は、3章の表には載せていない。第2段階でワークスペース範囲のロールを作るときの例として、「3.10」に残した（決定ではなく例。G-1）。全体管理者は、オーナーに任命されたワークスペースでだけ、オーナーとしての権限を持つ（D-1。「条件付き（オーナーに任命されたワークスペースのみ）」と書いた行）
- 3章の表の「オーナー」の列は、旧「部署管理者」の列と旧「オーナー」の列を1つにまとめたものである（K-2）。2つの列で値が違った行は、「自分のワークスペース（＝部署）」の範囲に合わせて書き、元の2つの値を備考に残した
- 表の「根拠」は、機能の番号と受け入れ条件の番号（例：0-1 AC-3）である。「要件2」は要件定義書の「2. 想定する利用者」、「#n」は要件定義書の「7. 未決定事項」の番号、「Q-n」は4章の論点の番号である
