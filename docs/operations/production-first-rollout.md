## 3. 進め方の考え方と、全体の順（工程 1〜10）

### 順番の考え方（ADR-0032）

- **利用を止めて、migration → 埋め戻し → 検索の索引の作成 → デプロイを、1 回の作業で続けて行う**。古い版（いま本番で動いている版）が、新しい DB の構造の上で動く時間を、数分（migration の終わりからデプロイまで）だけにする
- そのため、前の手順書にあった「古い版が新しい構造の上で動くことの確かめ（前の手順 1-6 の 3・U-5）」は、**行わない**。前の版が新しい構造の上で動くことは、確かめない前提で進める（ADR-0032 の例外）。**ただし、いま本番で動いている版は、戻す先として控える**（手順 1-6）
- 戻すときは、**アプリと DB を、組で戻す**（9 章）。**アプリだけを前の版に戻し、DB を新しい構造のまま残す方法は、使わない**
- **「先に migration だけを当てて、日を空ける」進め方は、しない**。途中で止めざるをえない場合の扱いは、8 章に書いた
- **migration を先に、アプリのデプロイを後に**する。新しいコードは、新しい表・列を前提にするため、先にデプロイすると、それらを使う API が DB のエラーになる
- **検索の索引の作成と、既読の位置の埋め戻しは、利用を止めている間、デプロイの直前に行う**。止めている間は書き込みがないため、作った後に、対象から漏れる投稿が出ない
- **件数を控えてから、すぐに戻す先の時点を控える**（手順 3-1 → 3-2）。利用を止めているため、二つは同じ状態になる。作業の間に件数が増えていたら、止まる

### この進め方が使える条件（ADR-0032。どれか 1 つでも欠けたら、始めない）

1. 本番に、利用者（社員）がいない。作業の間、利用を止めることを、前もって周知してある（手順 2-1）
2. 検証用の D1（#350）で、同じ順の通しのリハーサルを行い、戻せたこと・所要の時間を #160 に記録してある（手順 1-1）
3. 戻す先の時点が、Time Travel の保持期間の内にある（手順 1-4・3-2・8 章）

## 9. 失敗したときの扱いと戻し方

### 戻し方の考え方（ADR-0032）

- **アプリと DB を、組で戻す**。DB は、手順 3-2 で控えた戻す先（0013 を当てる前）に、Time Travel で DB 全体を戻す。アプリは、手順 1-6 で控えた、前の版に戻す
- **アプリだけを前の版に戻し、DB を新しい構造のまま残す方法は、使わない**（前の版が新しい構造の上で動くことを、確かめていないため）
- 戻すと失われるもの：**戻す先より後に本番に書かれたすべてのデータ**（migration・4 本の埋め戻し・検索の索引・工程 9 で作った確かめ用のデータ）。利用を止めているため、社員のデータは失われない見込み。**R2 に上げたファイルは戻らない**（DB の行だけが消え、ファイルが残る。工程 9 の確かめ用の添付）。**逆に、R2 から消したファイルも戻らない**（#270 の添付の削除は、行に印を付けた後に R2 の実体を消す。DB を戻すと、行は戻るが、消したファイルは戻らず、その添付を開くと実体がないため「見つかりません」になる。工程 9 の 9-6 で消した確かめ用の添付も同じ。手順 6-11 で印を付けた添付も、その後に Cron が動いて実体を消した後は、DB を戻しても実体は戻らない）
- 戻す先の期限を過ぎると、戻せない（Time Travel は保持期間の外へ戻せない）
- 逆向きの SQL を流す方法は、**検証していないので、この手順では用意しない**。必要になった場合は、別の Issue で SQL を作り、本番以外でリハーサルしてから、改めて承認を得る
- 前の手順書にあった「当たった分を残して、古い版のまま止める（選択肢 A）」は、使わない（古い版が新しい構造の上で動くことを確かめていないため）。止めて原因を調べる間は、利用の停止を続ける（8 章）

### 途中の migration で失敗したとき（工程 4）

- **1 本の migration の中は、まとめて取り消される**：最後の文で失敗すると、その 1 本の変更と、`d1_migrations` の記録が取り消される（ADR-0025 の、手元の D1 のリハーサルで確かめた事実。本番では未確認）
- **それより前に成功した migration は、当たったまま残る**見込み（wrangler は 1 本ずつ当てて記録するため）。**本番で、失敗した 1 本の後の migration が当たらずに止まるかは、AI は確かめていない**（13 章 U-10）
- 失敗したら：
  1. 何もしない（コマンドを繰り返さない・工程 5 以降に進まない・アプリをデプロイしない）
  2. 出力（エラーの文）を #160 に貼る（秘密情報が含まれていないかを見てから）
  3. 手順 5-1 の `migrations list` で、どこまで当たったかを確かめて #160 に書く
  4. 下の「デプロイの前に戻す」へ進む

### デプロイの前に戻す（工程 4〜8 のどこかで、デプロイの前に止めた場合）

アプリは前の版のまま（デプロイしていない）なので、DB だけを戻せば、アプリと DB の組が、作業の前の状態に戻る。

1. 戻すかどうかを、AI と決め、利用者が承認する。戻さずに、原因を調べてから続ける場合は、8 章の「工程 4〜8」の扱い（利用の停止を続ける・期限の内に再開する）にする
2. いまの日時が、戻す先の期限の内であることを確かめる
   - 違ったら（過ぎている）：止める。戻せない。#160 に書いて、AI と進め方を決め直す
3. 次を実行する（利用者が実行する）

   ```sh
   npx wrangler d1 time-travel restore internal-system-db --bookmark=<戻す先のブックマーク>
   ```

   - `<…>` の部分は、手順 3-2 で #160 に控えたブックマークに置き換える
   - 戻すと、出力に「戻す前の時点のブックマーク」が表示される。これも #160 に控える（戻したことを取り消すときに使う。T-05）
   - 戻している間は、処理中の要求が取り消される（T-05）
   - 違ったら（エラーになる）：止める。出力を #160 に貼り、AI に相談する。利用の停止は続ける

4. 手順 5-1 の `migrations list` を実行する
   - 見るべき結果：0013 から、2 章の一覧の最後までが、未適用に戻っている（手順 1-5 と同じ）
   - 違ったら：止める。#160 に書いて AI に相談する。利用の停止は続ける
5. 手順 3-1 のコマンドで件数を数える
   - 見るべき結果：元の件数（手順 3-1）と**同じ**。戻す先は埋め戻しの前なので、埋め戻しの後の基準とは比べない
   - 違ったら：止める。#160 に書いて AI に相談する。利用の停止は続ける
6. 画面で、ログインと、既存のチャンネルのメッセージが読めることを確かめる（古い版が、古い DB の上で動いていること）
7. #160 に、戻した理由と結果を書く。利用の再開を周知してよい（作業の前の状態に戻ったため）。**ここで終わる**。やり直すときは、原因を直し、利用者が改めて承認してから、**手順 1-1 から、すべてやり直す**（前回の工程 1 の記録は使わない。原因を直したことで、出す版・手順書・リハーサルが変わりうるため。8 章の「工程 1 で止めた場合」の飛ばし方は、ここでは使わない）。元の件数と戻す先も、工程 3 で控え直す

### デプロイの後に戻す（工程 8 の手順 8-3 の後、工程 9 で問題が出た場合）

新しいコードは、0013 以降の表・列を前提にし、前の版は、新しい構造の上で動くことを確かめていない。**アプリと DB の両方を、間を空けずに戻す**。利用の停止を続けたまま行う。

1. 戻すことを、AI と決め、利用者が承認する。工程 9 で作った確かめ用のデータは失われる
2. いまの日時が、戻す先の期限の内であることを確かめる
   - 違ったら（過ぎている）：止める。DB を戻せない。アプリも戻さない（前の版が新しい構造の上で動くことは確かめていないため）。#160 に書いて、AI と進め方を決め直す。利用の停止は続ける
3. 手順 1-6 で、前の版が控えてあることを確かめる
   - 違ったら（控えにない）：止める。アプリを戻せないため、DB も戻さない（新しい版が古い DB の上で動かなくなるため）。扱いは #348 で決まる（13 章 U-5）。#160 に書いて、AI と相談する。利用の停止は続ける
4. **アプリを前の版に戻す**：手順 1-10 で決めたコマンドで、手順 1-6 で控えた版に戻す（**#348 で決まる**。13 章 U-8）。戻した版の ID を #160 に書く
   - 違ったら（戻せない）：止める。DB は戻さない。#160 に書いて AI に相談する。利用の停止は続ける
5. **続けて、DB を戻す**：上の「デプロイの前に戻す」の手順 3〜7 を行う

## 10. 所要の見込みと、利用者への影響

- **所要の時間は、手順 1-1 のリハーサルで測った時間と、本番の件数（手順 3-1）で見積もる**。AI は本番の件数を知らない
  - 時間がかかりうるのは、既存の大きな表を読む次のもの：0016（`rooms` の全行のコピー）・0013（`users` の索引 2 つ）・0020（`messages` の索引 2 つ）・0027（`audit_logs` の索引 3 つ）・既読の位置の埋め戻し（参加者×部屋ごとに最新のメッセージを探す）・検索の索引の作成（`messages` の件数に比例する）
  - ほかの migration は、空の表と索引を作るだけで、時間はほとんどかからない見込み
  - D1 の 1 回の実行の時間の上限に当たるかは、リハーサルと件数を見てから判断する（13 章 U-11）
- **作業の間は、利用を止める**（周知。手順 2-1）。止めている間も、古い版は要求に応える
  - migration・索引の作成の間は、開いたままの画面の読み取りが、一時的にエラーになりうる
  - 書き込みが通ると、戻したときに消え、埋め戻しと索引の対象から漏れる。そのため、件数の見比べ（手順 3-3・5-4・8-1・9-0）で、比べる先（手順 3-1 の表）と違ったら止まる
  - ログインしていない要求の、状態を変える操作は、Origin の検査（`originCheck`）と認証で断られる
  - 毎日 03:17（日本時間）の Cron の時刻は、作業の時間に含めない（手順 2-2）
- **戻すことになった場合**：戻している間は、処理中の要求が取り消される。戻すのにかかる時間は、リハーサルで測る（13 章 U-12）
- **利用者から見た変化**：デプロイの後に、案件・TODO・添付・DM・通知・検索などの新しい機能が使えるようになる
