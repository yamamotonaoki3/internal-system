# プロジェクト固有のルール

このプロジェクトだけに当てはまるルールを書く。ハーネスが管理するファイル（`AGENTS.md`・Skill等）には書き足さない。
- ハーネスの改善提案の作成先は https://github.com/ysteam0117/harness とする（利用者指定）。AGENTS.mdの事前確認と秘密情報を含めない規則は維持する。

## 書く前に確かめること

| # | 問い | はい |
| --- | --- | --- |
| 1 | このアプリの業務や中身（扱うデータ・画面・取引先・お客さまの要望）を知らないと、書けないルールか？ | ここに書く |
| 2 | 特定の技術を使うときにだけ必要なルールか？ | ハーネス（技術プロファイル）への改善の提案にする |
| 3 | どのアプリでも守るべきルールか？ | ハーネス（共通仕様）への改善の提案にする |

迷ったら、ここに書いてよい。ほかのアプリでも通用すると分かったら、ハーネスの改善の提案（Issueテンプレート「ハーネスの改善の提案」）にし、ハーネスに取り込まれたらここから消す。

## このプロジェクトのルール

<!-- 例：レシピの材料は最大50件まで -->

- 要件定義書は、`docs/requirements.md`（目次・全体像・全体の未決定事項）と、`docs/requirements/`（機能ごとの詳細・非機能要件・データモデル）に分けて書く。機能の追加・変更は、該当する機能ファイルを直し、番号付きの受け入れ条件（AC-n）を維持する。受け入れ条件は、機能ごとの見出しの下に箇条書き（`- AC-n：…`）で書く。他の文書から参照するときは「0-2 AC-4」のように機能番号を付ける。ER図は Mermaid の erDiagram で書く
- Issueは、実装する機能の単位で立てる。フロントエンド・バックエンド・DBなどの作業領域では分けない（ADR 0002）。Skill「実装の進め方」の『作業領域ごとに子Issueに分ける』『対象の作業領域を書く』は適用しない。
- 一覧APIのページ送りは、`backend/src/lib/cursor.ts`（`cursorQuerySchema`・`afterCursor`・`toPage`）を使う。OFFSETは使わず、件数は`PAGE_LIMIT`に従う（メッセージ50・その他20・最大100）
- 監査ログは、`auditLogInsert`が返す文を、業務の更新と同じ`db.batch([...])`に入れて書く（単独で実行しない）。`detail`には、件数・変更前後の識別子や状態・失敗の分類などの概要だけを入れ、入れ子にしない。本文・氏名・メール・電話・CSVの行の値・秘密情報は入れない
- 本番の権限IDの一覧とResolverは、`createAuthorizer`を呼ぶ1か所で組む。認可の拒否は、`createAuthorizer`の`authorize`が`logger.audit`で必ず記録する（`logger`は必須）。拒否の記録を省く書き方をしない
- 開発・テスト用の使い捨ての秘密の値（ADR 0014）：AIが書いてよいのは、乱数で作った値を`.env.development`・`.env.test`に入れる場合だけ。本番（`wrangler secret put`・GitHub Secrets）と実在の認証情報は利用者が入れる。値を画面・会話・ログに出さず、ファイルを読まない（項目名だけを`npm run env:check`で確認する）。動作確認で使った値は確認後に作り直す（開発・テスト用の鍵だけ。本番と実データの鍵を入れ替えない規則は`docs/secrets.md`のとおり変わらない）。安全装置に止められたら回避せず、利用者に依頼する
- 画面のスタイル（ADR 0015）：色・文字・余白などの基準値は `frontend/src/styles/index.css` の `@theme` の1か所だけで定義し、色は用途で名付ける（色を足すときは `tokens.test.ts` の組み合わせにも足す）。画面で素の `button`・`input` にクラスを書かず、`frontend/src/components/` の共通部品を使う（部品は `className` を受け取らない）。クラス名は動的に作らず、任意の値（`[...]`）は使わない。`style` 属性と `<style>` は使わない（本番のCSPは `style-src 'self'`）。フォーカスの輪郭は `index.css` の1か所で決める。詳しくは `docs/design/style-foundation.md`
- 共通レイアウト（S-01。Issue #121）：サイドバー・下部メニューの固定リンクは `frontend/src/features/app-shell/navigation.ts` の配列だけに足し、データを取るセクションは機能の部品を `SidebarNav.tsx` の決まった位置に1行で差し込む。画面のルートは `frontend/src/App.tsx` のレイアウトルートの子に足す。管理項目は `requires`（権限ID）を付け、権限による出し分けは表示の制御であり認可ではない（認可はサーバー側で行う）。動かない仮の項目は置かない。詳しくは `docs/design/app-shell.md`
- 予約取引先 `INT` の初期登録（Issue #192）：業務要件5-7 AC-9を満たすため、初期登録だけの専用migrationを1本に限って手作成する。既存migrationは変更しない。通常のDDL変更を含む他のmigrationは生成手順を使う。本番への適用には別途利用者承認が必要（ADR-0018）。
- 取引先APIの利用者単位レート上限（Issue #192）：読み取りAPI3操作の合算は固定UTC 1分あたり120回、登録・改名・無効化の3操作の合算は30回。超過時は429と `Retry-After` 秒数を返し、計数DB障害時は503で拒否する。詳細は要件API共通仕様X-8を正とする。
- 複数の文の `db.batch` で前提を確認する書き方（Issue #196。利用者承認 2026-11-09）：D1には対話型トランザクションがなく、`db.batch` は途中の文が失敗すると全体を取り消す。読んだ事実が変わっていないこと（版の一致など）は batch の先頭近くで、不変条件（オーナーが部署ごとに1人など）は batch の最後で、`CASE WHEN 条件 THEN 値 ELSE NULL END` を NOT NULL の列に入れる更新文で確かめる（条件が崩れると NOT NULL 違反で全体が失敗する）。失敗は、Repository が制約の表と列の名前で専用エラーに変換し、Service が `AppError` にする。**未知のDBエラーは握りつぶさず、そのまま再送出する**。SQLiteの一意制約は文単位で判定されるため、同じ batch の中で名前を入れ替える更新は、自分自身と衝突しない順序に並べる。例は `backend/src/db/department.repository.ts`（`assertStatement`・`bumpVersion`・`translateError`）。
- 一度だけ表示する認証情報（初期パスワード。Issue #199）：フロントエンドでは、TanStack Queryの`useMutation`に載せない（結果がMutationCacheに残るため）。呼び出しを`onSubmit`で直接awaitし、受け取った値は表示する画面の`useState`だけに置く。localStorage・sessionStorage・URL・画面遷移の`state`に入れない。APIの応答には`noStore`を付ける。詳細は`docs/design/accounts.md`
- 全社連絡の補完（Issue #200）：全社連絡（`purpose=company_general`）の初期データだけの専用migration（0011）を1本に限って手作成する（3本目の例外。ADR-0022）。既存migrationは変更しない。本番への適用には別途利用者承認が必要。チャンネルの一覧・詳細・参加APIのレート制限は、上限がX-8で決まっていないため入れず、別Issueで扱う。
- 列追加でテーブルの作り直しが生成されたとき（Issue #130。利用者承認 2026-11-11。ADR-0024）：既存テーブルへの列追加で `npm run db:generate` がテーブルの作り直し（`__new_` テーブルの作成・全行コピー・DROP・RENAME）を生成したら、生成された migration の SQL を、`ALTER TABLE … ADD COLUMN …`（列定義に DEFAULT・NOT NULL・CHECK・REFERENCES を含む）と `CREATE INDEX` に書き換える。書き換えるのはこの SQL だけで、`meta/<n>_snapshot.json` と `_journal.json` は生成されたものを使い、既存の migration は変えない。書き換えたあとに `npm run db:generate` を再実行し、差分が出ないことを確かめる。書き換えた migration の先頭に、コメントで ADR の番号（0024）を書く。この場面には利用者の確認なしで適用する。列の追加以外で作り直しが生成されたときは止まって確認する。本番への適用は別途利用者が承認する。最初の適用は migration 0013
- 「最後のID以降」で読む一覧（Issue #201）：新着を`after`（直前に見たID）以降で取る一覧は、`cursor.ts`の`afterIdQuerySchema`・`toAfterIdPage`を使う。取りこぼしを防ぐため、書き込む側は「同じ部屋では、コミットの順にIDが増える」を、時計やULIDの単調性に頼らず、DBの条件付きの`INSERT … SELECT`（挿入するID以上のIDがないこと）で保証する。0行のときは原因を読み分け、IDだけが原因なら最大より大きいIDで作り直して再試行する（上限を超えたら503）。この保証はD1が書き込みを直列に実行することに依存し、読み取りレプリカ（Sessions API）は使わない前提。詳細は[messages.md](design/messages.md)。メッセージの投稿のレート制限は、上限がX-8で決まっていないため入れず、別Issueで扱う。

## 既定の方針（AI が質問せずに適用する判断。Issue #214）

Issue の実装を AI が連続して進めるとき、同じ種類の判断を毎回利用者に聞かないための既定値である。利用者が承認した判断（Issue #206 の決定、ADR-0021・0022）を一般化したもので、AGENTS.md の優先順位（利用者の指示 ＞ AGENTS.md ＞ Skill）のうち、AGENTS.md・Skill に反しない範囲の既定値として働く。planner・test-writer・implementer は、次の 1〜7 に当てはまる判断を質問せずに適用し、計画の「利用者に確認すべき点」には含めない。各方針の「利用者に戻す条件」に当てはまるときは、適用せず止まって利用者に確認する。

1. **既存データの補完**
   - 方針：migration にせず、`backend/db/scripts/` にべき等な SQL を 1 ファイルで置く。DB テストがそのファイルを読んで検証する。設計書に「適用前の対象件数の確認 → 実行 → 適用後に 0 件の確認」の手順を書く。手作成 migration の例外は ADR-0018・0021・0022 の 3 本（0006・0009・0011）のままで増やさない。本番への適用は機能の完了条件に含めず、別途利用者が承認する
   - 根拠：Issue #206 の決定、ADR-0021・0022（例外をこれ以上広げない）、AGENTS.md「本番環境に影響する操作は確認」
   - 利用者に戻す条件：migration が必要と考えたときは、作らずに必ず利用者に戻す。本番・共有環境への適用を求められるときも戻す
2. **仕様変更に伴う既存テストの変更**
   - 方針：Issue の受け入れ条件が既存の決定（決定記録の C 番号）を置き換えると明記している場合に限り、その決定に対応する既存テストの期待・名前を変えてよい。変えたテストは PR 本文に列挙する。それ以外は変えない。テストの変更は test-writer が行い、implementer は変えない
   - 根拠：AGENTS.md「テストと品質」（期待結果を根拠なく変えない。この方針は「根拠」を、受け入れ条件に明記された決定の置き換えと定めるもの）
   - 利用者に戻す条件：変えてよいのは、置き換えられる C 番号を直接検証しているテストに限る。それ以外のテストが落ちたら、変えずに利用者に戻す
3. **決定の置き換え**
   - 方針：`docs/requirements/decision-register.md` に新しい C 番号（連番）を振り、元の記述は残して置き換えの注記を付ける。設計書・要件の機能ファイル・API 草案の該当箇所に【C-nnn により追記】を付ける
   - 根拠：Issue #206 の決定（C-164 が C-163 の S-8 を置き換えた形）
   - 利用者に戻す条件：置き換えの内容が Issue の受け入れ条件に書かれていない（要件の追加・変更に当たる）とき
4. **監査ログの粒度**
   - 方針：管理者の操作に付随して自動で起きる処理（自動参加・自動作成など）は、その操作の監査 1 件に含め、個別の監査を増やさない。利用者本人の操作は従来どおり個別に残す
   - 根拠：Issue #206 の決定（C-164 (4)）。Skill「logger」（管理者の操作は audit で記録する）を、操作の監査 1 件で満たす。上の「監査ログは、`auditLogInsert` …」の規則（同じ `db.batch` に入れる・`detail` は概要のみ）は変わらない
   - 利用者に戻す条件：付随する処理が、操作した管理者以外の利用者の権限・データを変えるときは戻す。Issue の受け入れ条件が個別の監査を求めるときも戻す
5. **機能間の参照**
   - 方針：`frontend/src/features/<name>/index.ts` で公開したものだけを参照する。公開されていなければ、その機能の `index.ts` に export を足す
   - 根拠：Skill「frontend」（ほかの機能の内部を直接参照せず、公開部分を通す）、Issue #206 の計画レビューの結果
   - 利用者に戻す条件：公開すると循環参照になる、または機能の境界を変える（機能の統合・分割）必要があるとき
6. **フロントエンドのキャッシュ**
   - 方針：ある操作でほかの機能の一覧が変わるときは、その機能の `keys.all` も成功時に invalidate する
   - 根拠：Skill「frontend-state」（サーバー状態は TanStack Query、成功後に該当キーを invalidate）、Issue #206 の計画
   - 利用者に戻す条件：invalidate では反映できず、キャッシュの設計（キーの構成）を変える必要があるとき
7. **batch の不変条件**
   - 方針：既存の `db.batch` に不変条件の確認を足すのは、Issue の受け入れ条件がデータの整合を明示して要求する場合だけ。それ以外は最小変更を優先し、足さない。足す場合は上の「複数の文の `db.batch` で前提を確認する書き方」（Issue #196）に従う
   - 根拠：AGENTS.md「作業するときの心がけ」（変更の範囲は最小限）、Issue #206 の計画（不変条件は足さない）
   - 利用者に戻す条件：データの破損・整合の崩れにつながる経路が見つかったとき（受け入れ条件に書かれていなくても報告する）

8. **利用者に確認する点**
   - 方針：計画の「利用者に確認すべき点」には、上の 1〜7 で決まるものを含めない。残るのは、次だけである。
     - 要件の追加・変更
     - 本番環境への影響（本番への適用・デプロイ・本番 DB を含む）
     - 新しいライブラリの追加
     - 破壊的な操作
     - Skill に従えない書き方、またはルールが決まっていない書き方
   - 根拠：AGENTS.md「必ず立ち止まって、利用者に確認すること」、Issue #206（計画で 7 件、着手前に 5 件の確認）
   - 利用者に戻す条件：1〜7 に当てはまっていても、立ち止まる条件に当たるときは止まる。AGENTS.md「必ず立ち止まって、利用者に確認すること」「破壊的な操作は、必ず利用者の判断を仰ぐ」と Skill「実装の進め方」の「立ち止まる条件」は、この節で緩めない

## 改行コード（Issue #208）

改行コードは LF に統一する。リポジトリ直下の `.gitattributes` の `* text=auto eol=lf` で決める。prettier の既定（`endOfLine: lf`）と CI（Linux）に合わせるためである。Windows で `core.autocrlf=true` のまま作業ツリーが CRLF になると、`npm run format:check` が改行の違いで止まる。`format:check` の基準（`--end-of-line auto` で違いを無視する等）は緩めない。

- 新しいクローン：何もしなくてよい。チェックアウト時から LF になる
- 既存のクローン・worktree：この設定を取り込んだ後、作業ツリーに残った CRLF を LF に更新する。索引（リポジトリに保存された内容）はもともと LF なので、対象のファイルを削除してから、`checkout-index` で索引の内容を作業ツリーに書き戻す（git が「作業ツリーは最新」と判断したファイルは、`checkout-index -f` だけでは書き直されず、CRLF が残るため）。未コミットの変更が失われないよう、手順1で改行以外の差が 0 件であること（未コミットの変更がないこと）を確かめてから行う。差があるファイルがあれば、先にコミットするか退避する（未追跡のファイルは対象外）。手順は Git Bash（Windows）で実行する前提である（`xargs -d` は GNU の xargs の機能で、macOS の BSD xargs では動かない）

```
# 1. 事前確認：改行以外の差があるファイルと、ステージ済みの変更が、どちらも 0 件であること（0 件でなければ、先にコミットか退避をする。ステージ済みの変更があると、後の renormalize で今回の作業と混ざる）
git diff --ignore-cr-at-eol --stat
git diff --cached --stat

# 2. 対象の一覧を、削除の前にファイルへ保存し、件数を確かめる（パスの前はタブ区切りなので cut -f2 を使う。削除すると w/crlf が出なくなるため、先に保存する）
git ls-files --eol | grep 'w/crlf' | cut -f2 > /tmp/crlf-files.txt
wc -l < /tmp/crlf-files.txt

# 3. 書き戻し（対象を削除し、索引の内容 = LF で復元する。最後の renormalize は索引の stat 情報を更新し、git status の見かけの変更を消す）
xargs -d '\n' rm -f -- < /tmp/crlf-files.txt
```
