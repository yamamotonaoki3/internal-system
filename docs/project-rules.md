# プロジェクト固有のルール

このプロジェクトだけに当てはまるルールを書く。ハーネスが管理するファイル（`AGENTS.md`・Skill等）には書き足さない。
- ハーネスの改善提案の作成先は https://github.com/ysteam0117/harness とする（利用者指定）。AGENTS.mdの事前確認と秘密情報を含めない規則は維持する。

## 書く前に確かめること

| # | 問い | はい |
| --- | --- | --- |
| 1 | このアプリの業務や中身（扱うデータ・画面・取引先・お客さまの要望）を知らないと、書けないルールか？ | ここに書く |
| 2 | 特定の技術を使うときにだけ必要なルールか？ | ハーネス（技術プロファイル）への改善の提案にする |
| 3 | どのアプリでも守るべきルールか？ | ハーネス（共通仕様）への改善の提案にする |

迷ったら、ここに書いてよい。ほかのアプリでも通用すると分かったら、ハーネスの改善の提案（Issueテンプレート「ハーネスの改善の提案」）にし、ハーネスに取り込まれたらここから消す。

## このプロジェクトのルール

<!-- 例：レシピの材料は最大50件まで -->

- 要件定義書は、`docs/requirements.md`（目次・全体像・全体の未決定事項）と、`docs/requirements/`（機能ごとの詳細・非機能要件・データモデル）に分けて書く。機能の追加・変更は、該当する機能ファイルを直し、番号付きの受け入れ条件（AC-n）を維持する。受け入れ条件は、機能ごとの見出しの下に箇条書き（`- AC-n：…`）で書く。他の文書から参照するときは「0-2 AC-4」のように機能番号を付ける。ER図は Mermaid の erDiagram で書く
- Issueは、実装する機能の単位で立てる。フロントエンド・バックエンド・DBなどの作業領域では分けない（ADR 0002）。Skill「実装の進め方」の『作業領域ごとに子Issueに分ける』『対象の作業領域を書く』は適用しない。
- 一覧APIのページ送りは、`backend/src/lib/cursor.ts`（`cursorQuerySchema`・`afterCursor`・`toPage`）を使う。OFFSETは使わず、件数は`PAGE_LIMIT`に従う（メッセージ50・その他20・最大100）
- 監査ログは、`auditLogInsert`が返す文を、業務の更新と同じ`db.batch([...])`に入れて書く（単独で実行しない）。`detail`には、件数・変更前後の識別子や状態・失敗の分類などの概要だけを入れ、入れ子にしない。本文・氏名・メール・電話・CSVの行の値・秘密情報は入れない
- 本番の権限IDの一覧とResolverは、`createAuthorizer`を呼ぶ1か所で組む。認可の拒否は、`createAuthorizer`の`authorize`が`logger.audit`で必ず記録する（`logger`は必須）。拒否の記録を省く書き方をしない
- 開発・テスト用の使い捨ての秘密の値（ADR 0014）：AIが書いてよいのは、乱数で作った値を`.env.development`・`.env.test`に入れる場合だけ。本番（`wrangler secret put`・GitHub Secrets）と実在の認証情報は利用者が入れる。値を画面・会話・ログに出さず、ファイルを読まない（項目名だけを`npm run env:check`で確認する）。動作確認で使った値は確認後に作り直す（開発・テスト用の鍵だけ。本番と実データの鍵を入れ替えない規則は`docs/secrets.md`のとおり変わらない）。安全装置に止められたら回避せず、利用者に依頼する
- 画面のスタイル（ADR 0015）：色・文字・余白などの基準値は `frontend/src/styles/index.css` の `@theme` の1か所だけで定義し、色は用途で名付ける（色を足すときは `tokens.test.ts` の組み合わせにも足す）。画面で素の `button`・`input` にクラスを書かず、`frontend/src/components/` の共通部品を使う（部品は `className` を受け取らない）。クラス名は動的に作らず、任意の値（`[...]`）は使わない。`style` 属性と `<style>` は使わない（本番のCSPは `style-src 'self'`）。フォーカスの輪郭は `index.css` の1か所で決める。詳しくは `docs/design/style-foundation.md`
- 共通レイアウト（S-01。Issue #121）：サイドバー・下部メニューの固定リンクは `frontend/src/features/app-shell/navigation.ts` の配列だけに足し、データを取るセクションは機能の部品を `SidebarNav.tsx` の決まった位置に1行で差し込む。画面のルートは `frontend/src/App.tsx` のレイアウトルートの子に足す。管理項目は `requires`（権限ID）を付け、権限による出し分けは表示の制御であり認可ではない（認可はサーバー側で行う）。動かない仮の項目は置かない。詳しくは `docs/design/app-shell.md`
- 予約取引先 `INT` の初期登録（Issue #192）：業務要件5-7 AC-9を満たすため、初期登録だけの専用migrationを1本に限って手作成する。既存migrationは変更しない。通常のDDL変更を含む他のmigrationは生成手順を使う。本番への適用には別途利用者承認が必要（ADR-0018）。
- 取引先APIの利用者単位レート上限（Issue #192）：読み取りAPI3操作の合算は固定UTC 1分あたり120回、登録・改名・無効化の3操作の合算は30回。超過時は429と `Retry-After` 秒数を返し、計数DB障害時は503で拒否する。詳細は要件API共通仕様X-8を正とする。
- 複数の文の `db.batch` で前提を確認する書き方（Issue #196。利用者承認 2026-11-09）：D1には対話型トランザクションがなく、`db.batch` は途中の文が失敗すると全体を取り消す。読んだ事実が変わっていないこと（版の一致など）は batch の先頭近くで、不変条件（オーナーが部署ごとに1人など）は batch の最後で、`CASE WHEN 条件 THEN 値 ELSE NULL END` を NOT NULL の列に入れる更新文で確かめる（条件が崩れると NOT NULL 違反で全体が失敗する）。失敗は、Repository が制約の表と列の名前で専用エラーに変換し、Service が `AppError` にする。**未知のDBエラーは握りつぶさず、そのまま再送出する**。SQLiteの一意制約は文単位で判定されるため、同じ batch の中で名前を入れ替える更新は、自分自身と衝突しない順序に並べる。例は `backend/src/db/department.repository.ts`（`assertStatement`・`bumpVersion`・`translateError`）。
- 一度だけ表示する認証情報（初期パスワード。Issue #199）：フロントエンドでは、TanStack Queryの`useMutation`に載せない（結果がMutationCacheに残るため）。呼び出しを`onSubmit`で直接awaitし、受け取った値は表示する画面の`useState`だけに置く。localStorage・sessionStorage・URL・画面遷移の`state`に入れない。APIの応答には`noStore`を付ける。詳細は`docs/design/accounts.md`
- 全社連絡の補完（Issue #200）：全社連絡（`purpose=company_general`）の初期データだけの専用migration（0011）を1本に限って手作成する（3本目の例外。ADR-0022）。既存migrationは変更しない。本番への適用には別途利用者承認が必要。チャンネルの一覧・詳細・参加APIのレート制限は、上限がX-8で決まっていないため入れず、別Issueで扱う。
- 列追加でテーブルの作り直しが生成されたとき（Issue #130。利用者承認 2026-11-11。ADR-0024）：既存テーブルへの列追加で `npm run db:generate` がテーブルの作り直し（`__new_` テーブルの作成・全行コピー・DROP・RENAME）を生成したら、生成された migration の SQL を、`ALTER TABLE … ADD COLUMN …`（列定義に DEFAULT・NOT NULL・CHECK・REFERENCES を含む）と `CREATE INDEX` に書き換える。書き換えるのはこの SQL だけで、`meta/<n>_snapshot.json` と `_journal.json` は生成されたものを使い、既存の migration は変えない。書き換えたあとに `npm run db:generate` を再実行し、差分が出ないことを確かめる。書き換えた migration の先頭に、コメントで ADR の番号（0024）を書く。この場面には利用者の確認なしで適用する。列の追加以外で作り直しが生成されたときは止まって確認する。本番への適用は別途利用者が承認する。最初の適用は migration 0013
- 検索用の表の手で書く migration と索引（Issue #155。利用者承認 2026-11-20。ADR-0031）：FTS5 の仮想の表`search_fts`は、`--custom --name`で作った migration（0033）に手で書き、`schema.ts`に書かない。batch に入れる文を組むための表の形は`backend/src/db/search-index.sql.ts`だけに置く。メッセージの本文を書く処理（投稿・返信・編集・削除）は、同じ`db.batch`の末尾に`syncMessageIndexStatements`（削除は`removeStaleMessageIndexStatements`）を足す。ガード（`changes()`を見る文）との間に挟まない。索引の文の`meta.changes`は件数の判定に使わない（FTS5 の内部の書き込みも数えるため）。既存のメッセージの索引は`reindexMessages`（手元は`node scripts/db-local.ts <環境> search-reindex`）で作る。本番での実行は #160 で利用者の承認を得てから。詳細は[search.md](design/search.md)。【2026-11-21 追記（155-B）】添付を投稿・返信に結び付ける batch と論理削除の batch の末尾にも、添付のファイル名の組（`syncAttachmentIndexStatements`、削除は`removeStaleAttachmentIndexStatements`）を足す。`message_attachments`を変える処理（#270 の添付の削除など）を新しく足すときも、同じ batch の末尾に組を足す。`search_documents`を作り直すときは、ADR-0031 の追記の手順（作り直しの前に写しを全部消す手で書いた migration → 生成のままの作り直し → 全種類の登録し直しと不一致0件の確認）に従う。既存の手元の DB に migration を当てた後は、`search-reindex`で登録し直す。【2026-11-21 追記（155-C。C-202）】案件の件名を書く batch（承認による作成・再編集）の末尾にも、件名の組（`syncCaseTitleIndexStatements`）を足す。再編集では件名を変えないときも毎回足す。案件の件名を変える処理を新しく足すときも、同じ batch の末尾に組を足す。batch の結果を添字で読むときは、末尾からの添字で読まず、主の文を積んだ時点の位置を保持して読む（末尾に索引の文を足すと位置がずれるため。例：`buildEditStatements`の`updateAt`）。既存の案件の件名の索引は`reindexCases`で作る（手元の`search-reindex`がメッセージの後に続けて登録する。本番は #160・#353 で承認を得てから）
- 既存の行がある状態からの migration の更新の試験（Issue #148 の148-B-2。利用者承認済み）：列の追加など、既存の行を持つ表を変える migration の更新の試験は、テストだけで使う空の D1（バインディング`MIGRATION_UPGRADE_DB`。`vitest.config.ts`の`miniflare.d1Databases`で足す）で行う。直前の migration までを適用して既存の行を入れ、対象の migration だけを適用して、件数・既存の列・結び付きが保たれることを確かめる。migration は番号で決め打ちせず、内容で選ぶ。`wrangler.jsonc`（本番・開発の設定）は変えない。実例は`backend/src/db/attachment-publication.upgrade.db.test.ts`
- 「最後のID以降」で読む一覧（Issue #201）：新着を`after`（直前に見たID）以降で取る一覧は、`cursor.ts`の`afterIdQuerySchema`・`toAfterIdPage`を使う。取りこぼしを防ぐため、書き込む側は「同じ部屋では、コミットの順にIDが増える」を、時計やULIDの単調性に頼らず、DBの条件付きの`INSERT … SELECT`（挿入するID以上のIDがないこと）で保証する。0行のときは原因を読み分け、IDだけが原因なら最大より大きいIDで作り直して再試行する（上限を超えたら503）。この保証はD1が書き込みを直列に実行することに依存し、読み取りレプリカ（Sessions API）は使わない前提。詳細は[messages.md](design/messages.md)。メッセージの投稿のレート制限は、上限がX-8で決まっていないため入れず、別Issueで扱う。
- 選択項目の `sql` の副問い合わせ（Issue #294）：副問い合わせに外側の表の列を書くときは、列を入れ子の SQL として渡し（表の名前つきで書き出される形）、内側の表には別名を付ける。1つの表だけを読む文（JOIN のない `.from(表)`）の選択項目の `sql` に列を直接書くと、drizzle が列を表の名前なしで書き出し、内側の表に同じ名前の列があると内側の列として解釈され、相関の条件が常に真になるため。相関の条件のテストには、「ほかの行があると、常に真になる」場合を検出できるデータ（対象でない行が別に存在する状態）を入れ、ライブラリの書き出し方に頼る箇所は `toSQL()` で確かめる。例：`attachment.repository.ts`・`notification.repository.ts`・`case-request.repository.ts`
- 利用者が替わったときの画面のキャッシュ（Issue #284。[ADR-0030](adr/0030-clear-cache-on-user-switch.md)）：セッションの利用者の ID が前に分かっていた ID と違う値に替わったら、セッション以外のクエリのキャッシュは `frontend/src/features/auth/user-switch-guard.ts`（`installUserSwitchGuard`）が枠で一括して捨てる。新しいクエリのキーに利用者の ID を足す必要はない（既に ID を入れているキーはそのまま残す）。セッションは `publishSession` で書き、同じ利用者の再ログインでは何も捨てない（0-2 AC-8 の #120 の読み方）。この決まりが守るのは画面の表示の側だけで、進行中の操作（mutation の応答の書き戻し・途中から始まる通信・ログアウトの後処理）は Issue #300、別のタブでの切り替えは Issue #298 で扱う。本人・参加者限定のデータを画面に出す機能を足すときは、利用者の切り替えのテスト（`frontend/src/user-switch.session-switch.test.tsx` と `frontend/src/test/user-switch-harness.tsx`・`render-watch.tsx`）に、その画面を足すかを確かめる
- 本文のない投稿（添付だけの投稿。Issue #270 の2つ目。C-205）の目印：`messages.body`を読む処理は、`backend/src/db/message-body.ts`の`fromStoredBody`を通す。SQL で本文が空かを比べるときは`storedBodyIsEmpty`を使う。目印の値を、ほかの場所に書かない（テストの期待値だけは、独立に決めるためリテラルで書く）。目印を知っているのは`message-body.ts`だけで、API・画面は本文なしを空文字で受け渡す。漏れると、空白が見える・中身のない検索用の行ができる。設計と出口の一覧は[messages.md](design/messages.md)
- 資格を失ったときの読み込み直し（Issue #338。C-206。[ADR-0033](adr/0033-reload-page-after-access-loss.md)）：案件の資格を失ったと確定したら、片付けの後に、`frontend/src/features/access-loss/reload-after-access-loss.ts`の入口`requestAccessLossReload`を呼ぶ。呼ぶのは、この画面で参加者だったことを見た後に外されたと分かったときと、本人の退出だけ（最初から非参加で開いた場合などは呼ばない）。`window.location`を触るのは`browser-location.ts`だけにする。画面のテストでは、入口を`frontend/src/test/setup.ts`で`vi.fn`に差し替えている（待機の状態・購読・タイマーをテストの間に残さないため）。入口そのもの（と、入口の状態を読む境界、入口を本物のまま通す画面のテスト）は、そのファイルで`vi.unmock("…/reload-after-access-loss")`する。知らせの保存先（`sessionStorage`）に書くのは種類（`lost`・`left`）だけで、利用者の ID・案件の中身は書かない。詳細は[access-loss.md](design/access-loss.md)

## 既定の方針（AI が質問せずに適用する判断。Issue #214）

## 改行コード（Issue #208）

改行コードは LF に統一する。リポジトリ直下の `.gitattributes` の `* text=auto eol=lf` で決める。prettier の既定（`endOfLine: lf`）と CI（Linux）に合わせるためである。Windows で `core.autocrlf=true` のまま作業ツリーが CRLF になると、`npm run format:check` が改行の違いで止まる。`format:check` の基準（`--end-of-line auto` で違いを無視する等）は緩めない。

- 新しいクローン：何もしなくてよい。チェックアウト時から LF になる
- 既存のクローン・worktree：この設定を取り込んだ後、作業ツリーに残った CRLF を LF に更新する。索引（リポジトリに保存された内容）はもともと LF なので、対象のファイルを削除してから、`checkout-index` で索引の内容を作業ツリーに書き戻す（git が「作業ツリーは最新」と判断したファイルは、`checkout-index -f` だけでは書き直されず、CRLF が残るため）。未コミットの変更が失われないよう、手順1で改行以外の差が 0 件であること（未コミットの変更がないこと）を確かめてから行う。差があるファイルがあれば、先にコミットするか退避する（未追跡のファイルは対象外）。手順は Git Bash（Windows）で実行する前提である（`xargs -d` は GNU の xargs の機能で、macOS の BSD xargs では動かない）

```
# 1. 事前確認：改行以外の差があるファイルと、ステージ済みの変更が、どちらも 0 件であること（0 件でなければ、先にコミットか退避をする。ステージ済みの変更があると、後の renormalize で今回の作業と混ざる）
git diff --ignore-cr-at-eol --stat
git diff --cached --stat

# 2. 対象の一覧を、削除の前にファイルへ保存し、件数を確かめる（パスの前はタブ区切りなので cut -f2 を使う。削除すると w/crlf が出なくなるため、先に保存する）
git ls-files --eol | grep 'w/crlf' | cut -f2 > /tmp/crlf-files.txt
wc -l < /tmp/crlf-files.txt

# 3. 書き戻し（対象を削除し、索引の内容 = LF で復元する。最後の renormalize は索引の stat 情報を更新し、git status の見かけの変更を消す）
xargs -d '\n' rm -f -- < /tmp/crlf-files.txt
xargs -d '\n' git checkout-index -f -- < /tmp/crlf-files.txt
git add --renormalize .

# 4. 事後確認：w/crlf が 0 件であること、git diff が空であること、git status --short --untracked-files=no が空であること
git ls-files --eol | grep -c 'w/crlf'
git diff --stat
git status --short --untracked-files=no

# 5. 後始末：一時ファイルを消す
rm -f /tmp/crlf-files.txt
```

- **変わらないもの**：レビューの回数の上限（最大 3 回）・重大な指摘の扱い・記録の仕方は、Skill「レビュー」のままとする

## 2026-11-16決定の進め方の軽量化と範囲の絞り込み（Issue #267）

利用者の決定（2026-11-16、[Issue #267](https://github.com/yamamotonaoki3/internal-system/issues/267)）。背景：機能の実装が約35件残り、直近の実績は1日あたり1〜1.5件で、完了まで5〜7週間かかる。#138 では、軽微な指摘1件ごとに CI と最新の状態の確認を1周し（1日に3回）、ミューテーションの絞った診断でマージを約3時間待った。その間に見つかった本番の不具合は0件だった。ハーネスのルールより緩めるものは、[ADR-0028](adr/0028-lighter-process-and-narrowed-scope.md) に理由を記録し、「ハーネスのルールより緩めるもの」に載せた。

### 進め方

- **A 軽微な指摘でマージを止めない**：重大0件であれば、軽微な指摘は後追いの Issue に回してマージしてよい。最新の状態の確認（head の SHA が一致するレビュー）は、本番のコードが変わったときだけ行う。文書・テストだけの差分は、CI の成功だけでマージしてよい
- **B ミューテーションでマージを止めない**：認可・個人情報に関わるファイルだけ、絞った診断をマージの前に行う。そのほかはマージを止めず、リリース前の検証（#160）でまとめて実行する
- **C 計画レビューは最大2回**：重大な指摘が残る場合だけ3回目を行う。データ破損・認証の回避・情報漏えいにつながる指摘は、これまでどおり解消するまで続ける
- **D デモ動画は親 Issue の区切りでまとめて録る**：Issue ごとには録らない
- **E 並列**：依存しない Issue を、別の worktree で2件まで並列に進める。Stryker・E2E・Codex などの重い処理は同時に動かさない

### 役割の分担（2026-11-16 から）

統括は Claude Code とし、実装はそのサブエージェント（`.claude/agents/`）が行う。計画レビューとコードレビューは Codex が行う（`codex exec -s read-only`）。Codex が実装した変更は、Claude Code がレビューする。GitHub Actions のレビューは、#257 まで無効のままとする（2026-11-15 決定の役割分担の表と、コードレビューの手元の実施方法を、これに置き換える）。

### 範囲を絞る

目的（手元で動くデモ）に要らない機能を後回しにする。Issue は閉じない。

- 後回し：#117・#129・#152・#153・#157・#158・#159・#222・#223
- 優先：案件の中心（#146〜#150）・添付（#140）・検索（#155）・アカウントの無効化（#128）ほか

### 置き換える記述と、変えないもの

- 「2026-11-15決定の役割分担の切り替え」の、役割の表・計画レビュー・コードレビューの実施方法：上の「役割の分担」に置き換える
- 同節の「マージの順番」の head の SHA の確認：A のとおり、本番のコードが変わったときだけ行う。CI の成功とレビューの両方を確かめる考え方は、本番のコードが変わる差分で維持する
- 同節の「変わらないもの」の計画レビューの回数：C のとおり最大2回（重大が残る場合だけ3回目）。コードレビューの回数の上限は変わらない
- 「2026-11-09承認のミューテーション・E2Eの実行範囲」「2026-11-15承認のIssue #258ミューテーション改善」の、マージ前の絞った実行：B のとおり
- 変えないもの：コードレビュー（別の AI）、E2E、秘密情報・テストデータ・破壊的な操作・本番への操作の決まり

### 運用の境界（統括の解釈。安全な側に倒す。利用者が変えたら従う）

1. **「認可・個人情報に関わるファイル」**：その PR で変えたファイルのうち、(a) 認証・認可・見える範囲の判定を持つもの（`services/` の権限・参加・状態の判定、`db/` の見える範囲・書き込みの条件の SQL、`lib/` の判定の規則、ミドルウェア）、(b) 個人情報・秘密の値を扱うもの（暗号化・復号、本名・メール等の項目の出し分け）。迷ったら含める。画面の表示だけの部品は含めない
2. **「本番のコードが変わったとき」**：文書（`docs/`・`*.md`）とテストのファイル（`*.test.*`・`e2e/`・テスト用の部品・シード）以外は、すべて当たる。設定・migration・依存・CI・スクリプトの変更も「変わった」に含める
3. **「文書・テストだけの差分」の例外**：既存のテストの期待を変える、またはテストを消す・スキップする変更を含む場合は、別の AI のレビューを行う。テストを足すだけの差分は、CI の成功だけでよい
4. **「親 Issue の区切り」**：その親 Issue の、優先する範囲の子がすべてマージされたとき。または利用者が求めたとき
5. **並列の細部**：Issue ごとに別のブランチと worktree を使う。同じファイルを大きく変える Issue 同士は並列にしない。migration の番号は、先にマージするほうが先の番号を取り、後のほうが合わせ直す。E2E・Stryker・Codex・全体のテストは1つずつ動かす（検証用の DB とポートを共有するため）

## 2026-11-16決定の効率化の決まり（Issue #271）

利用者の決定（2026-11-16、[Issue #271](https://github.com/yamamotonaoki3/internal-system/issues/271)）。利用者が示した効率化の検討の資料（リポジトリの外にある）と、直近の実績（#138）を照らして選んだ。レビューの終了条件・ミューテーションの段階化・並列は #267 で取り入れ済み。ハーネスのルールより緩めるもの（1）は、[ADR-0028](adr/0028-lighter-process-and-narrowed-scope.md) の「2026-11-16 の追加（#271）」に理由を記録し、「ハーネスのルールより緩めるもの」に載せた。

### 取り入れるもの

1. **手元の検証を段階にする**：CI（`.github/workflows/check.yml`）は、コードを変えた PR で `npm run check` の全体を実行している（文書だけの変更は `npm run security` だけ）。CI は E2E を実行しない。手元で同じ全体をもう一度実行しない。手元は、変えたファイルの lint・format、型チェック、関係するテストのファイル、関係する E2E（範囲は ADR-0020）にする。全体のテストは CI に任せ、CI が失敗したら原因を直す。認可・個人情報に関わるファイルの絞ったミューテーションは #267 のとおり。AGENTS.md「完了の定義」2 の「プロジェクト全体に対して通っている」は、CI の成功で満たす
2. **テストの層の役割を計画で決める**：計画のテストケースの表に「どの層で確かめるか」と理由を書く。同じ性質を複数の層で重ねて確かめない（下の層で検出できるものは下の層だけ）。E2E は、利用者の主な操作の流れと、実ブラウザでしか検出できないもの（フォーカス・CSP・実際の配置など）に絞る。減らすときは、その欠陥をどの層が検出するかを書く（閾値を下げる・失敗するテストを消す・期待値を実装に合わせることはしない）
3. **期待値を実装から独立に決める**：実装の後にテストを足す場合（ミューテーションの生き残りへの対応など）も、期待値は受け入れ条件・設計書から決める。実装の動きを写して期待値にしない。レビューで「誤った動きを固定していないか」を確かめる
4. **失敗を分類してから直す**：失敗は、環境の不備（ポート・メモリー・一時的な不安定）と、製品の不具合・テストの誤りに分けてから対処する。環境の不備での再実行は1回まで。2回続いたら止めて報告する（メモリー不足で止められた処理は、利用者に聞かずに再実行しない）
5. **時間を記録する**：Issue ごとに、工程（計画・計画レビュー・テスト・実装・品質チェック・コードレビュー・CI・利用者の回答待ち）のおおよその時間と、やり直しの回数を、PR の本文の「確認したこと」に書く。取れない値は推定せず「未取得」と書く。次の改善は、この記録から決める。PR テンプレート（`.github/pull_request_template.md`）はハーネスが管理するため変えず、PR の本文に自由な行として足す
6. **レビューの依頼に終了の基準を書く**：別の AI への依頼文に、「好みの修正・合意済みの決定への反対は指摘にしない」「重大（データ破損・認証の回避・情報漏えい・受け入れ条件の未達）と軽微を分ける」を入れる

### 取り入れないもの・保留

- **実装を先に書き、テストを後で書く（画面など）**：保留。直近の実績では、時間を使っているのはレビューの往復・重い検証の待ち・直列の実行で、テストの順番ではない。資料も、順番より「期待値の独立」「変更の粒度」「検証の範囲」が効くとしている。テスト先行は `AGENTS.md` の核のルールで、緩めるには実測が要る。5 の記録がたまってから判断する
- **並列の数を増やす**：取り入れない。PC のメモリーと、検証用の DB・ポートの共有のため（2件まで。#267）
- **Claude Code と Codex に同じ調査をさせて照合する**：いまは行わない。調査そのものに時間と利用量がかかる。利用者が求めたら行う
- **常設の指示を短くする・Skill を必要なときだけ読む**：ハーネスが管理するファイルなので、このプロジェクトでは変えない。ハーネスの改善の提案にする

### 並列用の worktree の設定ファイルの作り方（利用者の承認 2026-11-16）
